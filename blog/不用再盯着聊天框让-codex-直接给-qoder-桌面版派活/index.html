不用再盯着聊天框：让 Codex 直接给 Qoder 桌面版派活

Agent 协作实战②：通过 H5 接口派发任务、接收结果

发表于 2026-10-23约 7 分钟AI桌面自动化Agent
目录
手机能控制桌面，入口藏在哪里？先让桌面 Agent 回一句话实际跑通的链路返回 201，还不等于 Agent 开始干活通了以后，怎么安排几个 AI 干活？Qoder 做实现，Codex 做 Review一个负责调研，一个负责核查额度快用完时，把工作交出去CUA、ACP、H5，各自有用武之地

装了好几个 AI 编程工具之后，你可能会遇到一个尴尬：它们都能干活，却总要你在中间传话。

Codex 写方案，复制给 Qoder；Qoder 做完，再把结果拿回来让 Codex Review。审查发现问题，又得搬一趟。

之前，我用 CUA 跑通过这条链路：让 Codex 操作 Qoder 桌面版的聊天框，输入消息、读取回答、继续追问。人从复制粘贴中解放出来，消息改由 Agent 通过界面传递。

但还有一个问题：每次派活，都要找到聊天框、输入文字、点发送吗？

这次继续往下查，发现了另一条入口：Qoder 官方 H5 背后的远程任务接口。

经过两轮实测，Codex 已经能通过这组接口创建本机 Qoder 桌面任务，发送消息，再用事件流读回回答。

手机能控制桌面，入口藏在哪里？

线索来自 Qoder 的官方远程控制功能。

桌面版保持运行，开启“允许 Qoder Mobile 控制此设备”，再用同一个账号登录手机端或 H5，就可以查看任务、追加指令、处理等待确认的交互。本机任务仍由桌面客户端访问工作区并执行。官方说明

官方提供的 H5 入口是 qoder.com/m，国内版是 qoder.cn/m。两套产品的账号和数据分别独立，需要与桌面产品匹配。下载与入口说明

这就留下了一个很直接的线索：浏览器里的消息，必然要通过某条通信链路送到桌面任务。

检查官方 H5 当前加载的前端代码后，找到了这组路径：

页面操作 背后的 HTTP 接口
找到设备和执行环境 GET /api/v1/remote/environments
查看任务列表 GET /api/v1/remote/sessions
创建任务 POST /api/v1/remote/sessions
发送消息和控制指令 POST /api/v1/remote/sessions/{id}/events
读取历史事件 GET /api/v1/remote/sessions/{id}/events
接收实时结果 GET /api/v1/remote/sessions/{id}/events/stream

前端代码里还能看到切换模型、中断执行、响应审批等控制消息。它们共用会话事件入口，通过不同的事件内容表达操作。本次核查的前端构建：0.0.56

于是，下一步很明确：沿着 H5 自己使用的接口，验证外部 Agent 能否把消息交给本机 Qoder。

先让桌面 Agent 回一句话

测试刻意选得很小：不改代码，不碰业务文件，只做两轮对话。

第一轮，Codex 创建桌面任务并发送：

这是接口连通性测试，不要调用工具，不要读写文件。请记住测试口令：海棠643。只回复：H5接口连接成功，19+23=42。

Qoder 返回：

H5接口连接成功，19+23=42。

接着，Codex 在同一个远程会话里追问：

继续刚才的测试，不要调用工具。上一条让你记住的测试口令是什么？只回复口令。

回答是：

海棠643

第二轮没有重复口令。它验证了会话上下文确实延续下来，而不是每次调用都重新开始。

检查项 实测结果
创建任务 HTTP 201，执行类型为 desktop
执行环境 environment_type=qoder，对应本机 Mac
第一轮结果 正确返回指定内容
追加消息 HTTP 200，返回新的事件序号
实时接收 HTTP 200，内容类型为 text/event-stream
第二轮结果 正确返回“海棠643”
桌面对应关系 侧栏出现“接口连通测试”，本地任务 ID 与执行事件一致

这次，消息的提交和回答的读取都通过接口完成。桌面界面用于检查设置与核对任务。

实际跑通的链路

Codex
  ↓ 在已登录的浏览器页面中发起同源请求
Qoder H5 内部 HTTP 接口
  ↓ 按所选设备与执行环境派发
本机 Qoder 桌面任务
  ↓ 返回执行事件与回答
SSE 事件流
  ↓
Codex 接收结果，继续追问

这里有两个容易混淆的地方。

首先，这次创建的是本机桌面任务。接口返回的 execution_type=desktop，执行环境也是本机 Qoder。它与启动 Qoder CLI、通过 ACP 调用 CLI，以及创建云端 Agent 任务，分别属于不同的接入方式。

其次，浏览器使用 HTTP 发送请求，通过 SSE 接收结果。SSE 可以理解为一条持续返回更新的响应：服务端有新事件，就往这条连接里发送。调用方由此接收状态变化、Agent 回答和完成结果，不必反复刷新聊天页面。

这次验证使用了浏览器已有的登录态。请求在 Qoder H5 页面内执行，由浏览器携带同站 Cookie，并按网页实现带上设备标识和接口版本头。没有把登录凭据复制到脚本或文章里。

CDP 在这条链路里负责连接浏览器、执行页面请求；它连接的对象是 Chrome。Qoder 桌面任务由官方远程控制通路接收。

返回 201，还不等于 Agent 开始干活

实测中最值得记住的坑，就出在创建任务这一步。

最初只带工作目录和模型等字段，服务端返回了 HTTP 201。网页任务列表也出现了新记录，但会话一直停在 init，没有取得桌面执行结果。

继续查看 H5 的构造逻辑，才发现它对 Qoder 桌面环境有专门的处理。创建不绑定项目的聊天任务时，使用的上下文包含：

{
  "client_type": "qoder",
  "model": "qfmodel",
  "workspace_type": "virtual",
  "cwd": "",
  "extra": {"workspace_id": ""}
}

按网页的桌面专用结构补齐字段后，新任务才跑出了完整的两轮结果。这里的 qfmodel 是本次环境中 Qwen3.8-Flash 的模型标识，不能据此假定所有版本都保持一致。

所以，验收至少要走完三步：服务端接受任务、桌面端接到任务、Agent 返回结果。一个成功状态码，只能证明其中一部分。

另一个实际问题是请求超时。浏览器的调试授权弹窗可能挡住操作；超时也不代表服务端没有创建任务。先检查已有会话和事件，再决定是否重试，可以避免一次测试变成两份任务。

通了以后，怎么安排几个 AI 干活？

最有用的变化，是可以围绕一个持续存在的任务会话安排分工。

Qoder 做实现，Codex 做 Review

把需求、允许修改的目录和验收条件写清楚，由 Codex 交给 Qoder。

Qoder 完成后，Codex 根据返回结果检查实际 diff、测试输出和文件内容。发现问题，就向同一会话追加具体修改要求。Qoder 能继续使用前面的上下文，用户不用再重新转述项目背景。

接口承担消息传递，审查仍要落到实际产物上。Agent 说“做完了”，还需要代码和验证结果支撑。

一个负责调研，一个负责核查

例如，让 Qoder 整理某个工具的接入方式，报告统一放进共享的协作目录。Codex 再核查来源、检查适用版本、指出结论中的问题，并把返修意见送回原会话。

文件承载详细材料，会话承载派发与反馈。任务长了，也不必把整篇报告一遍遍复制进聊天框。

额度快用完时，把工作交出去

任务做到一半，某个工具的额度开始吃紧，可以提前整理目标、当前进度、修改范围和下一步，把剩余工作交给另一个 Agent。

额度耗尽的工具无法继续承担调度，所以交接最好发生在额度将尽时。工作状态留在文件里，接手方能继续推进；原工具恢复可用后，再回来审查结果。

这些分工需要逐步补上任务状态、交付文件和异常处理，而这次跑通的收发通路，提供了其中的基础能力。

CUA、ACP、H5，各自有用武之地

方式 适合解决的问题 本次相关结果
CUA 操作桌面界面，适应只有按钮和输入框的应用 此前已跑通 Qoder 桌面两轮对话
ACP 通过统一协议调用支持它的 CLI Agent 已用于本地多个 CLI 的协作验证
H5 内部接口 借助官方远程通路创建和继续桌面任务 本次跑通创建、续聊和 SSE 结果读取

选择哪条路，取决于任务要落在哪里。CLI 协作可以走 ACP；需要进入桌面应用中的任务，则可以考虑 CUA 或该产品已有的远程入口。

H5 这条路也有明确边界：这些路径来自网页实现，目前没有公开的稳定桌面 API 契约。本次验证覆盖两轮对话和结果读取，依赖已登录浏览器、在线桌面端及远程控制开关。代码修改、复杂审批和长任务恢复，还需要各自的验收。

测试结束后，临时远程控制已恢复关闭，未执行的探测会话已归档，有效测试任务保留供复核。

原来，桌面 Agent 的协作入口，可能就藏在“用手机继续任务”这个功能里。

这次我们顺着它找到了接口，也让另一位 Agent 接上了话。以后安排“你实现、它审查、发现问题再改一轮”，就有机会把消息往返也一起交给 Agent。
