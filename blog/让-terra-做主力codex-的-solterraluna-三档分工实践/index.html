让 Terra 做主力：Codex 的 Sol、Terra、Luna 三档分工实践

整理日期：2026-10-27 · 本机配置实践

发表于 2026-10-27约 6 分钟

之前，我的 Codex 默认使用 GPT-6.1 Sol，另配一个 GPT-6 Luna 子代理。Sol 负责沟通、方案、实现和把关，遇到边界明确的工作，再交给 Luna。

这套分工容易理解，却留下了一个问题：常规开发仍然经常由 Sol 承担，而“边界明确就交给 Luna”的规则，又把业务实现和机械修改混在了一起。

加入 GPT-6.1 Terra 后，我决定调整默认入口：Terra 负责日常工作，Sol 处理复杂问题，Luna 承接轻量执行。

这篇记录的是分工思路和已经落地的配置调整。三种模型的任务边界属于当前的工作策略，需要继续根据真实项目表现修正。

为什么把默认主模型改成 Terra

最初考虑过保留 Sol 当主代理，只增加一个 Terra Worker，让它承接常规开发。

但如果每个日常任务都先由 Sol 理解、拆分，再交给 Terra，做完还要由 Sol 复核，那么 Sol 仍然参与了完整流程。对于一个局部修复或常规功能，这种交接未必划算。

因此，这次把日常协调也交给 Terra：它直接与用户沟通，理解常规需求，完成实现、整合和验收。只有出现复杂架构取舍、疑难故障或高风险改动时，再调用 Sol。

官方模型选择指南将 Terra 列为范围明确的代码修复、目标明确的电脑操作和基于材料的写作的适用选择，同时将 Sol 列为复杂项目的候选。这为分工提供了参考；是否适合自己的项目，仍要看实际完成情况。

三个角色，各自负责什么

角色 模型 当前职责
Terra：日常主力 gpt-6.1-terra 常规需求澄清、任务拆分、功能开发、局部重构、缺陷修复、测试实现、浏览器与 GUI 操作、整合和常规验收
Sol：复杂任务专家 gpt-6.1-sol 架构取舍、疑难故障根因分析、复杂跨模块改动、高风险审查、重大变更验收
Luna：轻量执行 gpt-6-luna 修改方式明确、复杂度低且容易验证的简单修复、机械修改、格式整理、统一批量替换、简单测试补充、文档和数据整理

Terra 作为主代理时，可以按需要调用 Sol 和 Luna。作为受托子代理时，三个 Worker 都只完成当前范围，不继续委派，以免交接层级不断增加。

Sol 也保留在用户明确指定时承担主代理的能力。遇到复杂项目，可以从一开始就选择 Sol，无须先让 Terra 尝试一轮。

分配任务，要看需要作多少判断

“改几个文件”“是不是写测试”“是否批量处理”，都不足以单独决定用哪个模型。

例如，同样是补测试：已有明确输入、输出和测试样例，只需补几个相近分支，可以交给 Luna；如果需要梳理业务状态、识别并发边界，或设计故障恢复测试，就应由 Terra 或 Sol 处理。

批量修改也是如此。统一替换一个确定的配置键，通常容易验证；修改多个模块中的同名字段，却可能牵涉不同业务语义和兼容性，不能因为重复次数多就交给 Luna。

这次采用三个判断维度：

  • 复杂度：需要多少业务理解、推理和方案取舍？
  • 风险：出错后会影响多大范围，是否涉及关键契约、权限或数据？
  • 验证难度：有没有清楚的完成标准，能否通过相关测试或实际操作确认结果？

范围清楚、需要一定业务理解的常规开发，由 Terra 执行。修改路径明确、低风险且验证直接的工作，才适合委派给 Luna。复杂判断和高风险问题交给 Sol。

简单任务直接做，委派要算交接成本

有三个模型可用，并不意味着每次都要启动三个代理。

主代理已经读过相关代码，只需做一个小改动时，直接完成通常更省事。另开子代理需要重新说明背景、划定范围、等待结果，再复核改动，这些工作也会消耗时间和 Token。

因此，配置里加入了一条原则：只有委派收益超过上下文交接和复核成本时，才启动子代理。

需要委派时，交接内容必须包含目标、允许修改的范围、禁止项、依赖关系，以及验收标准或验证命令。同时明确要求保留他人改动，避免不同任务相互覆盖。

遇到什么情况，应交回主代理

任务执行过程中发现需求有歧义、修改即将超出范围、根因不清或验证持续失败时，子代理应返回证据和最小下一步，由主代理判断。

这里需要区分两类问题：用户究竟想要什么，需要向用户澄清；复杂技术方案怎样取舍，可以请 Sol 分析。不能指望换一个模型就自动补齐缺失的用户意图。

常规任务由 Terra 验收即可。复杂决策、高风险审查和重大变更验收，再交给 Sol 专项处理。这样能让审查精力与风险相匹配。

这次具体改了哪些配置

本机调整涉及五个文件：

文件 调整内容
~/.codex/config.toml 将默认 model 从 gpt-6.1-sol 改为 gpt-6.1-terra
~/.codex/AGENTS.md 将 Sol + Luna 两档规则改为 Terra、Sol、Luna 三档分工，并加入委派成本和升级条件
~/.codex/agents/terra-worker.toml 新增 Terra Worker，定义主代理职责及受托执行边界
~/.codex/agents/sol-worker.toml 将 Sol 调整为复杂任务专家，保留用户指定时承担主代理的能力
~/.codex/agents/luna-worker.toml 将 Luna 的范围收紧到低复杂度、修改方式明确且容易验证的任务

默认模型的关键配置是：

model = "gpt-6.1-terra"

terra-worker.toml 定义的是一个可调用的自定义代理。仅新增该文件，不会改变默认主模型；默认入口仍由 config.toml 的模型设置控制。

模型分工段落属于 Codex 自有内容，本次没有改动由跨宿主策略源维护的标记块，也没有修改其他宿主配置。

验证完成到哪一步

修改前已经备份原文件。修改后完成了以下检查：

  • 主配置及三个 Worker 文件均能通过 TOML 解析，必要字段存在。
  • 默认模型为 Terra，三个 Worker 的名称与模型映射一致。
  • config.toml 除默认模型外，其余配置与备份一致。
  • AGENTS.md 的前导内容和全部同步块与备份一致，变更仅在模型分工段落。

这些检查证明配置文件已按预期更新。尚未完成新会话中的三个模型实际调用，也没有进行同题质量、耗时和用量对比。 当前会话的模型不会因为配置文件被修改，就自动切换成 Terra。

为什么不写死任务比例和节省幅度

50% Luna、35% Terra、15% Sol，可以作为讨论分工的例子，但我没有把它写进规则。

任务数量占比不等于 Token 占比。一个架构问题可能比十次简单替换消耗更多上下文；较轻模型如果反复返工，也可能增加总体成本。主代理的拆分、交接和审查同样需要计入。

API 单价也不能直接换算成 Codex 套餐的额度消耗，更不能据此承诺实际节省多少。

后续更有用的观察是：每类任务能否一次完成，返工几次，主代理需要补做多少，最终花了多少时间和用量。先让 Terra 承担日常工作，再用这些记录调整边界，比追求固定比例更适合长期使用。
