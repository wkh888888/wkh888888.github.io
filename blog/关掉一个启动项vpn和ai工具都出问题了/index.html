一次启动项清理引发的故障：沿着合规插件与 DNS 证据链，找回 VPN 和 AI 工具的连接。

日期：2026-09-30 · 故障记录：2026-09-17

清理 Mac 启动项时，我关掉了一个看起来不起眼的合规插件启动项。随后，零信任客户端登录提示“请求超时 (esm)”，AI 编码工具也卡在“等待模型响应”。

两个应用同时出问题，很容易先怀疑网络或账号。排查日志后，线索指向两件事：合规插件服务没有启动，以及 VPN 断开后仍残留的隧道 DNS。

本文记录的是 2026-09-17 的本机故障与验证结果。同样的报错可能有其他原因，下面的证据链比报错文字本身更有参考价值。

说明：文中不点名具体产品。客户端统一称“零信任客户端”，报错代号 esm 与错误码 C0017 保留原样——它们是故障现场的字面线索，也是搜索时能捞到这篇文章的关键词。

症状速查

  • 登录页显示“请求超时 (esm)”
  • （排查时手动停掉守护服务后）出现过“系统错误 C0017”
  • 副作用：AI 编码工具会话长时间卡在“等待模型响应”，报网络错误 3002

如果问题出现在清理启动项之后，先核对合规插件服务是否被禁用；仅凭 esm 超时提示，还不能确定根因。

先找到失联的合规插件

一句话：我在某个清理工具的“开机启动项管理”里关掉了合规插件的启动项。

它是零信任客户端的合规插件后台服务。本次日志显示，身份认证成功后向合规模块发送证书消息失败，随后出现插件连接失败和请求超时。服务被禁用与这条错误链相吻合。

本次认证接口已经返回成功，所以后续排查重点转向本机插件连接。

DNS 残留如何影响直连应用

本次排查记录涉及三类网络变化：

  • 创建 WireGuard VPN 隧道接口
  • 把 macOS 默认 DNS 改成隧道 DNS 10.x.x.x
  • 注入部分经隧道访问的内网路由

DNS 是系统级设置。一旦隧道、路由或这个 DNS 没能干净恢复，任何不走代理、依赖本机解析的应用都会受影响——“直接连接”模式的 AI 工具正是这类。

本地功能、缓存和既有长连接可能还正常，所以现象会显得很随机：往往在启动、同步配置、刷新权限或调用云端服务时才炸。

实测记录（2026-09-17）

  • VPN 状态已显示“已断开”，但 Wi-Fi DNS 仍是隧道 DNS，且到它的路由不再经过原隧道 → 向它查询外部域名超时
  • AI 编码工具会话卡在“等待模型响应”，报网络错误 3002；日志里的真实错误是 getaddrinfo ENOTFOUND <目标域名> —— 目标域名压根没解析成功
  • 同一台机器上，绕过代理直连该域名在解析阶段就超时；走系统代理 127.0.0.1:7890 则能到达
  • 把“网络代理”改成“跟随系统”后，日志确认该域名从 DIRECT 变成 PROXY 127.0.0.1:7890；随后返回服务端 429 —— 说明这步已经绕过了 DNS 故障，429 是独立的额度限制

这里有一个容易误判的地方：代理 curl 能通，不足以证明直接连接可用。应用走哪条链路，排查就验证哪条链路。

结论：这次故障已定位到“隧道 DNS 残留 + 直连方式”；但不能据此认为历史上每次 AI 工具超时都由同一个原因造成。

恢复服务，再验证连接

  1. 重新开启服务：清理工具 → 开机启动项管理 → 重新启用合规插件相关的启动项
  2. 重启 Mac，让合规插件和系统守护服务重新加载
  3. 重开客户端并登录
  4. 仍报 esm 超时：用客户端“发送诊断日志”，联系企业 IT / 安全客户端管理员，说明「合规插件服务已启用，仍连不上合规模块」

网络侧的临时办法：本机代理可用时，把应用的“网络代理”设为“跟随系统”。本次实测有效，但它依赖代理常驻，也不修系统 DNS、不解决额度限制。

从日志确认，而不是从报错猜测

客户端本地日志的顺序很清晰：

  1. 设备授权与用户认证接口返回成功 → 认证服务和基础网络是通的
  2. 发送 certificates 给合规模块时：记录「esm 断开连接，消息无法发送」
  3. 随后：记录「连接 esm 失败：connect collect-plugin three port error」
  4. 重试后：“合规插件连接失败”，约 11 秒后报「esm 请求超时」

日志位置形如 ~/Library/Application Support/<客户端>/logs/zta.log

日志可能含认证信息、证书或设备信息。对外发出前请用客户端自带的“发送诊断日志”，或先让 IT 脱敏。

排查过程中出现的 C0017

排查时我手动停过系统守护服务（形如 com.<厂商>.zta.Agent），之后客户端连不上本机守护端口，就显示 C0017。

它不是新的服务端错误：恢复守护服务或重启即可消除。

长期修复该怎么提

启动项误关在本机能修。DNS 和路由也是本机客户端 / 守护进程落地的，但是否由管理后台下发策略尚未核实，需企业 IT 或管理员确认。

给 IT / 安全客户端管理员的一段话术，可直接贴：

零信任客户端在 macOS 上把 Wi-Fi DNS 设为隧道 DNS。实测 VPN 显示断开后该 DNS 仍残留且查询超时，导致直连应用无法解析外部域名。建议先检查断开时的 DNS / 路由清理逻辑，再评估对内网域名走 split DNS 或提供可靠回退。请确认应由管理后台策略还是客户端修复。

不建议手工改客户端的 DNS / 路由 / 隧道配置：可能被守护服务覆盖，也可能破坏所在组织的安全访问策略。

下次清理启动项之前

不要在清理工具的“开机启动项管理”里禁用来源不明的企业安全、VPN、合规或守护类服务。要清理后台项，先确认归属和用途——这类合规插件必须保持启用。
