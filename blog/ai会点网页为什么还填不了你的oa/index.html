AI 会点网页，为什么还填不了你的 OA？

“我明明已经登录了，为什么你还让我重新登录？”

一次出差申请，卡在了这个问题上。

用户的 Chrome 已经打开历史单，要求也很明确：参考旧单，换成指定的一周，五天，其他信息保持一致。AI 打开 OA，却看见登录页。

原因很快找到了：工具连接的是另一套浏览器配置。用户已经登录的 Chrome，与自动化工具控制的 Chrome，不是同一个会话。

后来换成 CUA 的原生窗口路径，读到了原窗口里的参考单，才完成新建、填表、日期和行程核对，最后保存草稿。

这件事说明，讨论“AI 能不能操作浏览器”，至少要分开三个问题：连到了哪个浏览器、通过什么方式操作、拿什么证明做完了。

先把几个常见名字放回各自的位置

CUA、CDP、Playwright、BrowserSkill、web-access 经常一起出现，但它们代表的东西不同。

层次 要回答的问题 例子
Agent 与模型 谁理解目标、判断下一步？ Codex 等 Agent 及其使用的模型
操作工具与框架 用什么组织观察、点击和输入？ BrowserSkill、bb-browser、Playwright；web-access 中的浏览器工具
连接与控制通道 工具怎样接到目标软件？ CDP、浏览器扩展 API、操作系统辅助功能与输入接口
运行对象 实际操作的是谁？ 某个 Profile 的标签页、独立自动化浏览器、桌面应用窗口

CDP 是浏览器的调试与控制协议；Playwright 是自动化框架。模型可以调用 Playwright，也可以调用通过 CDP 封装的工具。CUA 则描述 AI 使用电脑界面的能力，具体工具可能结合截图、辅助功能信息或浏览器结构。CDP 文档；Playwright 文档

所以，不能把这些名字直接理解成几种互斥技术。BrowserSkill 的扩展路径也使用 CDP；AI 调用 Playwright 与固定脚本运行 Playwright，又是两种不同的执行组织方式。

三条操作路径，一种流程组织选择

从 Agent 的调用入口看，本文关注三条常见路径：

扩展连接：Agent → 工具 / 本地服务 → 浏览器扩展 → 网页
CDP 连接：Agent → 工具 / 本地代理 → CDP → 浏览器会话
系统界面：Agent → 电脑操作工具 → 窗口、控件与输入 → 浏览器或桌面应用

扩展连接也可能使用 CDP。这里按入口区分路径，不是在划分互不重叠的底层协议。

路径 本系列中的例子 重点关注
经浏览器扩展连接 BrowserSkill 扩展所在 Profile、任务窗口、标签页借用与归还
经调试连接访问浏览器 web-access 的本地 CDP 代理；bb-browser 也可走 CDP 调试连接、目标标签页、DOM 与页面状态
经操作系统界面控制 本次 CUA 原生窗口路径 当前窗口、辅助功能控件、截图与输入操作

还有一个与三条路径都有关的选择：流程由模型边看边决定，还是把已确定的步骤固化成脚本。Playwright 可以承担浏览器流程的脚本化和测试，也能被 Agent 逐步调用。

第一关：接着用户已经登录的会话做事

登录态属于具体浏览器配置与会话。工具写着“支持登录态复用”，并不表示这一次已经连接正确。

9 月的出差申请中，本机 bb-browser 使用独立配置目录，缺少 OA 登录态。改用 CUA 原生窗口路径，才接上用户原来打开的页面。这是当次配置的实际情况，不能据此推断所有 bb-browser 都必须重新登录。

10 月 8 日的报销操作又出现了变化：bb-browser 当时连接的会话不合适，CUA 状态读取超时，最终由 web-access 的 CDP 路径完成报销草稿。中途 OA 会话过期，用户重新登录后才继续。

两次案例没有统一任务和起始条件，不能据此评出工具强弱。它们共同指向一个检查点：先核对浏览器实例、Profile、账号和目标页面，再开始填表。

独立自动化浏览器也能登录，Playwright 也支持复用认证状态。问题不在“有没有窗口”或“是不是无头”，而在当前接入方式是否满足任务需要。Playwright 认证说明

第二关：输入框有字，不等于页面接受了输入

连接正确之后，难点转到页面自身的交互。

报销页面使用受控输入。程序直接修改 DOM 值，界面可能显示了新金额，但框架内部状态并未同步。操作需要遵循页面控件的交互，再核对保存后的回显。

日期控件也类似：改了主表日期，行程是否联动？天数是否重新计算？项目选项是否精确匹配？这些都需要读取实际结果。

因此，一条可用路径要同时解决“看见控件”和“让应用接受动作”。DOM、辅助功能树、截图各有可观察的信息，遇到信息缺失时，可以换入口或结合使用。

第三关：点击保存，不等于业务完成

出差草稿至少要检查：项目、日期、天数、行程、预算，以及当前究竟是草稿还是已送审。报销草稿则要检查金额、分类和附件。

一次超时也不能简单理解为保存失败。请求可能已经被服务端处理，重试之前应先确认有没有生成单据，避免重复申请。

这两次 OA 操作最终都停在草稿，并回读了结果，没有提交审批。它们验证了各自案例的执行路径，并不证明所有复杂业务流程都能自动完成。

怎么选：按工作现场和重复频率判断

当前任务 先检查什么 可考虑的路径
继续处理已经打开的网页 目标 Profile 与标签页能否接入 扩展连接、CDP，或原生窗口路径
需要查页面结构、请求或控件状态 工具暴露了哪些网页信息 浏览器专用工具
流程跨越网页和原生弹窗、桌面应用 是否需要系统级界面操作 CUA 原生路径配合浏览器工具
每次发布都重复相同步骤 步骤与预期结果是否已稳定 固化为 Playwright 等框架的用例

没有必要在任务开始前就押定一个工具。已有接口或可靠脚本能完成的步骤可以直接使用；需要探索时再让 Agent 观察页面，遇到原生界面再接电脑操作能力。

至于哪个更省 Token，主要看返回的信息量、模型参与判断的轮次和重试次数。固定脚本不调用模型时，运行本身不产生模型 Token；AI 编写、启动、分析结果和修复脚本的外围用量另计。本系列没有同任务 Token 对照数据，不给工具排用量名次。

真正值得比较的是：在同样任务和验收标准下，哪条路径能完成工作，需要多少人工介入，以及后续维护是否方便。
