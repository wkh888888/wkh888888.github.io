CUA、Playwright/CDP、bb-browser、BrowserSkill，都能操作网页。真正影响体验的，是它们连到了哪里、看到了什么，以及每一步是否还需要模型判断。

日期：2026-09-30

“我明明已经登录了，为什么你还让我重新登录？”

一次看起来很简单的出差申请，卡在了这里。

需求只有一句话：参考旧单，把出差时间改成指定的一周，五天，其他信息保持一致。旧单已经开在 Chrome 里，项目、城市、交通方式和预算都能看见。

AI 用浏览器工具打开 OA，却返回了登录页。它据此判断需要用户登录，而原来的 Chrome 窗口明明已经登录。

后来才发现：工具连到了另一套浏览器配置。

换成 CUA 原生窗口操作后，AI 读到了原窗口里的参考单，完成新建、填表、日期与行程核对，最后保存了草稿。

这个小插曲，让几种浏览器自动化技术之间的差别变得具体起来。它们都能点击“保存”，但从接入现有工作，到重复执行测试，适合的任务并不相同。

浏览器连对了，自动化才真正开始

本机当时的 bb-browser 通过调试端口连接 Chrome，使用的是独立配置目录 ~/.bb-browser/browser/user-data。这个会话没有 OA 登录态。

日常使用的 Chrome 则是另一套会话，里面已经打开历史出差单。

后来调用 CUA 工具的 cua.getApp("Google Chrome")，接入原生窗口，才继续了用户已经开始的工作。这是本次实际观测，不代表所有 bb-browser 安装都会使用独立配置。

登录状态属于具体的浏览器配置和会话。一个工具“支持复用登录态”，意味着它具备这种能力；实际是否复用成功，还要看连接对象。

选工具时，这个问题值得先问：它能不能接着我正在使用的账号和页面继续做事？ 少一次错误连接，就少一轮登录排查、用户打断和无效模型调用。

四种名字，几种不同的控制入口

把 CUA、Playwright、CDP 和浏览器 CLI 放在同一张排行榜里，很容易比较错对象。

CDP 是 Chrome 的调试协议，提供检查和控制浏览器的通道。Playwright 是自动化框架，使用程序组织操作、断言和测试。bb-browser 与 BrowserSkill 则把浏览器能力包装成方便 Agent 调用的工具。CDP 官方文档

CUA 描述的是 AI 观察和操作电脑的能力，具体入口可以不同。本文比较的是这次使用的原生窗口路径，而不是假设所有 CUA 都采用同一种实现。

本次 CUA：    AI → 电脑操作工具 → macOS 窗口与控件 → Chrome 网页
本机 bb-browser：AI → CLI → daemon → CDP → Chrome 网页
BrowserSkill：AI → bsk CLI → daemon → 浏览器扩展 → CDP / 扩展 API → 网页
Playwright：  脚本或 AI → 浏览器自动化框架 → 网页

这些入口会影响能观察到的信息、操作范围，以及如何接入现有会话。

CUA：把当前窗口交给 AI 接着操作

这次原生窗口路径主要读取 macOS 的辅助功能信息。按钮、文本框、单选项和字段值，被工具整理成可供模型理解的控件树；模型再选择点击、设置文本或发送按键。Apple 的 AXUIElement 接口提供界面对象的辅助功能信息。Apple 文档

所以，这次填表并没有要求 AI 每一步都看截图猜坐标。它能读取“交付类是否选中”“日期是什么”“出差天数是多少”，再检查这些字段之间的关系。截图和坐标操作则可以补充结构化信息不足的地方。

它的优势在于接近用户的实际工作现场：已经登录的页面、打开的窗口，以及网页之外的原生弹窗，都可能进入同一条流程。

临时处理一次 OA 单据，或者探索陌生软件，CUA 很合适。 但控件语义缺失、窗口变化和模型误判都可能影响稳定性。每天反复执行同一组测试时，需要考虑如何把流程固化。

BrowserSkill：给 Agent 一个共享登录态的工作窗口

腾讯 BrowserSkill 使用浏览器扩展连接目标 Chrome 或 Edge 配置。Agent 的命令经过 CLI 和后台服务传到扩展，再通过 CDP 与扩展 API 操作网页。官方架构说明

它为任务提供独立、可见的代理窗口，并共享所选 Profile 的登录状态；需要操作原有标签页时，采用显式借用和归还机制。官方中文说明

这对经常处理内部业务网站的人很有吸引力：Agent 有自己的任务窗口，用户可以继续使用其他页面。它还提供请求、响应与控制台等网页调试信息，适合调查“为什么保存失败”。

不过，代理窗口共享账号权限，不能把窗口分开理解成权限隔离。是否选中了正确的浏览器配置，仍然需要核对。

对于长期操作已登录的网页系统，我会优先考虑这种接入方式。这是基于架构的选型倾向；本次还没有用 BrowserSkill 完成同一任务，因此不能把它写成实测胜出。

bb-browser：让 AI 用短命令操作网页

bb-browser 提供打开页面、读取快照、点击和填写等 CLI 操作，项目文档也描述了 CLI、daemon 与 CDP 的连接方式。项目仓库

它适合轻量网页查询、临时填表，以及已有网站适配器覆盖的任务。AI 不必为了一个小任务先搭建完整测试工程。

这次连接错会话暴露的是配置核对问题，不能直接推出“bb-browser 不支持登录态”。使用它时，应先确认连接的实例和配置，再判断页面状态。

Playwright：让已经跑通的流程能够反复验证

第一次探索业务流程，AI 可以边观察边决定下一步。到了每次发布都要跑的回归测试，流程与预期结果通常可以写成代码。

Playwright 提供浏览器控制、断言、隔离、并行执行和报告，并支持 Chromium、Firefox 与 WebKit。官方入门文档

例如，把出差申请流程写成一个用例：选择项目，填入起止日期，验证主表与行程联动，保存，再重新打开检查数据。这样的用例可以重复执行，也能明确指出哪一步没有达到预期。

Playwright 也可以通过 CDP 接入已有 Chromium。不过，官方提示这种连接的能力完整性低于 Playwright 自身协议连接，不能把两种方式完全等同。BrowserType 文档

它需要维护脚本、定位和测试数据，换来的是长期回归的可重复性。AI 仍然可以调用 Playwright，但如果每一步都让模型重新决策，就没有充分发挥固定用例的价值。

哪个更省 Token？先看模型参与了多少次

工具名称本身无法给出可信的 Token 排名。

让 AI 每次观察页面、判断按钮、选择动作，再检查结果，会持续调用模型。把一段已确定的流程写成脚本，独立运行并完成断言，则可以减少这些重复决策。

执行方式 影响模型用量的主要因素
CUA 主要依靠截图 图片处理方式、观察次数、动作重试
CUA 主要读取 AX 树 控件树大小、是否返回差异、上下文长度
bb-browser 逐步操作 快照范围、命令轮次、适配器是否减少步骤
BrowserSkill 逐步操作 观察结果、截图与调试证据的大小、模型轮次
AI 逐步调用 Playwright/CDP 返回的信息量，以及多少动作需要实时判断
固定 Playwright 脚本独立运行 没有模型调用时，执行本身的模型 Token 为零

最后一行有一个边界：让 Codex 启动脚本、分析报告或修复失败，外围对话仍会产生模型用量。脚本运行的机器成本和维护成本，也需要另算。

BrowserSkill 扩展本身不会自行调用 AI 提供商，模型用量产生在使用它的 Agent 一侧。官方说明

精简的 AX 或页面快照有机会减少输入；反复返回完整树、长正文、全量请求或截图，则可能增加消耗。图片与文本没有适用于所有模型的固定换算比例，Token 数也不能直接等同于费用或套餐百分比。

本次只实际完成了一条 CUA 保存路径，没有对各工具做同任务 Token 采样，因此没有实测排名，也没有节省百分比。

要比较，至少统一模型、任务、起始登录状态和通过标准，并重复运行。记录成功率、模型输入输出用量、决策轮次、重试和耗时，把失败尝试也计入成本。少核验几个字段得到的低用量，不能当成更高效率。

我的选择：按任务频率和操作范围来分工

你要完成的事 我会优先考虑
接着当前窗口处理一次临时业务 CUA 原生窗口路径
长期操作已登录的 Chrome/Edge 内部网站 BrowserSkill，先验证目标 Profile 与连接
轻量网页任务或已有适配器支持的操作 bb-browser
每次发布重复执行相同验收流程 Playwright 固定用例
涉及浏览器之外的桌面软件和原生界面 CUA 原生路径

这几种方式可以组合。先让 AI 探索流程，找出日期联动、金额合计、保存回显等关键检查点；再把稳定路径写成回归用例。流程变化或测试失败时，AI 回到界面帮助复现和分析。

出差申请里，“保存成功”只是一条提示。真正需要确认的，还包括日期与天数一致、项目编号正确、行程和预算回显无误，以及当前状态究竟是草稿还是已送审。

这次自动化最终完成的是保存草稿。工具换了，登录态问题解决了，业务核验仍然需要一步步做完。

如果你也准备让 AI 接管一个业务流程，可以先从一张可核验的草稿开始：连接正确的会话，完成一次操作，再重新打开检查结果。这个过程会比工具演示更直接地告诉你，哪条技术路径适合自己的系统。
