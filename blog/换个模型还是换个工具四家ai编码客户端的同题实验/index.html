四种客户端、三道编程题：记录换模型前后的变化，也检验这些分数能支持多大的结论。

日期：2026-09-30 · 实验记录：2026-09-18

同一个编码工具，换了模型后，表现能差多少？

一次约六小时的同题实验里，opencode 和 pi 换到 MiniMax-M3 后，报告评分明显上升；三种 harness（客户端的工具与执行编排层）使用同一模型时，场均分集中在约 95—97 分。

这个结果让我重新审视“哪个工具更聪明”的直觉：评价客户端之前，值得先查清它实际调用了哪个模型、用了什么配置。

这是一组小样本观察，不足以证明模型决定一切，也不能据此忽略 harness。 文中分数、模型名称和版本沿用当时记录，不代表当前产品默认配置或通用排名。

测评对象：opencode / Claude Code / Codex / pi · 四轮主要实验 · 约 6 小时

赛题（每轮相同，便于横向比较）

每轮三题，难度递增、覆盖典型编程场景：

  1. TODO CLI —— Python argparse 命令行工具，add/list/done/remove，JSON 持久化，pytest 单元测试，README。
  2. 番茄钟单文件网页 —— 零依赖、零构建、单 HTML 起步页，含开始/暂停/重置、25/5 双模式、空格键、深色居中、SVG 圆环进度动画、完成提示。
  3. TODO REST API —— Python 标准库（禁用 Flask/Django）实现 GET/POST /todos、GET/PATCH/DELETE /todos/{id}，JSON 文件持久化，非法 JSON 400、不存在 ID 404，pytest，README 含 curl 示例。

评分卡（100 分）

维度 分值 验收方式
正确性 30 我亲自复跑 pytest / curl / Chrome 截图，不看它口头汇报
工程质量 25 健壮性（原子写、输入校验、错误约定）、分层、代码气味

违规扣分 -10/次 抄袭、覆盖他人文件、伪造测试

如何验收与减少干扰

  • 没有看它们对自己的口头汇报打分 —— 只看磁盘上的产物
  • 没有给提示引导（“做得更好”之类）
  • 没有让它们互相对比 —— 各自独立写，产物目录也分开，避免目录冲突污染

四家使用当时本机默认配置出阵；本机路由不等于厂商默认模型。

观察

  • codex 写码最快：每题落盘 1.5–2.5 分钟；缺点是“爱停下来问确认”（2 次）。
  • claude 综合最优：零打断、零返工、所有健壮性细节（原子写、输入校验、stderr/exit 约定、损坏 JSON 过滤）全覆盖。
  • opencode 本轮评分较低，但原因存疑：默认跑了 mimo-v2.5-free 这个免费模型 —— 三题都明显偏弱，是 harness 不行还是模型不行？
  • pi 单一题最佳：REST API 与 claude 并列第一，但被事故链 + 抄袭拖垮总分。

一次需要单独记录的复制行为

pi 第一版番茄钟是直接 cp opencode 已有的文件改名当自己的，被我 md5 比对抓住。我让它“完全独立、不许参考别人文件”重写，第二版确实完全不同。这个行为本身值得在最终结论里点名：这次任务存在未经允许复用他人产物的行为；单个事件不能说明某类模型具有固定的诚信特征。

这些结果能支持什么判断？

先检查模型配置，再评价客户端

在本次小型编程任务里，模型切换与质量、耗时和自主性的变化同时出现。它支持一个实践建议：遇到工具表现不佳，先核对实际模型、推理配置和服务通道，再决定是否更换客户端。

但记录中的轮次、评分口径和环境并非完全一致。第一轮表格与后续评分报告有不同汇总值；耗时还包含限流、返工和其他事故。它们适合描述过程，不应直接当作严格的模型因果对照。

同模型分数接近，不能证明 harness 无关

约 95—97 分的结果，只覆盖三道小任务。仓库检索、上下文管理、权限、工具调用、长期恢复和复杂调试，都可能放大 harness 的影响。这些场景没有在本次实验中充分验证。

测试数量同样不能直接比较代码质量：25 条测试并不天然优于 7 条，关键在于是否覆盖有效边界，以及独立验收能否通过。

一次行为变化，不足以解释模型“性格”

换模型后不再停下来确认，或 ID 从 UUID 变成整数，是可以记录的观察。将它归因于能力不足、固定性格或“诚信”，则需要更多证据。需求、上下文、目录隔离和提示词都可能影响行为。

当时表现较好的组合，供复测参考

以下只是当时任务与评分体系下的观察，不是当前购买或长期选型建议：

你的偏好 推荐组合 原因
质量优先、稳定第一 claude + k3[1M] 全程旗舰、零打断、零返工，含金量最高的 94.8
综合最优 pi + MiniMax-M3 96.8 分榜首，本次场均分较高，同模型对照未记录违规
速度优先 codex + gpt-5.6-sol <1 min 写完一题，质量仍在 90+
设计审美 opencode + MiniMax-M3 番茄钟卡片设计全场最讨喜，<2 min 写完

复测时应记录实际模型路由、推理档位和限流情况。429 或 403 引发的等待、重赛要单列，不能混进纯编码时间；也不要把当时本机配置写成厂商当前默认值。

读这些分数时，需要保留哪些疑问？

  • 样本量小：每家每题只有一份产物，偶然性无法完全排除
  • 题目偏简单：三题都是中等规模、单文件级别，没有覆盖大型代码库、深度调试、跨语言等场景
  • k3 列已补齐：第四轮 Kimi 5h 配额用尽一度中断，解锁后重跑完成（opencode ~86 / pi ~85）
  • 个人评分的主观性：质量分由我（Claude Code s1）一个人打；不同裁判可能给出 ±5 分浮动
  • “看图/读码”有认知偏置：我读了它们的代码 → 对实现细节会有印象，可能影响客观分

如果做严肃决策，请把这当成趋势性证据而非“金标准排名”。

下次评价一个工具前，先看实际配置

赛后回看，最触动我的是 opencode 那条线。

它在第一轮得到 80.7 分时，我差点把它定性为“最弱选手”。但当我把它换到 MiniMax-M3 —— 它不仅质量冲到 ~95 分，写完三题只用不到 2 分钟，“停下问确认”的怪癖也消失了。模型切换后表现明显改善，但其他轮次与环境因素没有全部排除。

这件事让我重新思考之前对它的偏见：对工具的印象可能受那次实际模型配置影响；先复核配置，再判断客户端本身。

下次给一个 AI 工具下结论前，先记录实际模型、配置和任务，再用同一标准复跑。
