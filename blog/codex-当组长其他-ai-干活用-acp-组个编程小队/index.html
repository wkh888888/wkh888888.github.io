Codex 当组长，其他 AI 干活：用 ACP 组个编程小队

Agent 协作实战③：通过统一协议调度 CLI Agent

同时装了几个 AI 编程工具之后，我发现自己多了一份工作：给它们安排工作，再搬运结果。

Codex 想好了方案，切到另一个终端，让 Qoder 实现；Qoder 做完，再把说明复制给 Codex review。如果还要找 OpenCode 补充意见，又得开一个会话，把背景讲一遍。

工具多了，切换和交接也跟着多了。

上一篇，我们让 Codex 通过 CUA 操作 Qoder 桌面版，完成了两轮对话。这次换一条路径：用 ACP 把 CLI Agent 接起来，让 Codex 当组长，给其他 AI 派活、收结果、做 review。

这套接法的核心是 ACP，也就是 Agent Client Protocol。本次选择 acpx 作为客户端，负责启动目标 CLI、建立 ACP 会话并传递消息。

Qoder、OpenCode、CodeBuddy，已经分别跑通了真实回复和同会话追问。协调工作可以留在 Codex，具体任务交给其他 Agent，结果再带回来。

从“换个终端问一下”，到“让 Codex 帮我问”

先看一组实际结果。

我们通过 acpx 创建 Qoder CLI 会话，让它记住代号“松石482”，并回复一句连接成功的文字。随后再执行一条命令，继续同一个会话，询问刚才的代号。

Qoder 正确回复了“松石482”。

同样的两轮测试交给 OpenCode，也得到了正确答案。CodeBuddy 在测试会话指定 Hy3 模型后，则正确记住并返回了另一组代号“澄湖593”。

这里值得关注的，是第二条命令接上了第一条的上下文。Codex 可以先交代任务，再围绕回答补充要求，不必每次都把完整背景重新发一遍。

ACP 把小队接起来，acpx 负责本次接入

这里的 ACP 是 Agent Client Protocol，用于让客户端驱动 Agent，会话、提示和执行更新都可以通过协议交互。

acpx 则是本次使用的 ACP 命令行客户端。Codex 执行 acpx 命令，acpx 启动目标 Agent 的 ACP 入口，发送提示并接收结果。

ACP 定义双方怎样交互，acpx 把这套交互变成 Codex 可以调用的命令。 换用其他兼容的 ACP 客户端，也可以沿用这个接入思路；各 Agent 的启动、认证和能力差异仍需处理。

你把目标交给 Codex
        ↓
Codex 拆分任务、执行 acpx 命令
        ↓
acpx：创建会话、发送提示、接收更新
        ↓ ACP
Qoder CLI / OpenCode / CodeBuddy CLI
        ↓
结果回到 Codex，继续追问或验收

所以，这次接法并不要求 Codex 自身提供原生 ACP 启动参数。它作为协调者，调用一个 ACP 客户端，就能驱动目标 CLI。

也不需要先把这些 Agent 部署成 A2A 网络服务。本次验证的是本机客户端与 CLI Agent 之间的 ACP 通路。

跑通第一条链路：Codex → acpx → Qoder

本机安装的 acpx 版本是 0.19.6，安装记录中的命令为：

npm install -g acpx@latest

使用前，需要准备好目标 CLI，并完成它所需的登录和模型配置。安装 acpx，不会同时替你解决目标 Agent 的账号、额度和模型可用性问题。

下面是本次 Qoder 两轮验证的命令形式。将 <测试目录> 替换为自己的独立目录，在同一目录下使用同一个会话名：

# 创建命名会话
acpx --cwd '<测试目录>' --deny-all --no-fs --no-terminal qoder sessions new --name smoke

# 第一轮：放入测试代号
acpx --cwd '<测试目录>' --deny-all --no-fs --no-terminal qoder -s smoke '请记住代号松石482，只回复ACPX连接成功，19+23=42。不使用工具。'

# 第二轮：继续同一会话
acpx --cwd '<测试目录>' --deny-all --no-fs --no-terminal qoder -s smoke '上一条的测试代号是什么？仅回复代号，不使用工具。'

# 测试结束后关闭会话
acpx --cwd '<测试目录>' qoder sessions close smoke

第一轮取得了指定的连接成功文字，第二轮正确返回代号。测试结束后，会话关闭成功；关闭会话不等于删除历史。

这些命令使用了 --deny-all --no-fs --no-terminal：不批准权限请求，也不提供客户端文件系统与终端能力，并在提示里要求不使用工具，便于先确认对话链路。它们不是目标进程的完整操作系统沙箱；实际开发任务还需要根据工作范围配置工具能力和权限，不能把这组纯对话参数直接当成代码执行配置。

换成 OpenCode，复用同一套调度思路

OpenCode 本机已有原生入口 opencode acp。这次显式指定它，使用本机 CLI：

acpx --cwd '<测试目录>' --deny-all --no-fs --no-terminal --agent 'opencode acp' sessions new --name smoke

acpx --cwd '<测试目录>' --deny-all --no-fs --no-terminal --agent 'opencode acp' prompt -s smoke '请记住代号松石482，只回复ACPX连接成功，19+23=42。不使用工具。'

acpx --cwd '<测试目录>' --deny-all --no-fs --no-terminal --agent 'opencode acp' prompt -s smoke '上一条的测试代号是什么？仅回复代号，不使用工具。'

acpx --cwd '<测试目录>' --agent 'opencode acp' sessions close smoke

一个小坑是参数位置：本次使用原始 --agent 命令时，命名会话写成 prompt -s smoke。最初把 -s 直接放在根命令后，被 acpx 拒绝了；修正后，两轮测试通过。

这类错误很容易被误认为“Agent 不支持 ACP”。实际上，命令参数、协议连接、登录状态和模型执行，是不同的排查位置。

小队再加一员：MiniMax Code CLI

10 月 22 日，本机又加装了 mcode，也就是 MiniMax Code CLI。它提供原生的 mcode acp 入口，通过 stdio 与客户端通信。实际启动后，ACP 初始化成功，返回的 Agent 名称为 minimax-code，版本为 0.6.12。

因此，接入时可以使用同样的客户端思路，显式指定目标命令：

# 接入写法示例：使用本机 mcode 的原生 ACP 入口
acpx --cwd '<测试目录>' --deny-all --no-fs --no-terminal --agent 'mcode acp' exec '不要使用工具，只回复连接成功。'

这里直接指定 mcode acp，不依赖 acpx 是否内置了 mcode 别名。此命令是接入示例，本轮实际验证的是 ACP 初始化握手；前面 Qoder、OpenCode 和 CodeBuddy 的两轮回复记录保持独立。

有了统一协议，新增一个 CLI Agent 时，就可以围绕它的 ACP 入口接入现有调度流程。这里调用的是 mcode CLI，与 MiniMax Code 桌面版以及另一个 mmx 命令分别判断。

场景一：Qoder 实现，Codex review

对我来说，最有用的分工之一，是让一个 Agent 专心实现，另一个 Agent 检查结果。

Codex 先明确需求、修改范围和验收条件，再通过 acpx 把任务交给 Qoder。Qoder 交付后，Codex 读取完成说明，检查实际 diff，运行必要验证，再把具体问题反馈到同一会话。

Codex 明确任务
  → acpx 派发给 Qoder
  → Qoder 实现、验证、汇报
  → Codex 检查代码和结果
  → 同一会话反馈问题
  → Qoder 修正，Codex 复核

交给执行方的内容，可以这样组织：

目标：修复订单列表在切换筛选条件后仍使用旧页码的问题。
范围：只修改分页与筛选相关代码，保留已有无关改动。
验收：第三页切换筛选后请求第一页，翻页时保留筛选条件。
交付：说明修改文件、实现原因、实际验证结果与遗留问题。

共享工作区在这里负责提供实际产物，ACP 负责传递任务和结果。审查时要把对方的汇报与代码对应起来，不能只凭一句“已完成”就结束。

同一批文件可以由 Qoder 负责修改，Codex 先只读审查；需要切换执行方时，再明确交接，避免两个 Agent 同时覆盖彼此的改动。

场景二：额度快用完，提前把工作交出去

任务做到一半换工具，最烦的是重讲前情。

可以让 Codex 提前整理交接内容：目标、当前分支、已有修改、已执行检查、尚未解决的问题，以及下一步应该做什么。再通过 acpx 发给可用的 Agent，让它接着推进。

重点是提前。如果 Codex 当前会话已经无法执行，就不能指望它继续调用 acpx。 因此，阶段性保存交接材料比等到额度耗尽才想办法更实用。

换 Agent 时，已有文件能留下，任务进度和判断依据也要留下。把这些交代清楚，接手方才不用重新走一遍探索过程。

场景三：让另一个 Agent 挑方案里的毛病

也可以先不让对方改代码，只交一份方案，请它检查遗漏。

例如，Codex 写出数据库迁移方案，交给 OpenCode 检查回滚路径和边界条件；读回意见后，继续在同一会话追问某一项风险。或者让 CodeBuddy 审阅修改说明，再由 Codex 对照实际代码核实。

这类分工可以把审阅目标说得很窄：只找数据丢失风险，或者只检查兼容性。比起泛泛地“再看看”，范围明确的问题更容易产生可操作的反馈。

一个真坑：退出码是 0，不代表任务成功

CodeBuddy 的测试让这一点变得很具体。

默认模型 Step-5-Preview 当时遇到配额限制。acpx 的 quiet 输出没有正文，进程却退出 0。继续检查 ACP 事件，才看到 stopReason=refusal，以及错误元数据里的 429 quota 信息。

如果协调方只检查退出码，就可能把这次失败算成完成。

随后，我们在新的测试会话中指定 --model hy3，取得了两轮正确回复，没有修改全局默认模型。

这意味着，自动调度至少要核对三件事：有没有有效回复，协议是否报告拒绝或错误，以及任务要求的产物是否存在。进程成功退出只是其中一个信号。

Cursor 的情况则发生在另一层：握手与建会话都成功，但模型请求提示 Upgrade your plan to continue。客户端能连接，不代表账户具备执行条件。

有 CLI 用 ACP，要进桌面就用 CUA

这两篇文章解决的是同一个痛点：减少人在 Agent 之间传话。但操作对象不同。

需求 可采用的路径
调用支持 ACP 的本机 CLI Agent Codex → acpx → ACP → 目标 CLI
让任务与回复出现在目标桌面应用中 Codex → CUA → 桌面 Agent
查看或审查对方修改的文件 访问约定的工作区与 diff

ACP 接法可以直接围绕命名会话和返回结果组织调度。CUA 则适合需要进入桌面任务的情况，按钮、焦点和界面状态也成为流程的一部分。

选哪条路径，取决于任务应该在哪里执行、结果应该在哪里出现。

把“换个 AI 试试”，变成一次明确的交接

装更多 Agent，真正有用的地方，是能根据任务安排它们：一个实现，一个审查；一个额度不足，另一个接手；一份方案写完，再找另一个工具提出质疑。

acpx 和 ACP 为本机 CLI 提供了一条已跑通的对话路径。Codex 可以把工作交出去，取得回复，再继续追问。围绕它，把范围、权限和验收条件说明白，就能少做几次终端切换，少搬几遍上下文。

人负责目标与关键判断，工具之间的任务传递，则可以交给工具来做。
