别再给 AI 当传话筒了：让 Codex 和 Qoder 自己聊

Agent 协作实战①：用 CUA 打通桌面聊天框

一个 Agent，坐到了另一个 Agent 的聊天框前让它们接上话的，是 CUA为什么已经有 CLI，还要折腾桌面看起来只是发句话，实际卡在了“点了没反应”场景一：Codex 额度快用完，把工作交给 Qoder场景二：Qoder 干活，Codex 做 review场景三：让另一个 Agent 挑方案里的毛病换成 WorkBuddy，思路也一样把协作流程设计完整少做一次消息搬运工

平时同时用几个 AI 工具，最常做的一个动作，可能就是复制粘贴。

把这边写的方案交给那边审一下，再把意见复制回来，让第一个工具继续改。每个 Agent 都有自己的本事，人却成了它们之间的消息搬运工。

更麻烦的是，这种传递往往不止一次。审查意见要带回来，修改结果又要送过去；做到一半换工具，还得把前情再讲一遍。任务越长，人越像在给几个 AI 轮流接线。

能不能只交代一次目标，让它们自己把话接上？

这次，我让 Codex 操作 Qoder 桌面版：打开新任务，输入消息，读回回答，再接着追问。两轮对话跑通了，整个过程中，消息由 Codex 通过桌面界面提交给 Qoder。

最有意思的地方是：这条链路走的是鼠标、键盘和屏幕。

一个 Agent，坐到了另一个 Agent 的聊天框前

先看实际发生了什么。

Codex 在 Qoder 桌面版里新建任务，发出第一条消息：

这是 CUA 桌面对话连通性测试，请不要使用工具，也不要读取或修改任何文件。请记住测试代号“云杉825”。本轮只回复：Qoder桌面连接成功，18+24=42

Qoder 回复：

Qoder桌面连接成功，18+24=42

接着，Codex 在同一任务里追问：

上一轮让我记住的测试代号是什么？仅回复代号，不使用工具。

Qoder 回答：

云杉825

第二条问题没有重复代号。Qoder 正确接上了上一轮的上下文，Codex 也从桌面界面读到了这条回答。

这组测试很小，却把几个关键步骤串了起来：找到桌面应用、建立会话、提交问题、取得回答、继续追问。最终，Qoder 把这个任务自动命名为“连通性测试”。

检查项 实测结果
新建 Qoder 桌面任务 成功
第一轮消息与回复 正确显示在桌面会话中
第二轮上下文追问 正确返回“云杉825”
两轮执行状态 界面均显示成功、模型迭代 1 次
单轮执行耗时 界面各显示 4 秒，不含桌面操作和重试时间

这两轮问答把协作所需的基本动作串了起来：Codex 发出任务，Qoder 回应，Codex 根据结果继续沟通。接下来就可以围绕这条通路安排工作分工。

让它们接上话的，是 CUA

这次用到的 CUA，可以理解为让 Agent 使用电脑界面的能力。它能帮助 Codex 找控件、点击按钮、输入文字，再读取界面发生了什么。

整条路径是这样的：

Codex 想好要问什么
        ↓
CUA 操作 Qoder 桌面：点击、输入、发送
        ↓
Qoder Agent 在桌面任务里回答
        ↓
CUA 读取回复，交回 Codex
        ↓
Codex 根据回答继续追问

实际操作时，Codex 使用当前环境提供的 mcp__cua_repl 工具，绑定 Qoder 应用，结合可访问性树和截图判断下一步。

“可访问性树”听着有点技术味，作用很直观：它把屏幕上的控件变成可读取的信息，例如“新的任务”“发送消息”，以及回答里的“云杉825”。截图则用来核对画面，必要时辅助定位。

Codex 根据这些信息行动，再检查结果。你可以把它想成一个会看屏幕、会操作聊天框的协调者。

为什么已经有 CLI，还要折腾桌面

因为我想调用的，就是桌面里的那个 Agent。

在此前的测试里，我们已经通过 ACP 跑通了 Qoder CLI 的两轮对话。命令行有它的接入方式，但“调用 CLI”和“给桌面 Agent 发消息”解决的是不同需求。

即使 CLI 和桌面打开同一个项目目录，桌面能看到文件变化，也不能据此说桌面 Agent 参与了对话。

这次的要求很具体：让问题出现在 Qoder 的桌面任务里，让它在那里回复，再由 Codex 读回来。CUA 完成了这件事。

这也解释了它和 ACP、A2A 的关系：

路径 如何把任务交过去 本次情况
ACP 客户端通过协议驱动 Agent 会话 此前 Qoder CLI 已实测；本轮未用
A2A 通过 Agent 间协议交换任务与结果 本轮未用
CUA 直接操作应用界面，提交消息、读取回复 本轮两次问答通过

这里采用的是由 Codex 协调、Qoder 执行和回应的协作方式。任务和反馈通过桌面界面传递，不需要把 Qoder 桌面版当作原生 ACP 或 A2A 服务。

看起来只是发句话，实际卡在了“点了没反应”

真正耗时间的，并不是那道加法题。

操作过程中，有些点击发出去了，界面没有按预期变化。有时可访问性树已经显示新任务，截图却还停在此前的画面。还遇到过一次 noWindowsAvailable，需要重新绑定 Qoder 才恢复。

输入框也出过一个小插曲：文字已经写进去，可访问性树能读到，但发送按钮没有立即变成可用状态。补充实际键盘输入后，前端才更新了发送状态。

这类问题很像我们自己用电脑时碰到的情况：焦点没对、页面没刷新、按钮还没准备好。区别在于，人通常一眼就会调整，Agent 必须从返回的界面信息里判断。

所以，这次操作最重要的经验是：每一步都要看结果。

文字进入输入框
  → 发送按钮可用
  → 消息出现在会话列表
  → 回复出现
  → 执行状态结束

工具返回“点击完成”，只能说明动作执行过。消息有没有交出去，要看它是否进入会话；任务有没有完成，要看回复和最终状态。如果画面没变化，先检查再决定是否重试，否则可能把同一任务发两遍。

刷新状态、重新绑定应用、调整窗口触发重新绘制，帮助我们完成了这次测试。这些恢复动作也提醒我：把 CUA 用于长期自动协作，界面稳定性会是需要认真处理的一环。

场景一：Codex 额度快用完，把工作交给 Qoder

一个很实际的需求是：Codex 做到一半，额度快用完了，项目还得继续。

这时候，真正需要传过去的远不止一句“你接着做”。前一个 Agent 已经看过哪些文件、做过哪些修改、测试过什么、卡在哪里，都决定了下一个 Agent 能不能接住。

如果提前安排交接，可以让 Codex 把当前进度整理成一份交接单，再通过 CUA 发进 Qoder 的桌面任务：

请接手这个任务：修复订单列表的分页问题。

项目：<项目目录>
目标：切换筛选条件后回到第一页，翻页时保留筛选条件。
已完成：定位到分页状态与筛选状态更新顺序的问题，尚未修改代码。
重点文件：<文件路径>
待完成：修复、验证，并说明修改原因。
验收：筛选、翻页、清空筛选三条流程均正常。
注意：保留工作区已有改动，不覆盖无关文件。

这只是一个交接格式示例。实际使用时，还应该写明当前分支、已有改动、测试结果和未解决问题；如果工作区已有未提交修改，要让接手方知道哪些属于本次任务。

这里有一个时间点需要说清楚：交接最好发生在额度耗尽之前。 如果当前 Codex 会话已经无法继续执行，就不能指望它再自动操作 CUA 完成交接。此时需要用户把提前保存的交接单交给 Qoder，或者由一个仍可运行、已获授权的协调程序接手。

所以，更实用的做法是在任务阶段结束时保存进度，让接手材料随时可用。这样，即使换工具，也不用从头解释整个项目。

场景二：Qoder 干活，Codex 做 review

另一种分工是把实现和审查交给两个 Agent。

例如，由 Codex 整理需求与验收条件，通过 CUA 交给 Qoder。Qoder 完成修改后，Codex 读取它的完成说明，再检查实际代码和 diff。

Codex 明确需求、范围和验收条件
        ↓ CUA 派发
Qoder 实现修改、执行验证、汇报结果
        ↓ Codex 读取回复并检查实际产物
Codex review，提出具体问题
        ↓ CUA 反馈
Qoder 修复，Codex 复核

这时候，共享工作区就有了明确作用：CUA 负责传递任务和反馈，文件与 diff 则提供审查依据。Qoder 的“已经完成”是开始验收的信号，最终还要看代码是否符合需求、测试是否覆盖关键行为。

一次交付可以要求 Qoder 回报四件事：改了什么、为什么这样改、实际运行了哪些检查，以及还有什么没解决。Codex 再带着这些信息检查产物，重点看遗漏需求、行为变化和回归风险。

如果发现问题，反馈也要具体。例如：

筛选后虽然回到了第一页，但请求参数里的页码仍是旧值。请检查状态更新与请求触发的顺序，修复后验证“在第三页切换筛选条件”这一流程。

这比一句“再检查一下”更容易形成有效的修改与复核。

为了避免相互覆盖，同一批文件可以由 Qoder 负责修改，Codex 在 review 阶段先只读检查。需要 Codex 直接修改时，先完成工作交接，再切换执行方。

场景三：让另一个 Agent 挑方案里的毛病

有些任务还没到写代码这一步，就值得让另一个 Agent 参与。

Codex 先写出实现方案，交给 Qoder 检查边界条件、迁移成本和遗漏场景；读回意见后，继续追问某个具体取舍。文字审阅也类似：一个 Agent 起草，另一个 Agent 找逻辑漏洞，再把意见带回来修改。

这类任务可以沿用前面的问答方式，把方案、审阅意见和追问在同一会话里接起来。两个 Agent 给出相同意见时，仍要核对事实、需求与实际结果。

换成 WorkBuddy，思路也一样

文章里操作的是 Qoder，但这个思路也可以用在 Codex 和 WorkBuddy 之间。

例如，Codex 把任务目标、相关材料和完成标准整理好，通过 CUA 在 WorkBuddy 桌面版里新建任务、发送消息；WorkBuddy 执行后，Codex 读取回复，再继续补充要求或检查产物。

Codex → CUA → WorkBuddy 桌面 Agent
             ↓
      执行任务、返回结果
             ↓
Codex ← CUA 读取回复 → 继续反馈或验收

对于使用者，最直接的变化还是少一次复制粘贴：不必自己把 Codex 的要求搬到 WorkBuddy，再把 WorkBuddy 的回答搬回来。需要交接时传进度，需要审查时传意见，把人的注意力留给目标和结果。

进一步看，理论上，只要其他 Agent 桌面版的界面能被 CUA 识别和操作，能够提交任务、展示回复，就可以沿用这套方式。协调方决定要交什么工作，CUA 负责操作目标应用，再把结果带回来。

可以复用的是协作流程，具体操作需要适配各个应用。 WorkBuddy 和 Qoder 的按钮、输入框、任务状态与权限弹窗各不相同；有些内容能直接从可访问性树读取，有些需要结合截图定位。登录状态、额度和界面是否可操作，也会影响执行。

这让“接上另一个 Agent”有了一条基于桌面界面的路径。选好适合任务的工具后，可以围绕它安排派发、追问、交接与审查，而不用每一步都由人充当传话筒。

把协作流程设计完整

这些场景共用一条通路：Codex 通过 CUA 把任务交给 Qoder，读取回应，再决定继续追问、反馈修改意见，还是验收结果。业务目标可以变化，消息传递的方式可以复用。

要把它用好，任务描述里需要带上明确的工作范围和完成标准。涉及代码时，指定项目目录、允许修改的文件和验证方法；涉及审阅时，说明重点关注什么，以及希望怎样返回意见。

等待结果时，也要同时看消息与执行状态。遇到附件、权限确认或界面变化，就根据当前画面处理，再继续任务。执行结束后，把回复与实际产物对应起来，避免只凭一句“已完成”就结束。

例如，一个小型代码任务可以按这样的顺序推进：

  1. Codex 写清需求、修改范围和验收条件，交给 Qoder。
  2. Qoder 实现并说明改动、验证结果和遗留问题。
  3. Codex 检查 diff，运行必要验证，给出具体审查意见。
  4. Qoder 修改，Codex 复核，确认任务完成。

这也让共享工作区、CUA 和 Agent 分工各有作用：工作区保存产物，CUA 传递消息，Agent 根据各自职责执行与判断。

少做一次消息搬运工

这次实验的起点，是一个很日常的念头：既然我已经在两个 Agent 之间来回复制问题和答案，为什么不让它们自己完成这段传递？

现在，至少在这台 Mac 上，Codex 已经能操作 Qoder 桌面版，问它一个问题，读回回答，然后接着聊。

那个原本需要人切窗口、复制粘贴的环节，已经有了一个实际跑通的替代方案。从 Qoder 出发，同样的思路也可以延伸到 WorkBuddy 等桌面 Agent，围绕交接、实现、审查和返修安排分工。

让 Qoder 干活，Codex 来 review；需要换执行方时，再带着进度交接。把问答接起来之后，协作就有了可以落地的起点。

实测日期：2026 年 10 月 20 日。环境为 macOS、Codex 桌面应用、Qoder 桌面版 0.4.8；Qoder 界面所选模型为 Qwen3.8-Flash。本文依据此次本机测试记录整理，不代表其他版本和环境均可复现。
