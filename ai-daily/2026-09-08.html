Spotify 用 shunt 插件把 Claude Code 的 Token 消耗砍掉 90%：拦截读文件，交给便宜模型

AI Coding
来源：Spotify Engineering Blog / byteiota / Analytics India Magazine · 2026-09-06 前后 · HN 首页热帖

Spotify 工程师 Dimitri Mazmanov 在内部 Backstage 平台 Portal 上做了一个 Claude Code 插件 shunt，核心思路一句话：Claude 负责思考，便宜模型负责 I/O。

他的原话很扎心——"AI 编码助手替我做的大多数事不是思考，是 I/O：为了回答一个文件的问题去开五个文件，或者照抄旁边二十个测试的写法。"

  • 拦截层：用 PreToolUse 钩子拦 Read 调用，文件超过 350 行（可用 SHUNT_MIN_LINES 配置）就阻断，改走 /bulk-reader skill；check-bash-read 还会拦 cat/head/tail。
  • 执行层：Portal 的 "AiKA Modes"（声明式 agent，跑在临时运行时上，类似 agent 版 Lambda）用 Gemini 2.5 Flash、temperature 0.2 读完全文，只回结构化要点，不写散文。
  • code-writer 模式：生成的样板代码直接写盘，Claude 永远看不到内容——贵模型的上下文窗口里根本不加载它不需要的东西。这是和"把 subagent 路由到便宜模型"的本质区别。
场景结论
官方数据Java monorepo 四个场景测试，批量读取平均省约 90% token
HN 质疑Sonnet 5 输入 $2/M、输出 $10/M，差 5 倍。$100 输出 + $30 输入 → 省 $27，总额 $130→$103，实际只降 21%
边界Flash 漏掉过一个 Claude 一眼看出的线程安全 bug；摘要缺可靠行号，编辑类任务无法委派；单次委派 10–30 秒、Portal 上限 30 秒
代码已开源：spotify/portal-ai-plugins，bulk-reader / code-writer 两种 mode 可通过 AiKA 复用
为什么值得看：这是本周最实用的一篇工程实践，而且对你的场景直接对口——你手上就是 Java monorepo（ccdc），读大文件正是 token 黑洞。但要清醒：90% 是"输入 token 的 90%"，不是账单的 90%；只有读密集型（摸陌生仓库、梳理依赖、扫配置）才吃满收益，写/调试为主的会话会大幅缩水。另外别把它和 CLAUDE_CODE_SUBAGENT_MODEL=haiku 混为一谈——后者换的是"谁处理任务"，shunt 换的是"文件内容进不进上下文"。

Hugging Face 开源 Funes：给编码 agent 装一层"你自己拥有的记忆"，跨机器跨工具都能召回

AI Coding
来源：Hugging Face Blog（David Corvoysier）· 2026-09-03 发布 · 本周持续发酵

所有主流编码 agent 都有一个结构性缺陷：无状态。Claude Code、Codex、pi、Hermes 每次开会话都是陌生人——下午在 Claude Code 里理清的架构决策，第二天换 Codex 全忘了。

Funes 的做法是"记忆是数据集，不是服务"：把 agent 已经留在磁盘上的 session trace 解析成统一的 turn-and-block 结构 → 分块 → 用固定的本地模型做嵌入 → 写进本地 Lance 数据集。

  • 一条命令接入：funes add claude（或 codex / pi / hermes）建索引、注入 recall/get 工具、装好每轮自动增量索引的钩子。
  • 检索链路：向量 + BM25 混合 → RRF 融合 → cross-encoder 重排 → 按新近度加权 → 附带相邻块。全部本地跑，无 ML runtime 依赖、不需要账号。
  • 保留原文不蒸馏：写入时不压成"事实摘要"，返回的永远是原始 turn，并标明来自哪个 agent、什么时间、哪个 session、第几轮。官方理由很实在：压缩过的摘要会把关键细节抹掉。
  • 跨机器：可绑定到你自己的私有 HF dataset，换台机器 funes add codex acme/funes-memory 记忆就跟着走。发布前做凭证脱敏 + 二次扫描。

HF 的对比评测：两个需要前序会话推理的任务，上下文压缩只在其中一个成功（另一个因为摘要阶段丢了细节直接失败）；recall 的成本是手写交接文档的 1/4 到 1/8。

为什么值得看：切工具/换机器的切换成本，本质是厂商的护城河。Funes 把记忆层做成你自己拥有的数据集而不是订阅制 API，等于把这个护城河填了。另一个值得抄的思路是它和"用 Markdown 存记忆"（Cal Paterson 上周的提法）的取舍：Markdown 简单，但撑不起上万轮的排序召回——你的 MEMORY.md 体系正卡在这个量级拐点上，值得评估。

一周内 601 个 MCP 工具从"只读"悄悄变成"可写可删"，版本号还没变

AI Coding · 安全
来源：mcpindex 周度合约 diff（18,907 工具 / 2,887 servers）· AGI Hunt 2026-09-08

mcpindex 对公开 MCP server 的声明式合约做每日快照并对比，本周数字相当吓人：

指标数量说明
合约发生变更的工具18,907覆盖 2,887 个 server
其中安全相关变更12,257改变了工具能做什么
只读 → 破坏性翻转601分布在 129 个 server，单个最多占 11%
新增必填参数812（上周 405）其中 207 来自单一 server，179 个版本号字符串没变
被移除的参数1,146agent 可能还在发，直接失败或落到未预期的默认值

核心风险：周五接好的 server，周六 agent 还用周五的参数在调——失败或者拿到一个你没选过的默认值，而版本号一模一样。这就是"rug pull"的工程版本。

同一批报道还提到另一条：LLM 网关成了更大的爆炸半径。LiteLLM / Bifrost 这类代理把各家 provider 的 key 和 admin 面板、工具服务器放在同一个进程里——一旦被拿下，交出去的是钥匙 + 一个能写库、能开 YOLO 模式的 agent。今年已经有一个广泛使用的网关包在 PyPI 上被投毒并从 CI 里抽走 key。

为什么值得看：你这边正在用 agent-mail 等多个 MCP，这条是直接风险提示，不是行业花边。三个可落地的动作：① 按 digest 而不是名字 pin MCP server；② 标注是自报的、不可信，read-only 标注不等于没有写路径；③ 别把 provider key 和 agent 运行时放同一个进程。附一条自检标准（来自 cohorte 的清单）："我们review过这个 server"是感觉，"描述哈希变了就拒绝加载"才是能拿给审计看的事实。

宇树发布人形机器人全自主搏击视频：UnifoLM-X2-1.0 世界-动作大模型首次跑通动态对抗

具身智能
来源：宇树科技官方视频 / 新华网 · 2026-09-07

9 月 7 日宇树发布视频，展示人形机器人全自主搏击能力——注意是"全自主"，不是遥控、不是预设动作序列。

背后是 UnifoLM-X2-1.0 世界-动作大模型，官方称突破了瞬时规划、决策、动态交互执行三个瓶颈，验证了"世界模型驱动人形机器人大规模落地部署"的基础可行性。

搏击这个选题本身有讲究：它同时要求毫秒级的感知—预测—决策—执行闭环（对手会变招）、强对抗下的动态平衡、以及非结构化接触下的力控。相比跑步、跳远这类可预规划的动作，它更接近"真实物理交互"的下限要求。

为什么值得看：这是"世界模型"从仿真叙事走向真机验证的一个硬指标。此前行业痛点正如赵沁平院士所指：虚拟仿真难以复刻真实世界的物体形变、触觉反馈与环境扰动，必须打通"虚拟训练—真机部署—数据回传—迭代优化"闭环。搏击演示说明这条闭环至少在一个高动态场景里跑通了。当然，演示 ≠ 量产可靠性——99% 成功率意味着出门 100 次仍有 1 次掉链子，这仍是全行业没过的坎。

具身智能
