AWS 把自家云 API 做成一份能在笔记本上跑的副本：438 个接口模型、200 多项服务，全部代码由 agent 写、agent 审，人一行没写也没看 —— 而它自己公布的保真率是 56.5%

AI Coding · 无人审的代工厂
AWS 官方博客《All Things Distributed》客座文章（Swami Sivasubramanian，11 月 11 日）与 Matt Goldberg 的项目说明；GitHub aws/aws-emulator 的 README 与 v1.0.322 发布资产 scores.json.gz；i-Scoop、DevOps Daily、DEV Community 三家独立复核；腾讯新闻、网易科技的当日中文转述

11 月 11 日，AWS 发布 AWS Emulator：一个在本机跑起来、只认 AWS API 的模拟器。把 AWS CLI 或任意 SDK 指向 127.0.0.1:9297，你的代码就在内存里的假资源上跑，不要账号、不联网、不花钱。代码以 CC0 献入公有领域（只有 vendor/ 目录是 Apache 2.0），用 Rust 写，每个 AWS 服务一个 crate。

  • 它要解决的是 agent 自己制造的瓶颈。编程智能体写完代码要验证，而验证要真云：部署一套测试栈、验一个 SQS 可见性超时、跑一次 DynamoDB 条件写，每个循环要花 45 到 120 秒，agent 在轮询状态里烧掉上下文，账单一起涨。把这份副本放到本机，循环就从分钟级回到秒级。
  • 规格与参考，两样都有。高级首席工程师 Matt Goldberg 的原话是：模拟器完全由自主智能体编写，团队没有写、也没有审查过任何一行代码。他给 Kiro 的三步提示是：照 AWS CLI 写测试、跑到在真 AWS 上通过、再做一个能通过同一批测试的内存版。起步是周末实验，Amazon SQS 的初版 15 分钟就出来了；周一团队已经拿它测自家软件。
  • 三支队伍，各管一段。写测试的：把公开的 Smithy API 模型变成真实场景（建队列、发消息、收、删），每个场景先在真 AWS 上跑通才算数，验证完冻结成静态保真测试。找问题的：把保真测试回放到模拟器，失败就归组、开 issue。修问题的：一个 agent 认领一个 issue，改完走闸门。当前 6,544 个 issue 待修、12,708 个已修。
  • 四道闸门。补丁必须能编过、符合编码规范、过一轮由专门的安全 agent 做的对抗审、并且保真测试零回归，四项全过才进主线。Goldberg 的比喻是涂色本：小孩不是故意涂坏，是握不好笔，所以要给出清晰的填色边界。早期 agent 确实跑偏过 —— 它想从零写一个 Python 解释器来跑 Lambda，后来被引到现成库上。
  • 提交历史替官方做了背书，也留下了疑点。上线时主干 29,684 次提交，身份全是 agent：IssueFinderAgent 16,664、IssueFixerAgent 12,981、Scaffolder 29、TraceIdMigration 6、ReleaseManagerAgent 4，没有任何一条带人名。规模是 436 个服务 crate、437 个 Smithy 模型、40,130 个 operation 文件、14,099 个测试文件、vendor/ 之外 1,614 万行 Rust（EC2 一个 crate 就 70 万行）。但 .github/ 下没有 CI 工作流，提交也不带 review 标签 —— 那道安全对抗审「可能真的做了，但你在这里看不到」。
  • 成绩单是它自己发的。v1.0.322 的 scores.json.gz 里 42,937 个计分单元：24,243 过（56.5%）、18,614 不过、80 跳过；按步骤算 49,810 / 68,007（73.2%）；分服务看，KMS 93.9%、SQS 89.8%，CloudFormation 只有 15.8%（414 / 2,612）。这份文件覆盖 355 个服务，而官方口径是「200 多项」、InfoWorld 数出 426 项。
  • 有一个设计值得抄。没实现或没验证过的操作直接返回 HTTP 503，而不是假装成功。一个安静返回「看起来合理但错」的数据的模拟器，比没有模拟器更糟。

为什么值得关注：第一，agent 写代码早就不新鲜了，新鲜的是人退到了闸门这一侧：不写、不看，只负责定规格、建闸门、看保真率。这件事能成立的前提不是模型够强，而是这两样东西齐了 —— 可机读的规格（Smithy 模型）和可查询的参考实现（真云）。少一样，同样的 agent 就只能停在周末实验。

第二，56.5% 这个自曝的数字，比任何宣传口径都有用。步骤级 73.2% 说明多数场景是走到最后一步才断；KMS 的 93.9% 与 CloudFormation 的 15.8% 差着一个数量级，说明「保真」不是一个数，而是按服务分层的一张分布表。任何「本地 AWS 替身」的选型，第一步都该是去查自己要用到的那几个服务在这一列上是多少。

第三，对国内团队最实际的是它把「云依赖的测试」从付费项变成了本地项，断网、无账号、可进 CI；代价是它不收 PR，只有 issue 与保真报告两个通道 —— 你改不了它，只能等下一个 release。而 11 月 7 日到 11 日五天发了 12 个 release，不钉版本就是在赌。

口径提醒与边界：56.5% 是厂商自己发布的成绩单，不是第三方评测。DevOps Daily 另外用 40 个常规工作流自查，40 项全过。两件事不矛盾：那套自评是奔着找洞去的，找问题的 agent 还会不断往模型失败的地方加题；常规路径能跑，边角还在动。这两组数字回答的是两个不同的问题，不能拿来互相否定。

保真不等于安全。README 明写不要用它跑生产负载，也不要用它测安全；IAM 策略的校验方式与真 AWS 不一致。凡是涉及权限、审计、加密行为的验证，仍然要回真云。

默认开遥测（可用 --telemetry、EMULATOR_TELEMETRY=off 或 config.toml 关掉）。源码构建要至少 100 GB 空闲磁盘，一般团队应该用预编译包。另外它处于早期：12 个 release 五天一发，任何「我们测过了」的结论都要连版本号一起记。

与 11-05 ① 的分野：那期讲的是围住 agent 的那层自己破洞（Docker Sandboxes 逃逸、Pydantic AI 九条公告），讲的是围栏被绕过；这一期讲的是围栏存在但无法被审计。前者是安全问题，后者是证据问题。

如果手上有一套依赖 S3、SQS、DynamoDB 的测试：先拿这三个服务跑一遍现有端到端用例，再去发布页对一遍这三个服务的保真分，然后按结果分两堆 —— 能进 CI 的进 CI，涉及权限与配额语义的留真云。

上 CI 之前做三件事：锁死具体版本（别用 latest）、关掉遥测、给那条路径写一句断言「HTTP 503 表示未实现」。它返回 503 是设计，不是故障，别让重试逻辑把它拖成超时。

如果要把它当 agent 的自测台，注意 CI 里加个 aws-emulator skill 就够（需要 AWS CLI 2.35.0 以上），不必改业务代码。

404 名工程师、5 周：同一个人的 token 花费翻倍，提交量只多约 10%；提交数相当的周与周之间，第 90 百分位的花费是第 10 百分位的 39 到 240 倍

AI Coding · 度量失效
arXiv 2611.13396《AI 时代的代码行数？一项关于工程师 token 花费究竟衡量什么的案例研究》（11 月 10 日提交；卡内基梅隆 + JetBrains Research + 加州大学欧文分校，七位作者）；StackChief、Bad Influence 等独立要点整理

论文要回答的问题很直接：公司现在拿工程师的 token 花费来监控采纳率、定预算、衡量生产力，这个数和工程产出到底是什么关系？做法是把 JetBrains 内部网关记录的 coding agent 调用日志，与 404 名工程师在一个主力 IDE 产品上的提交对齐，窗口是 5 周（2026 年 6 月 29 日到 8 月 2 日），另外配一份 412 人的内部问卷。

  • 花费跟人走，不跟活走。五周里第 90 百分位的工程师，用了第 10 百分位的 71 倍 token。
  • 把产出按住，差距不收敛。在提交数相近的每一档里，花费的第 90 百分位是第 10 百分位的 39 到 240 倍。即便进一步控制提交数、改动行数、与 bug 关联的提交、提交天数之后，第 90 百分位的人周仍然是第 10 百分位的 58 倍。
  • 同一个人内部的边际收益率很低。花费翻倍，对应提交多约 10%；反过来，提交翻倍的周，token 只多约 20%。
  • 现有工作指标解释不了什么。提交、行数、bug 修复合起来，只能解释工程师之间花费差异的 38%、同一个人周与周之间差异的 13%。而「是谁」这一个因素，解释了 79% 的偏差。研究者还试了用角色、是否带团队、所属团队去预测没见过的工程师的花费，结果都不如直接用周均值。
  • 没有产出的那部分有多大。一个没有任何提交的周，仍然要花掉这个工程师平均周的 77%；作者估计 39% 到 42% 的 token 与产出无关（实习生 59%、QA 工程师 50%）。
  • 钱主要花在重发上下文。一次调用的中位数是发出约 400 倍于收到的 token；两个 agent 吃掉了 69% 与 31% 的用量。研究期内上线的一个新模型，两周内就拿走了 45% 的花费 —— 花费对「模型换代」极度敏感，对「干了多少活」不敏感。
  • 问卷解释了另一半。技术岗报告，在近九成的 agent 使用里，任务不止于写代码：数据分析 52%、头脑风暴 49%、调研与规划也都算在内。所以 token 花费量的是「这个人在多少种工作上用了 agent」，不是「他交付了什么」。

为什么值得关注：第一，这是 10 月 28 日那份 Amazon 内部备忘录的实证版。当时是一家公司说「token 数与代码行数是深度有缺陷的指标」，这期是把花费与产出按人和按周对齐之后的结果 —— 同一结论从判断升级成证据，还多给了一个更扎心的数：不提交的周也要花掉 77%。

第二，对团队最可用的结论是那条边际收益率。花费翻倍只换来 10% 的提交，意味着「给团队加预算」这件事的杠杆极低；而账单里最大的一块是重发上下文（发出是收到的 400 倍）。把预算投到减少无效上下文上，比投到提高额度上更可能见效 —— 这和 11-11 ② aiXcoder 把上下文压缩拆成专用小模型是同一件事的病因与药方。

第三，「是谁解释 79%」这句话的分量被低估了：它意味着花费是个人工作习惯的指纹，不是工作量的刻度。任何拿 token 排名、拿采纳率当 OKR 的做法，量到的其实是「这个人怎么用」，而不是「这个人做了多少」。而同一个指标一旦进入考核，最先变形的一定是使用方式。

口径提醒与边界：全部是关联，不是因果。作者自己写明「我们所有的估计都是关联」，因为用多少 agent 是工程师自己选的，不是随机分配的。

样本是一家公司（JetBrains，约 2,600 人）、一个主力产品、一个五周窗口。实习生与 QA 的「无关 token 占比」明显更高（59%、50%），说明岗位差异极大，不能外推成行业均值；也不必把「10%」当成所有团队都会有的数，它是这一家、这一段时间的斜率。

提交量本身也不是好指标，作者没有主张它是。所以「token 与提交的相关性弱」不能读成「token 没用」，只能读成「token 不是产出的代理」。这两句话对管理决策的影响完全不同。

同批检索里还会看到「多智能体架构多烧 1.4 到 4.7 倍 token」这类数字，那是另一篇多智能体架构对照论文的结论，不在本研究里，别混着引用。

如果团队已经在看 token 账单：把它留在成本科目，别升格成绩效科目。要看产出，落「任务 + 结果证据」，而不是花费排名。

做一次「无提交周」的账单占比自查。如果接近 77% 那个量级，说明大量花费在探索与试错上，先优化上下文复用与缓存，而不是先设额度上限 —— 限额只会把探索推到月底。

给 agent 会话加一句开场约束「这次要产出什么」，比事后看 token 曲线有用；这句约束同时也让「无提交周」变得可解释。

一天 42.7 万个 PR 由 coding agent 开出，占当天公开 PR 的 31.9% —— 而 30 天 91% 的合并率里，63% 是仓库主人在合自己的活

AI Coding · 计数与归属
MyClawn 的实时计数板与方法说明（DEV Community 原文，读数时间 11 月 12 日 14:00 CET）；ClawdBytes、Web Pulse 的独立转述；对应仓库 openclaw/openclaw 的 30 天数据来自同一份方法说明

有人不想再引用调查、也不想再引用厂商新闻稿，于是直接去问 GitHub 自己的搜索 API。做法是：四个主流 coding agent 默认会在 PR 上留标记（其中一个会在描述里自动附一行生成说明，四个都用固定前缀的分支名），对公开仓库打 is:pr is:public 加 24 小时窗口，取返回的 total_count，不抽样、不外推。

  • 24 小时口径。11 月 11 日到 12 日之间，公开仓库上由 agent 开出的 PR 共 427,042 个，同期全站 1,339,893 个，占 31.9%。
  • 30 天口径。累计 10,862,952 个，其中合并 9,887,585（91.0%）、未合并直接关闭 376,440（3.5%）、仍然开着 598,927（5.5%）。分 agent 的合并率从 68.5% 到 92.6%。
  • 最值钱的一段是自己拆自己的台。抽最新 115 个 agent PR 看归属：63% 由仓库主人自己开、13% 由成员或协作者开、只有 24% 来自团队之外。也就是说那个 91% 主要反映的是「人们在自己的仓库里用 agent 推自己的活，几分钟后自己合掉」。
  • 换到真正收外部 PR 的项目，画风就变了。openclaw/openclaw 30 天收到 806 个 agent PR，占该项目 22,310 个的 4%；其中 492 个合并、125 个未合并直接关闭；最近 30 个里有 29 个来自团队之外。
  • 它自己列了四条算不到的地方。私仓看不见；不带标记的 agent 工作看不见（编辑器里用的、或者把 footer 删掉的）；多标记的 PR 在 30 天口径会被计两次（24 小时口径已剔除重复）；人可以手工起一个同名前缀的分支来刷数。所以这是「公开 GitHub 上带标记的 agent 工作」的下限，不是 AI 写代码的普查。

为什么值得关注：第一，这是 10 月 29 日 GitHub 官方年报那个「超过 40%」的第一次外部对照。官方按「首个 draft 是否来自可检测到的 agent」算，第三方按四个 agent 的标记算，分母、识别方式、重复计数规则全不同 —— 两个数不必打架，但它们放在一起说明：「agent 参与了多少 PR」这个指标已经不可比，除非连算法一起引用。

第二，那条方法学结论比数字重要：合并率不是质量指标。在自己的仓库里，一次合并等于一次提交，不构成任何评审。把它当质量证据，和把代码行数当生产力，是同一类错误 —— 而这条正好接上本期 ② 的那句「token 是花的指纹，不是产出的刻度」。

第三，对开源维护者这一侧，结论其实偏正面：真正收外部 PR 的项目仍在行使判断（806 里 125 个被直接关掉）。11 月 12 日 ③ 讲「审核瓶颈被移到了无偿维护的开源社区」，这一期第一次给出了具体比例 —— 瓶颈是真的，但闸门也还在守。

口径提醒与边界：这块计数板是 MyClawn 自家产品，原文也把话写在明处：计数板是我们的，这篇稿子由我们的一名 AI agent 写成。它是一个有立场的测量者，但方法公开、代码以 MIT 开源、查询条件可复现 —— 这三点让它仍然可用，不等于中立。

91.0% 是四个 agent 30 天求和后的口径，带两个标记的 PR 会被算两次；31.9% 那个数是另一套剔除重复后的 24 小时口径。两个数不能互相除，也不能拼成「91% 的 31.9%」。

「63% 由仓库主人开出」来自最新 115 个 PR 的抽样，样本小、且取的是「最新」而不是随机，只能当信号，不能当全量分布。

与 10 月 29 日 ② 的 40% 不可直接比较：分母是否含私仓、如何识别 agent、按首个 draft 还是按最终标记、是否跨 agent 剔除重复，都不一致。凡是引用，必须把口径一起带上。

如果维护开源库：在 CI 里按「提交者是否有写权限」分两条路。自家人自合并走快车道；外部 agent PR 走完整评审。别用同一个合并率指标同时衡量这两件事，它会把快车道的好看数字摊到慢车道上。

如果看团队效率：把「agent 开出的 PR 数」从看板拿掉，换成「合并后 30 天内被回滚或被修复的比例」——后者才是 91% 想说明却说明不了的那件事。

想量自己：用 is:pr is:public author:你 加上 agent 标记跑一遍，先对自己的仓库有数，再决定信不信这个指标。

编码智能体进物理世界的第一考：1,156 个任务、35 个套件、47 种机器人，最强的一个在标准设置下只解决 34%，而给它完整仿真状态与无限重置能做到 77%

具身智能 · 评测框架
arXiv 2611.12177《Embodied First Exam》（11 月 9 日提交，预印本；30 位作者，含 Dawn Song、Pieter Abbeel、李飞飞、Jiajun Wu、Yuke Zhu、Manling Li）；CSDN DAMO 开发者矩阵的中文解读；Hugging Face 热榜与 Daily Papers 收录

前提是一个正在发生的转向：已经有人让 coding agent 去控制机器人，并且早期效果不错。但现有机器人基准都是围绕视觉运动策略学习建的，没法回答「编码智能体在物理约束下能不能可靠地开各种机器人」。EFE 就是为这个问题新建的考场。

  • 规模。1,156 个任务、35 个套件、47 种机器人。其中 9 个新套件超出了抓取放置：空间谜题、灵巧操作、多机器人交互、动态全身控制、sim-to-sim 工程。
  • 三种设置，差别只有一样东西：真实世界给不给你上帝视角。标准设置只给传感器观测、默认不允许重置环境；实时设置让环境在模型推理时继续跑；特权设置给完整仿真状态与无限重置，用来搜 oracle 解，作为成绩上界。
  • 方法也交给 agent 自己选。框架原生支持三种控制方式：直接控制、写代码去控制、或者训一个策略来控制。也就是说，它测的不是某个 VLA 的分，而是「一个编码智能体会自己选什么办法」。
  • 成绩。456 个核心任务（901 个用例）上，八个 agent 里最强的是 GPT-6 Astra in Codex：标准设置 34%（约 155 个任务），特权设置 77%。
  • 失败在哪。作者给每次失败的尝试都标了出错阶段，再跨 agent、跨设置、跨阶段比较。中文解读给出的两条是：失败集中在任务的第一阶段，或涉及材料变化与本体移动的环节；较弱的 agent 更容易在建立必要接触之前就失败。强 agent 在实时设置下更倾向直接控制，在特权设置下更常选择训策略 —— 换推理 harness 会显著改变成功率。
  • 一条反直觉的结论。「能重置」对成功率的提升，明显大于「给出精确的物体状态」；尤其是在需要高精度的阶段，重置能帮 agent 越过累积误差。

为什么值得关注：第一，这是第一次把「编码智能体能不能开机器人」当成独立命题来考，而不是沿用视觉运动策略的基准。它连「用什么方法」都交还给 agent，所以测出来的不是模型天花板，而是一个 agent 在物理世界里自己找办法的能力 —— 这比任何一个 VLA 的分数都更接近真实部署时要面对的问题。

第二，34% 与 77% 之间那 43 个百分点，就是「特权」的价钱。真实世界不给完整状态，也不给无限重来。任何在仿真里用特权设置训出来的成绩，都要先减掉这一块再看。这与 11 月 10 日 ⑤ TI-0.1 那次「仿真 84.5%、真机 2.6%」是同一类折价，区别是这次折价被可控地量出来了，而不是在真机上突然塌掉。

第三，「重置比状态更值钱」如果站得住，投资方向就要改：提升具身 agent 性价比的路径可能是把失败恢复做便宜（快速复位、允许重试、人工接管要快），而不是继续堆感知精度。对做产线与仓储的团队，这是个和直觉相反的投入建议 —— 但也正好解释了本期 ⑤ 那个仓库场景为什么能先跑通。

口径提醒与边界：全部在仿真里，没有真机成绩；「47 种机器人」是仿真本体。特权设置的数字是上界，作者自己也是这么定位的，不能当能力报。

34% 与 77% 出自论文正文与中文解读，第三方尚未复现。另有两点数字口径要注意：与核心任务相关的数在不同摘要里表述不一（套件总数 35、本体 47、任务总数 1,156，而核心任务是 456 个、用例 901 个），引用时要把「套件总数」与「核心任务数」分开写；「换推理 harness 会显著改变成功率」是定性结论，论文摘要未给具体幅度。

预印本，未见同行评审。30 位作者来自多机构，本轮未逐一核实评测代码与 harness 是否全部公开 —— 若要复现，先确认代码仓库与版本。

与 9 月 23 日 ④ 的 22.48% 不是同一张榜：那条是 RoboDojo / RoboProbe 口径、42 个任务跑 2,100 次；这里是 EFE 的 456 个核心任务。两个数不能相减，也不能说「涨了 11 个百分点」。

以后看到任何具身 agent 的成绩，先问三件事：用的哪种设置、能不能重置、harness 是什么。缺一项，分数就先打七折再读。

如果在做产线或仓储的具身方案：把「失败后多久能复位重试」列成一级指标去测。它可能比感知精度的边际收益更大，而且更容易被写进验收条款。

想自己跑：先取一个套件在标准设置下跑通，再切到实时设置 —— 从标准到实时那段掉幅，往往比绝对值更能说明工程成熟度。

具身智能 · 规模化交付
新浪财经 11 月 12 日报道、凤凰网转量子位、昆腾动力官方口径（创始人兼 CEO 李强）；同期星动纪元在邮政与顺丰的分拣数据来自网易智能 11 月 12 日报道，非昆腾数据

11 月 12 日，昆腾动力宣布：在称重量方、分拣供包、固定拣选三类场景完成产品与市场匹配（PMF）验证，已进入多家头部电商平台与物流企业的仓库，形成跨仓复制与客户复购，累计拿到近 5000 台机器人批量订单，开始进入规模化获客与交付阶段。它的具身机器人今年第一次进入菜鸟供应链的双十一真实作业现场。

  • 节奏给得很完整。今年 7 月与一家头部跨境电商平台开始前期沟通与现场考察 → 9 月机器人进仓 → 10 月开始签批量采购合同。三个月从考察走到批量合同，这个速度本身就说明仓方要的不是演示。
  • 指标。通用双臂机器人在称重与供包岗位完成部署验证，供包效率每小时 1200 件以上、成功率 99%。
  • 技术侧的两处细节值得记。一是视觉感知与动作策略联合学习，不新增件型就不必逐一编程调试；二是采用异步输入模型 —— 相机、触觉与本体状态按各自的时序与频率进模型，由模型自己学其中的关系，不强行对齐。现场的失败、人工介入与恢复过程全部进数据闭环，迭代以天计。
  • 为什么是物流仓（公司自己的解释，也是这条最值得读的部分）：这类环节单次动作失败不影响整条产线生产，还能快速拿到失败反馈，可以重试、核验或交人工接管；而仓方的验收是四项硬指标 —— 成功率、节拍、异常恢复、持续运营。有难度、有反馈、有标准，三个条件同时成立的场景极少。
  • 下一步。12 月底计划发布一款全新构型，把现场积累的工位约束带进设计，重点提适用性、连续作业能力与经济性。

为什么值得关注：第一，这是订单口径而不是交付口径，但在具身这条线上，近 5000 台的批量订单本身就是一次口径变化：这个行业过去最缺的不是好看的 demo，而是愿意签批量合同、并且会复购的客户。跨仓复制与复购这两个词，比 5000 这个数字更能说明问题。

第二，它把「什么样的场景先跑通」讲清楚了：允许失败、反馈密集、指标可验收。这解释了为什么人形还在跳舞而双臂已经在称重 —— 差距不在技术水平，在场景的可验收性。而本期 ④ 那条「重置比精确状态更值钱」，恰好是同一件事在评测侧的版本。

第三，把它和本周另外三条连起来看：思灵拿了 5 亿美元扩产、泰国批了五家中国零部件厂建基地、北京把 20 万台每年的整机产能写进 2028 目标。订单、产能、零部件三条线在同一天往前推，说明这一轮押的是 2027 年前后的放量，不是今年的业绩。

口径提醒与边界：近 5000 台是订单，不是交付，交付与验收节奏未披露。1200 件每小时与 99% 都是厂商自述，报道未说明件型分布、连续作业时长、以及 99% 到底是单次抓取成功率还是工位级任务完成率 —— 这两个口径差别很大，不能被同一个百分号盖住。

「首次进入菜鸟供应链双十一现场」的具体工位数、机器台数、值守时长均未给出，无法判断是规模部署还是试点。所有数字均未经第三方审计。

真实工况的节拍通常会先掉下来。同期另一家（星动纪元）披露其分拣机器人在真实混包工况下的节拍先回落、再爬升，昆腾是否经历同样的回落，报道里没有写。这是二手转述的另一家公司数据，不能当昆腾的成绩或短板。

与 9 月 14 日速览③ 那笔「特斯拉向 Optimus 供应链下约 5000 台订单」只是数字相同，两件事无关。

评估这类供应商，别问峰值节拍，问三件事：连续作业 8 小时的节拍衰减曲线、异常件的自动恢复率、卡住之后谁接手以及多久恢复。

把验收条款写成四项硬指标（成功率、节拍、异常恢复、持续运营），不要写一个总分 —— 这是本期最可以直接抄走的一条。

如果一个工位的单次失败会拖垮整线，先别上机器人。先把工位结构改成「允许失败、可快速复位」，再谈自动化；这条顺序反过来，项目大概率会拆设备。
