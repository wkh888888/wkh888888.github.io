微软用 Agent 把 Copilot 运行时从 TypeScript 重写成 Rust：43 万行、12 万美元、15.9 倍，以及几十个「编译通过但语义错了」

AI Coding · 自主重构
来源：微软杰出工程师 Stephen Toub 技术长文 · The Register（Joab Jackson，9/18）· Solidot · AI and Tech News · 搜狐 / 网易中文转述（9/19–21）

支撑 GitHub Copilot 以及一大票微软产品的软件运行时，现在整个是用 Rust 写的，而移植工作的大部分是 AI Agent 干的。微软杰出工程师 Stephen Toub 把全过程写了出来。

规模先摆在桌上：Agent 把 43 万行 TypeScript 转换成了 80 万行生产级 Rust。过程不是一次性重写，而是逐模块替换，跨越 14.5 周、135 次发布，平均每天开约 1.3 个移植 PR。成本是 约 12 万美元的 AI Token，外加一名开发者约三周的时间。Toub 的对照是：这件事如果人工做，要几年、要几百万美元。用到的模型点名了 GPT-5.6 Sol 与 Claude Opus 4.8，按各自擅长分配任务——也就是「用 Copilot 重写 Copilot」。

收益是真的。基准测的是「共享客户端 + 100 条并发管道下完成 1000 次单轮会话生命周期」：原 TypeScript 实现每秒完成 7.55 次，进程内运行的 Rust 每秒 120 次，15.9 倍。内存更夸张：10 个客户端的一批 Agent，TypeScript 吃掉 1383 MB，Rust 只吃 126 MB，而且任务保持在进程内完成，不用像 TypeScript 那样去拉起外部后台进程。

最有信息量的部分是两个反直觉观察。其一，Agent 花在「收集信息」上的时间远远多于写代码——Toub 说「AI 狂喷代码」的流行印象几乎正好是反的，实际工作模式更像迭代式调查：检查状态、形成假设、针对性修改、清洗、重试。他举的极端例子是 session.ts，一个三万多行的 TypeScript 文件：整场转换耗时 25 小时，开头 56 分钟只用来读文档、做了 122 次工具调用，然后派生出 15 个子会话，各自建 worktree 并互相通信。

其二，也是这条的题眼：几十个代码回归（regressions）。在 Rust 里，代码能编译，模型就当它是对的。Toub 原话——「if it compiles, it is correct 只适合当笑话讲」。他归因于四类：语义含混、分支漂移、功能缺失、行为不一致。RustConf 上顾问 Lisa Crossman 给了同样方向但更锋利的表述：Rust 能挡住内存不安全的代码，但挡不住 Agent 写出一个「语法正确、但根本不是你要的那个程序」。 Toub 也明确划了界：「这绝不是说每个大型 TypeScript 程序都该变成 Rust」，真正的动因是需求——通过 C ABI 嵌入、低启动与稳态开销、可预测的资源占用。另外要留意：这次只做了逐模块对等替换，没有优化运行时结构本身，那是下一步。

为什么值得关注：这是目前公开材料里规模最大、账目最完整的一次「Agent 重写生产系统」——不是 demo，是一个嵌在 VS Code、Visual Studio、Excel、Outlook、PowerPoint 和无数云服务里的真实运行时。它第一次把这类工作的成本结构摆到了台面上：43 万行、14.5 周、12 万美元 Token + 3 周人力，这个数字组合会直接改写「要不要做大规模重构」的决策（过去这类项目通常因为「算不过来账」被无限期推迟）。但真正值得记的是它的负结果：编译器不是验收方。几十个 regression 全部通过了编译，全部是语义层面的错。这把问题精确地推到了下一层——当产出的速度快到人类读不过来时，什么才算「验收」。微软的答案是「让它跑起来 + 人盯回归」，但 Toub 自己也承认 Agent 主要时间在读文档而不是写代码，说明这个流程里的人类注意力仍然是不可替换的瓶颈。还有一条容易被忽略：他们刻意没做结构优化。也就是说这 15.9 倍来自纯粹的语言与运行时特性，架构层面的收益还完全没吃到。

四条立刻可落地：① 用「编译通过 ≠ 正确」重排你的 Agent 代码评审：类型检查与构建只配当第一道筛子，必须叠加独立的语义验证（行为对比测试、属性测试、旧实现双跑）。② 别指望「不带凭据」的旁路能救你——这次是加载脚本那一瞬间凭证就出去了（与第 ③ 条同构）。③ 大规模迁移优先选「逐模块对等替换 + 后续优化」 的节奏，比一次性重写更容易验收，也更容易回滚。④ 重新算一遍你手上那些「算不过来账」的重构项目——12 万美元对 43 万行这个锚点会让很多结论翻转。

口径修正（重要）：① 15.9 倍与 1383→126 MB 都是单一基准下的数据（1000 次单轮会话生命周期 / 10 客户端批处理），不代表整体性能提升 16 倍。② $120,000 是 Token 成本，不是项目总成本——另需约三周开发者时间，且不含回归修复与后续优化。③ 80 万行 Rust ≠ 43 万行 TS 的等价物：Rust 语言本身更冗长，行数增长部分是语言特性，不能读成「Agent 把代码写膨胀了一倍」。④ 「几十个 regression」来自 Toub 自述，微软未公布完整清单与发现方式（人工审查 / 测试 / 线上）。⑤ 本条事件 The Register 于 9/18 首发，9/19–21 中文源集中转述，按本周披露处理，不是当日新发。⑥ Toub 明确反对推广：「绝不是每个大型 TypeScript 程序都该变成 Rust」。

GAVEL：一个权重都没动，靠外挂的图世界模型把 Qwen3-8B 从 41.2% 抬到 91.8%

Agent 架构 · 校验外包
来源：arXiv:2609.19315《GAVEL: Graph World Models for Verified and Efficient Long-Horizon LLM Task Planning》· dair-ai 推荐（9/19）· AGI Hunt · MarketBrief · Vuink

这篇论文的卖点可以压成一句话：模型一个权重都没改，成功率从 41.2% 涨到 91.8%。 涨的部分全部来自模型外面那层。

GAVEL 做的是长时程机器人任务规划。它维护一个显式的图世界模型，里面存三样东西：对象之间的关系、每个动作的前置条件与效果、以及对「没看见的物体在哪」的概率信念。LLM 每生成一个动作，这张图先在执行之前预测这个动作的后果；发现违规就拦下来；凡是能直接由世界模型推出的修正，就地改掉，不再回问 LLM；只有那些需要语义推理的错误，才交还给 LLM 重新规划。

数字（BEHAVIOR-1K）：100 个长时程单任务，成功率 41.2% → 91.8%；500 条多任务指令，19.9% → 92.6%。副产品是，按「物体可能在哪儿」的分布重排剩余子任务，行进距离比静态版本少约 5.4%。

注意模型是 Qwen3-8B——一个紧凑的开源小模型。作者的落点也正是这个：大部分提升来自 harness 的质量，而不是模型的能力。换言之，很多被归因为「模型不行」的失败，其实是「外面没有约束层」。

为什么值得关注：这条和昨天那条微软重写是同一个问题的两种解法，方向正好相反。微软的做法是让 Agent 产出更多代码，然后用编译器当校验器——结果证明编译器只能验类型，验不了语义，几十个 regression 就这么漏过去的。GAVEL 的做法是干脆把校验器放到模型外面，做成一个可以被单独检查、单独修改、单独替换的显式结构：图里写着前置条件和效果，动作对不对是查得出来的，不需要问模型。这直接回答了当前 Agent 工程最贵的一个问题——涨点到底该买更大的模型，还是该补外面的约束层。在 8B 这个体量上，答案是后者，且幅度大到不像调参（41%→92%）。另一个值得抄的设计是它的分流：能从世界模型推出来的修正不回问模型，只有需要语义判断的才回去。这给「校验成本」设了上限，否则每次动作都回问 LLM，等于把省下来的钱又花掉。还有一层更长远的意思：显式世界模型是「可审计」的——它写下来了机器人以为世界是什么样，出错时能回放；而 LLM 权重里的「世界知识」没法拿来当证据。

四条立刻可落地：① 遇到 Agent 长任务掉链子，先别换模型——先问「有没有一个显式的状态图 / 前置条件表可以让它自查」。② 把校验做成分层：能用规则推出的就地修，只有语义层才回模型，控制住回问次数。③ 需要证明「为什么这么做」的场景（合规、安全、审计），优先选显式结构，因为权重无法作为证据出示。④ 关注点从「单次成功率」移到「失败能否在执行前被拦下」——这才是部署场景真正要的指标。

口径修正（重要）：① 全部结果来自 BEHAVIOR-1K 仿真环境，不是真实家庭机器人。评论者 @jinnibot 明确提示「把它当成仿真 harness 的结果，不是已部署的家务机器人」。② 论文的图世界模型需要人工提供对象关系、前置条件与效果——这是本体与场景相关的工程投入，不是零成本插件，跨场景迁移的代价未被计入那些百分比。③ 「模型权重未改动」指底座 LLM 未微调；GAVEL 本身是一个新增的外部框架，整体系统的复杂度是上升的。④ 论文 9/19 前后进入传播，arXiv 编号 2609.19315，未见第三方复现。

一枚只活 60 秒的令牌，换回一枚活一年的跨站标识：ChatGPT 的 __obi cookie 与「拒绝营销也没用」

Agent 安全 · 隐私边界
来源：独立安全研究者 buchodi（Buchodi's Threat Intel）9/20 抓包报告《ChatGPT 现在知道你在别的网站做了什么》· Hacker News 当日榜首 · explainx.ai / genztech / prismix 技术拆解 · 码农早餐（9/21）

9 月 20 日，独立安全研究者 buchodi 发布了一份抓包报告，当天冲上 Hacker News 榜首。结论一句话：OpenAI 能把你在别的网站上的行为，对应回你的 ChatGPT 账号。 他把整条链路在自己的安卓手机上完整复现，用两种独立抓包方法互验，再对上几个月的观测流量——覆盖 936 个广告像素、1,029 个主机名、23,929 条请求。

机制分三步，没有一步需要用户参与。第一步，你在 chatgpt.com 上时，客户端生成 16 字节随机数，请求后端签发一个 RS256 JWT：签发方 chatgpt-wadi，受众 bzr.openai.com，用途 obi_sync，里面同时装着 你的账号标识 sub 和标识符 obi，60 秒过期。（bzr 是 OpenAI 内部对广告平台「bazaar」的简称，wadi 是签发服务名——这套系统在内部是有正式命名的。）第二步，客户端把这个令牌跨站提交给 bzr.openai.com/v1/obi/sync，响应回写：Set-Cookie: __obi=…; Domain=.openai.com; HttpOnly; Max-Age=31536000; Path=/; SameSite=none; Secure。SameSite=none 加 Secure 正是 cookie 能跟着跨站请求一起发出去的必要配置，Max-Age 是一年。第三步，任何在 ChatGPT 投过广告的公司都会在自己站点装 oaiq.min.js（和 Meta Pixel 一个路数），浏览器去加载这段脚本的那一刻就自动带上 __obi。

这里有个技术细节值得单独记：SDK 里其实有一条「不带凭据」的代码路径，但它救不了你——因为浏览器是在加载脚本那一瞬间就把 cookie 附上去的，那时 OpenAI 的代码一行都还没执行。作者原话是「光是加载这个标签，身份就已经泄露了」。同一批请求里，OpenAI 其余标识 cookie 全被浏览器拦下了（oai-did、oaicom-stable-id 是 SameSite=Lax，会话类域名不匹配），__obi 是唯一一枚被配成跨站共享的 OpenAI 标识 cookie。

顺手带走的东西比想象中多。SDK 还会从广告主页面刮身份信息，按 OpenAI 自己的标签分四类：in 是广告主主动传的，fm / ht / js 分别是从表单字段、渲染后的页面文本、tag manager 数据总线里刮的。实测流量里刮来的比主动给的多：685 起对 255 起；最大的邮箱来源是 tag manager 数据总线——SDK 直接替换了 window.dataLayer.push，还读 adobeDataLayer，并解析 gtm.js 的 l= 参数专门找改过名的 GTM 层。邮箱、电话、姓名发出前做 SHA-256；国家、地区、城市、邮编是明文，邮编最常被刮（28 个站点、100 次）。URL 被裁到「域名 + 路径」，23,929 条里没有一条带查询串——但路径活了下来，而采集端收到的路径里出现过一种疾病、一个债务处理漏斗页、一份诉讼咨询表单。881 个能看到配置的像素里 638 个开了自动匹配，观测到的信贷与借贷广告主无一例外。

最刺眼的是同意开关的设计。OpenAI 的 cookie 政策把 __obi 归在「分析类（Analytics）」下——它是这一栏里唯一的一条；而分析和营销是两个独立的同意开关。作者解码的每一个同步令牌都带着 consent_decision: analytics_allowed，也就是说：同意分析、拒绝营销的用户，照样会拿到这枚跨站标识。 面向广告主的开发者文档里，只列了第一方 cookie __obref（最长 365 天）和广告点击参数 oppref（30 天），对负责跨域穿透的 __obi 只字未提。9 月 14 日作者把机制和两个问题发给了 OpenAI 的 press 与 privacy 邮箱，回复来自客服：确认收到、会转内部复核，两个问题都没有回答。

为什么值得关注：先说清楚——这套机制本身是标准广告技术，作者自己也这么定性：登录账号 + 像素触发时的第三方 cookie + 站外转化归因，Meta 多年前就做过结构等价的东西。没有先例的不是这套机制，而是把它跑在一个 AI 聊天产品上。 差别在于输入的内容：人在搜索引擎里输入关键词时知道自己站在公共网络上，在社交平台点赞时知道那是广场；但对着一个对话窗口，人们说出来的是家庭变故、心理焦虑、职业危机，是还没整理过的话。而 AI 聊天产品正从「回答你」走向「替你做事」，需要给的上下文只会越来越多，这个池子是活的。同一周还有一条反向新闻可作坐标：9 月 20 日晚智谱宣布 MaaS 平台上线「数据内容不留存」——开通后输入输出不做静态存储，只在当次推理内存里用一次，也不用于模型迭代（例外：Batch API / File API 这类本身要求持久化的形态不覆盖，法律要求或核查违规时可留存 30 天以上）。同一周里，一边是消费端一枚有效期一年的跨站标识在安静工作，一边是国内厂商把「不留存」做成卖点，而零留存本身也不是新概念（OpenAI 与 Anthropic 早就为企业客户提供过同类选项，同样申请制、同样保留合规例外）。差别只在于：付费企业客户可以要求「用完即焚」，普通用户手里握着的是一个「同意分析、拒绝营销」的开关，而那个开关管不住这枚 cookie。

四条立刻可落地：① 用 ChatGPT 处理敏感内容的人，考虑拦截 bzrcdn.openai.com（会牺牲部分站点功能，自行权衡）。② 浏览器侧：Safari ITP、Firefox Total Cookie Protection、Brave 默认已拦；Chrome 用户需自行配置第三方 cookie 阻断。③ 做广告归因的团队核对自己的 pixel 配置——「自动匹配」在 638/881 个像素上是开着的，你可能并不知道自己在传什么。④ 记住这个工程教训：「不带凭据」的代码路径救不了你，标签加载那一刻凭证就已经出去了；同理适用于任何第三方脚本。

口径修正（重要，本条尤其需要）：① 全部观测出自单一研究者、单一设备（Android 版 Chrome），桌面版 Chrome 未测。② Safari 的 ITP 会拦掉所有第三方 cookie，iOS 上任何浏览器都跑在 WebKit，因此该机制在任何 iOS 浏览器上都不成立；Firefox 与 Brave 默认拦截。③ 命中率有限：约每五个 ChatGPT 会话才产生一个同步令牌，ChatGPT 移动网页版会投广告但根本不做同步；「加载脚本即泄露」这条观测需要浏览器里已经存有 __obi。④ 最关键的一条：归并这一步没有被观测到。 202 只说明采集端收下了一个带着 cookie 的事件，OpenAI 服务端有没有真把它算到账号头上，是从设计推出来的，作者明确写了自己没有看着这件事发生。 ⑤ 932 个解码令牌中 736 个标 account_user、196 个标 anonymous，匿名标识同样稳定（一台设备一个，至少留存 27 天）。⑥ 0.1.31 版本曾连姓名与地理位置一并采集，范围在 8 月 27 日收窄——描述的是历史版本行为，不是当前版本。⑦ 各源对 HN 热度口径不一（592 分 / 315 评论 与 424 分 / 224 评论 并存），不影响结论。⑧ 本条转述自独立研究者的公开报告，OpenAI 未公开回应。

OpenAI 的 Astra 真把机械臂开动起来了：一次成功很惊艳，但演示和产线之间隔着几个数量级

具身智能 · 大脑接管身体
来源：AGI Hunt 9/21 日报 · FutureX Physical AI Daily Issue 126（09/21）· 机器之心 · CMU 机器人研究者 Wenli Xiao 公开实验 · Retrocausal 联创 Zeeshan Zia 评论

OpenAI 把 Astra 定位成「能在电脑上做你能做的任何事」，而这周它开动了一条真实的机械臂。目前社区里主要有两种用法：把 Astra 当 policy（从相机观测直接输出动作），或者当 agent（先规划、写代码，再调用下层 policy）。

最引人注目的一个实验来自 CMU 机器人研究者 Wenli Xiao：他录一段人做某个新任务的视频，喂给 Codex，再让 Astra 控制机械臂复现，一次就成功了——他管这叫「物理 ICL（physical in-context learning）」。如果这个结果站得住，含义相当直接：教机器人做新动作的那套「数据采集—遥操作—训练」流程，可能第一次出现了一条绕过去的捷径。

速度上另有对照。在一条 AgileX 机械臂上做「把红方块放进盒子」：Jev 用了 27 秒，GPT-6 Astra 用了 1 分 11 秒（出于安全，臂速被限制在 10%）。

robotics 研究圈现在最关心的问题变成了数据来源：Astra 的训练数据里到底有没有机器人数据？ 一份 786 人的投票里，84% 认为「肯定有」。Amazon Alexa 首席科学家、Retrocausal 联创 Zeeshan Zia 的评价更直白：「看起来机器人领域的 OpenAI 可能就是 OpenAI，而不是 Physical Intelligence 或 Skild。」

为什么值得关注：这条的价值不在「Astra 会开机械臂了」，而在它把「通用模型能不能直接当机器人大脑」从立场之争变成了可复现的实验——录段视频、喂进去、一次成功，任何人都能照着做一遍。真正需要冷静的是验收尺度：FutureX 的定性很准，「20 次单任务的演示」和产线上用的「上万次试验的成功率统计」，中间差着好几个数量级。一次成功能证明「存在这条路」，证明不了「这条路能承载生产」。这也正好把今天的主线拉出来了：演示不需要校验器，部署需要。目前这条链路上没有一层是负责校验的——视频到动作的映射没有置信度，模型不会告诉你它不确定，机械臂也不管自己是不是在安全边界内（这次还得靠把臂速压到 10% 来保证安全）。换句话说，能力已经跨过来了，校验还留在对岸。 对国内做具身的团队，这条还有一层压力测试的含义：如果通用大模型确实开始吃机器人能力，那「我们有多少小时真机数据」这个护城河的估值需要重算。

四条立刻可落地：① 先按「能力演示」而非「可用方案」读这类结果——要求发布方给出多次试验的成功率分布，而不是单次成功视频。② 想复现的话，从短时程、物体少、失败代价低的任务开始，别一上来挑产线动作。③ 任何让通用模型直控本体的实验，先做物理限速与急停（本例把臂速限制在 10% 就是这个作用）。④ 关注后续：训练数据里是否含机器人数据目前仍是圈内推测（84% 投票），等 OpenAI 明确披露再据此做选型判断。

口径修正（重要）：① 「一次成功」是单次实验结果，非统计意义上的成功率——与产线口径不可比，请勿换算。② Jev 与 Astra 的 27 秒 vs 1 分 11 秒为单次对照，且机械臂被限速至 10%，绝对时间不反映实际节拍。③ 「84% 认为 Astra 训练含机器人数据」是一份 786 人的社区投票，是猜测不是证据，OpenAI 未披露训练数据构成。④ Zeeshan Zia 的评价是个人观点。⑤ 本条经由 AGI Hunt / FutureX 的当日汇总传播，原始实验细节以研究者公开材料为准，未见同行评议。

300 台机器人进主题乐园：具身智能第一次被放进一个年客流千万、天天开门的考场

具身智能 · 规模化运营
来源：上证报中国证券网（9/20，记者宋薇萍）· 广州日报 / 大洋网 · 重庆日报转文汇报 · 深圳商报·读创 · 大河财立方（9/20）· Counterpoint Research 出货统计

9 月 24 日，由智元（AGIBOT）与长隆集团联手打造的全球首个大型具身智能主题乐园将在珠海横琴长隆飞船乐园启幕。开园当日，超 300 台智元全系机器人集体「上岗」，超 100 个机器人交互体验点同步开放，覆盖七个核心场景：机器人文娱商演、科普研学、导览导购导引、服务零售站、智能伴游、酒店场景、体育竞技。园方设计了数百个有独立姓名、不同性格的机器人角色，做全域沉浸式体验。开园当天，智元与长隆共建的具身智能文旅联合研究院揭牌，全球首个文旅场景大规模 5G-A 具身智能创新应用等多个「行业首创」成果集中亮相。刚刚在世界人形机器人运动会拿下金牌榜、奖牌榜双第一的智元「冠军同款」机器人也会在园内常态化展示。

落地场景本身的量级值得注意：横琴长隆飞船乐园是全球最大的室内主题乐园，以沉浸式宇宙探索和海洋生态科普为核心，开园以来累计接待游客超 1000 万人次。

把机器人放进乐园并不新鲜——迪士尼 1963 年就在加州乐园的「魔法提基屋」用了 Audio-Animatronics，近两年其 BDX 机器人已能与游客互动；日本长崎豪斯登堡的「海茵娜酒店」2015 年开业、2017 年推出无人酒吧；国内黄鹤楼的「李白机器人」、秦始皇帝陵的「机器人 + AR」导览、恩施大峡谷的「小青」、上海迪士尼的保洁机器人也都是先例。但这些案例的规模普遍在数台到数十台，功能多集中在讲解、表演、巡逻或保洁中的一项。 横琴项目的差别在两点：规模（300 余台 + 100 余个交互点被纳入同一套园区运营体系）与性质（强调「常态化」运营，而非单次展演）。

为什么值得关注：这条最值得看的不是「机器人会跳舞」，而是验收尺度变了。过去一年具身智能的自证方式是发一段视频、跑一个基准、办一场演示——这些都可以被挑选、可以重来、可以在最理想条件下拍。主题乐园不接受这套：它天天开门、客流密集、游客年龄与需求极其分散、机器人要连续运行数月。对智元而言这是一个年客流千万级的真实数据场；对整个行业而言，这是第一次把数百台机器人放进同一个不可控、不可暂停、且失败会被游客当场看见的环境里。还有一层是组织难度：从单台设备执行固定任务，到数百台同时进园，中间隔着设备调度、内容更新、现场安全、运维响应这一整套运营体系——这些在实验室和工厂里都不算主要矛盾。所以这条真正的观察指标不是开园那天的表演，而是三个月后的可用率、故障响应时间和每台机器人的日均人工干预次数。如果这几个数字能公布，它会成为这个行业第一个真正有分量的规模化落地口径；如果公布不出来，那开园本身也只是又一场大号演示。

四条立刻可落地：① 观察指标换成运营口径：可用率、MTBF、日均人工干预次数、单机日均服务人次——比任何演示视频都有信息量。② 做文旅 / 零售场景方案的团队，重点看「多机调度 + 内容更新 + 现场安全」这套运营体系怎么搭，而不是单台能力。③ 注意 5G-A 在文旅场景的规模化应用是本次的隐藏看点（与 09-15 的机器人专用 SIM 卡是同一条线的不同落点）。④ 对照历史先例（迪士尼 1963、海茵娜 2015）判断「常态化运营」的成色——机器人酒店最终大量撤下机器人的教训不要忘。

口径修正（重要）：① 9 月 24 日启幕是未来事件（本日报发布于 9/21），本条按官方预告收录，现场实际投入数量、运行状态与体验效果需以开园后实际为准。② 出货数据两源冲突：深圳商报引智元口径为「2026 上半年人形机器人出货 8400 台、全球份额 44%」；大河财立方引 Counterpoint Research 为「约 9700 台、全球份额超 43%」——两套口径分属不同统计机构与统计方式，不要混用。③「全球首个 / 规模最大 / 场景最丰富 / 技术最先进」「全球最大规模人机共演」「全球首次机器人空中飞人」「全球首个文旅场景大规模 5G-A 应用」均为公司 / 媒体口径，无第三方认证。④ 智元此前主要布局工业制造、商业服务、科研教育，文旅消费场景为首次较大规模进入，运行效率、维护成本与游客接受度仍待检验。

五条读成一条链：今天的主线可以压成一句话——「能跑通」已经不值钱了，值钱的是谁来校验它真的跑通了。 ① 43 万行被 Agent 重写完毕、性能涨了 15.9 倍，而校验器是编译器——它只能证明类型与内存是对的，于是留下了几十个语义回归，Toub 自己把「能编译就对了」定性为笑话；② 给出的是正解：把校验器从模型里拿出来，做成一个显式、可检查、可单独修改的图世界模型，一个权重没动，41.2% 变 91.8%，而且只有需要语义判断的错误才回问模型（给校验成本设了上限）；③ 是反例：用户侧根本没有人校验——你以为关掉了营销 cookie，其实一枚归类为「分析」、有效期一年的跨站标识在干活，SDK 里那条「不带凭据」的分支形同虚设（和第 ① 条「加载脚本那一刻凭证就出去了」是同一个病灶），而且连「有没有真归并到账号」这一步都没人观测到；④ 是能力先到、校验没到：Astra 一段视频一次成功很惊艳，但 20 次演示与产线上的上万次成功率统计之间是几个数量级，演示不需要校验器；⑤ 是今天唯一校验尺度真实的一条——300 台机器人、年客流千万、天天开门、失败会被游客当场看见，它逃不掉。把五条放在一起，承的是 09-13「验收权外移」和 09-20「输出端归谁管」的下一问：验收方已经找到了，现在的问题是校验器装在哪一层——装在编译器里只能验类型，装在模型外面的显式结构里才能验前置条件，装在 cookie 政策里什么都验不了，只有装在时间和客流里才验得出可靠性。今天五条分别给出了这四种答案的价格。
