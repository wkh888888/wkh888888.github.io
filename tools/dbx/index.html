dbx：让 Spark 项目像普通工程一样本地开发、版本化发布

它不替你写 Spark 代码，只解决「本地写完怎么可靠地跑到集群上、还留得下版本」这件脏活。

先说清楚它的位置

dbx 全称 Databricks CLI eXtensions，是 Databricks Labs（官方实验室，非商业支持）维护的开源 CLI。它不是 Databricks CLI 的替代品 —— 恰恰相反，它重度依赖后者的 SDK 和认证。它也不是 MLflow CLI 或 Terraform Provider 的替代品：不碰基础设施，只管作业的打包、部署、启动与版本化。

一句话概括它的工作：把你从「在 Notebook 里点来点去」过渡到「本地 IDE 写代码、命令行发布、CI 里自动跑」。

它解决什么痛点

用 Databricks 的团队基本都经历过这个演变：

  1. 数据科学家在 Notebook 里跑通了逻辑；
  2. 要上生产，得把 Notebook 变成作业，参数、依赖、集群配置全靠界面点；
  3. 开发/测试/生产三套环境，配置靠人肉复制，改一处漏两处；
  4. 出问题时问「现在线上跑的是哪个版本」，没人答得上来。

dbx 针对的就是 2~4：本地代码打包上传、多环境配置集中管理、部署带版本号、可以在 CI 里一键完成。

典型命令长这样：

dbx deploy --environment=prod      # 按环境部署，自动生成版本化目录
dbx launch --environment=prod      # 在目标集群上启动作业
dbx sync repo -d my-repo --source .  # 本地改动实时同步到工作区

dbx sync 是我认为最实用的一条：本地改完立刻同步到工作区，保留了 Notebook 快速迭代的手感，又不用放弃 IDE 的重构和补全。

使用前的两个提醒

第一，新项目请先看 Asset Bundles。 Databricks 官方已经把 dbx 的文档标记为 retired，明确推荐新项目用 Declarative Automation Bundles（DAB，已内置进新版 Databricks CLI）。如果你是全新起步，直接上 DAB 更稳；dbx 的价值主要在：已有 dbx 工作流要维护、或者团队习惯了它的项目模板与 CI 写法。

第二，交互调试不是它的活。 dbx 没有交互式断点调试能力，要单步调试得配合 Databricks Connect。它管的是「部署与启动」，不是「调试」。

适合谁 / 不适合谁

适合 不适合
已有 Notebook 项目要工程化、要进 CI 全新项目（优先 DAB）
Python / JVM 项目多环境发布 R 项目（只能部署，无交互开发）
需要部署版本可追溯 想要基础设施即代码（用 Terraform Provider）

上手

pip install dbx
dbx --version        # 需 0.8.0 以上

认证复用 Databricks CLI 的 .databrickscfg（DATABRICKS_HOST + DATABRICKS_TOKEN，或用配置 profile）。装完先跑 dbx sync 感受一下本地与工作区的同步，再谈部署。
