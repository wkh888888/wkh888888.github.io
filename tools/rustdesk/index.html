RustDesk：把远程桌面的服务器搬回自己家

三期连着看，边界画的位置各不相同——Pinky 画在审批网关，ego lite 画在标签页，RustDesk 画在你自己那台服务器上。

先说清楚它不是什么

远程桌面是个老赛道，RustDesk 常被一句话概括成「免费开源版 TeamViewer」，这个说法漏掉了它真正值钱的部分：

  • 它不是又一个 VNC / RDP 客户端。VNC、RDP 是协议，你得自己解决「对方在哪、怎么穿 NAT」；RustDesk 是完整方案，自带 ID 注册、打洞协调和中继兜底，开箱就能连，也允许把这套中间层整个换成自己的。
  • 它不是「厂商云服务的免费替身」。TeamViewer / AnyDesk 的 ID 与中继永远在厂商手里，商业模式是订阅；RustDesk 的差别是那两个服务你可以自己跑，信任链因此从厂商挪回自己的机器。这才是「self-hosting」写在仓库 description 里的原因。
  • 它不是纯 P2P。打洞成功时两端直连，失败时（对称 NAT、CGNAT、企业防火墙）流量会走 hbbr 中继——中继要部署、要暴露端口、要有带宽，别以为自建服务器可以省掉。
  • 它不是「装了就零依赖」。默认用的是官方公共服务器，部署在境外；中文社区里关于延迟高、晚高峰断连的反馈相当一致，这也是几乎所有中文自建教程的出发点。想稳，就得自建。
  • 它不是 MIT / Apache，是 AGPL-3.0。客户端和 Server OSS 都是。自用无所谓，一旦二次开发、改代码、集成进自己的产品对外提供服务，传染性条款是要认真读的。
  • 它不是只有一个版本。Server OSS 免费，商业版 Server Pro 才带 Web 控制台、集中地址簿、LDAP/SSO、2FA 这些管理能力；把 Pro 的功能算进「免费自建」会踩空。
  • 它不是「自建了就自动安全」。密钥分发、无人值守密码、端口暴露、版本补丁，全变成你的责任。

预期摆正：这是个 2020 年建库、已经相当成熟的项目，但它的价值不在「免费」，而在你能把中间那一层拿回来自己管——以及随之而来的运维账单。

一手数据（2026-11-11 14:06 从 GitHub API 拉）：rustdesk/rustdesk，128,965 star / 20,537 fork / 214 open issue，主语言 Rust，AGPL-3.0，最新 release 1.5.1（2026-11-01）；服务端 rustdesk/rustdesk-server 10,728 star，同样 AGPL-3.0，最新 1.1.16（2026-07-20）。网上流传的 125k star / 1.5.0 是 10 月快照。

它解决什么痛点

  • 商业远控的成本与不确定性：订阅按用户/设备涨，商用检测误判、连接时长限制都见过；ID 和中继在对方手上，涨价时没有议价空间。
  • 数据经第三方中转的合规问题：远程维护时鼠标、键盘、剪贴板、文件传输全在链路上，公司客户数据、财务系统不该过别人的中继。
  • 国内连公共服务器的体验：延迟飘、偶发连不上，中继带宽也有限。
  • 要跨一堆平台：Windows、macOS、Linux、iOS、Android、Web 都要能连，还要无人值守访问、文件传输、TCP 隧道。

官网引用的一份 1000 多名自建用户在线调查里，用途分布是 37% IT 支持、25% IT 管理与维护、29% 远程办公、9% 工业及其他——自建的人绝大多数是拿它干运维的，不是拿它偶尔帮朋友看一眼屏幕。

核心能力

模块 说明
架构 只有两个服务：hbbs（ID / rendezvous，注册设备、协调打洞）+ hbbr（relay，直连失败时转发）。服务端刻意保持「笨」：只协调和转发
连接路径 客户端持续向 hbbs 心跳上报地址 → A 问「B 在哪」→ hbbs 尝试 TCP/UDP hole punching → 成功则两端直连（不耗中继），失败走 hbbr
加密 P2P + 端到端加密；会话密钥在两端协商，即便走中继，服务端也只看到密文、解不开内容
密钥绑定 hbbs 首次启动在数据目录生成 id_ed25519 / id_ed25519.pub；客户端填入公钥后只认你这台服务器，防止陌生 broker 插进来
音视频 VP8 / VP9 / AV1 软编解码，H264 / H265 硬编解码
功能 远程控制、文件传输、剪贴板同步、TCP 隧道、无人值守访问；Windows 上可不装、非管理员运行，按需提权
平台 Windows / macOS / Linux / iOS / Android / Web；另有 Flatpak、F-Droid 分发
开放性 官方仓库明说可以「自己写一套 rendezvous/relay server」，并给了 rustdesk-server-demo；协议不是黑盒
版本分界 OSS：客户端 + hbbs/hbbr 全免费；Pro：Web 控制台、集中地址簿、LDAP/SSO、2FA、按设备授权

我认为最值钱的两个：「服务器是笨的」这个架构决定（中继不解密，自建的风险面天然比“厂商能看见一切”小）和公钥 pinning（把信任锚定在自己生成的密钥上，而不是“连上一个看起来像我服务器的地址”）。相比之下，全平台支持只是顺理成章的配套。

平台与安装

客户端

官方 release 按架构给了 EXE / MSI / DEB / DMG / APK / Flatpak / AppImage / RPM 等。macOS 直接拖 .dmg 即可。

本机实测（macOS 26.6.2 / arm64）：

项 实测值
应用 /Applications/RustDesk.app，1.5.1，69 MB，2026-10-30 安装
签名 Gatekeeper accepted、Notarized Developer ID，主体是个人开发者 zhou huabing（不是公司主体——开源项目常见形态，值得留意但不等于风险）
配置目录 ~/Library/Preferences/com.carriez.RustDesk/，含 RustDesk.toml、RustDesk2.toml、peers.toml 等
自建相关键位 配置结构里预留了 custom-rendezvous-server / relay-server / key / rendezvous_server 等项
服务端 本机没有 hbbs / hbbr 进程，21116/21117 也无监听——这台机器只是客户端

服务端：官方主推 Docker，也能裸机跑

两条路都可以。官方主推 Compose（rustdesk/rustdesk-server 镜像 + network_mode: host，两个容器分别 hbbs / hbbr，挂同一个持久数据卷）。但对「不碰容器、纯裸机进程 + 反代」的环境，其实更简单：从 Server OSS release 下载 rustdesk-server-linux-amd64.zip，解压出 hbbs、hbbr 两个二进制，各写一个 systemd unit 托管，数据目录持久化即可——整套东西就两个进程，不需要数据库、不需要消息队列。

端口表（官方文档，最容易配错的地方）：

服务 端口 用途
hbbs TCP 21115 NAT 类型测试
hbbs TCP + UDP 21116 UDP：ID 注册与心跳；TCP：打洞与连接服务（两个协议都要开）
hbbs TCP 21114 Web 控制台，仅 Pro 版
hbbs TCP 21118 Web 客户端支持，不需要就关掉
hbbr TCP 21117 中继服务
hbbr TCP 21119 Web 客户端支持，不需要就关掉

最小可用集合就是 21115 / 21116(TCP+UDP) / 21117；21118、21119 不用 Web 客户端就别开。

客户端配置：设置里填 ID Server（你的 hbbs 地址）、Relay Server（可选）、以及 id_ed25519.pub 的内容。 fleet 场景可以在分发客户端时把配置预置进去。

裸机 + OpenResty 反代的两个要点（如果你要用反代暴露 Web 客户端）：一是 X-Real-IP 必须由反代自己设置；二是用防火墙把 21118/21119 限制成只有反代能连。原因在下一段。

边界与注意

  • 官方明写的 WebSocket 头伪造风险：启用 21118/21119 时，hbbs/hbbr 会信任 WebSocket 连接的 X-Real-IP / X-Forwarded-For 来判断真实客户端 IP，且这两个头不做校验。任何能直连这两个端口的人都能伪造任意 IP，绕过基于 IP 的限速与封禁、并污染日志。所以：要么关掉这两个端口，要么只通过会自己设置 X-Real-IP 的反代暴露，并由防火墙挡住直连。这是官方文档 Caution 原文，不是社区猜测。
  • AGPL-3.0 的传染性。自用、内部运维没问题；改代码对外提供服务，先搞清义务。
  • 无人值守密码是最大攻击面。一旦设了永久密码，拿到 ID + 密码就等于拿到这台机器的完整控制权。强密码、限定设备、别开自助注册；2FA / 集中权限在 Pro 版才有。
  • 公共服务器在境外。社区反馈集中在延迟与偶发断连；这是自建的主要动因，但「官方停止中国服务」这类绝对说法我没有找到官方声明，不写进结论。
  • 自建 = 自己运维：id_ed25519 私钥要备份（丢了所有客户端都得重新分发公钥）、服务端要跟版本、防火墙要最小化暴露。1.5.1 的 changelog 里已经有了「校验签名更新元数据」「可信设备 V2」这类安全向改动，说明这条线还在动。
  • 编译门槛不低：从源码构建要 Rust + C++ 环境、vcpkg（libvpx / libyuv / opus / aom）、Flutter（旧 Sciter UI 已 deprecated）。想自己出包，先预留半天。
  • README 顶部有 Misuse Disclaimer：作者明确不支持未授权访问、控制或侵犯隐私的用途。企业里推广前，把使用规范和审计先立好。
  • Pro 的钱要算清：Web 控制台、地址簿、LDAP/SSO、2FA 都不在 OSS 里；团队集中管理的需求若强，要么上 Pro，要么自己在外层补一套访问管理与审计。

适合谁

方案 中间层在谁手上 开源 成本 运维责任
TeamViewer / AnyDesk 厂商云 否 按用户/设备订阅 厂商
VNC / RDP + 自己组网 无独立中间层，靠 VPN/端口映射 视实现 低 自己
MeshCentral / Guacamole 自建 是 免费 自己（较重）
RustDesk + 自建 hbbs/hbbr 自己的服务器 是（AGPL-3.0） OSS 免费 / Pro 按设备 自己（只需两个进程）
  • 有公网 VPS、要长期远程维护多台机器的人：两个二进制就能把 ID 和中继全搬回自己手上，规格要求极低（打洞成功时中继几乎不吃流量）；
  • 对数据主权有合规要求的团队：中继只见密文、日志与 ID 留在自己机房，这条比“端到端加密”四个字更能过审；
  • 国内用户嫌公共服务器慢的：自建节点选离自己近的机房，延迟可预期得多；
  • 不想碰容器的：裸机 systemd 托管两个进程完全够用，Docker 只是官方给的最省事路径，不是前提。

不适合谁：只是偶尔帮朋友远程一次的人（默认公共服务器就够，别为一次连接运维一台 VPS）；没有公网入口、也不愿配组网/端口映射的；需要开箱即用的账号体系、SSO、2FA 和集中审计却不想付 Pro 的；以及打算把无人值守密码长期开着、又不做 IP 限制和访问审计的——那等于给全网留了一扇门。

一句话收尾：把三期的「边界」摆在一起看很有意思——Pinky 把边界画在网关审批上，ego lite 画在标签页隔离上，RustDesk 画在服务器归属上。三者都在回答同一个问题：当能力交出去之后，最后那道能由你说了算的闸门，到底装在哪。RustDesk 给出的答案最朴素也最硬——装在你自己的机器上。
