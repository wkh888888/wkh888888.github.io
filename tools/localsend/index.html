LocalSend：连账号都不用，把文件留在局域网里

前面五期都在讨论「中间那一层归谁」，这一期干脆把中间层删掉——没有账号、没有服务器、甚至不需要互联网。

先说清楚它不是什么

LocalSend 常被叫「跨平台 AirDrop」，这个比喻好懂，但会漏掉它真正的取舍：

  • 它不是网盘或消息类应用。不上传、不同步、不留存历史；两台设备互相发现、传完就结束，没有一个「云端」存在。
  • 它不是聊天工具的文件传输。虽然 README 里用「secure communication between devices」描述，实际交付的是本地 REST API + HTTPS 的文件收发，不是 IM。
  • 它不是破网工具。跨网段、跨公网、异地互传都不在默认能力里；官方设定就是「同一个局域网」。想跨网络，得自己配 VPN / 组网，那是另一层的活。
  • 它不是 AirDrop 的完整等价物。AirDrop 靠苹果生态的蓝牙 + Wi-Fi 直连与设备身份体系；LocalSend 靠局域网广播发现 + 每台设备即时生成的自签证书，没有账号体系，也就没有「这个设备是不是可信」的现成答案。
  • 它不是装上就一劳永逸。README 明说没有自动更新，并建议从应用商店或包管理器安装以便升级。
  • 它不是只给电脑用的。Windows / macOS / Linux / Android / iOS / Fire OS 六端都有官方分发渠道，这才是它相对 AirDrop 的核心价值。

预期摆正：LocalSend 的价值不是「更快」，是把文件传输这件事从任何第三方手里拿回来。代价是你要接受局域网这个物理边界。

一手数据（2026-11-11 15:04 从 GitHub API 拉）：localsend/localsend，98,334 star / 5,618 fork / 1,031 open issue，Dart/Flutter，Apache-2.0，建库 2022-12-16，最新 release v1.18.2（2026-08-21）。官网 localsend.org。

它解决什么痛点

  • 生态混搭：Mac 传 Windows、Windows 传 Android、Android 传 Linux——AirDrop 只管苹果设备，互相之间的通路通常靠微信文件助手、QQ、网盘绕一圈。
  • 「传个文件为什么要上云」：几十 MB 的截图、几百 MB 的安装包，从这台机器到一米外的另一台机器，却要先传到某个服务器再下载回来，既慢又留痕。
  • 公司/内网环境的合规别扭：客户资料、日志文件不能过公网盘，但又没有专门的内网传输工具。
  • 没网也要传：会议室、机房、飞机上、只有一台路由器的临时环境，互联网不通但局域网是通的。

LocalSend 的答案是把协议压到最小：设备之间用 REST API 通信，全部数据走 HTTPS，TLS/SSL 证书在每台设备上即时生成；不需要账号、不需要注册、不需要外部服务器，也不需要互联网。

我认为最值钱的两个：「不需要账号」这件事本身（没有登录态、没有设备绑定、没有云端历史，是这五期里信任面最小的一个）和端口只有一个（53317，排查网络问题时的复杂度比一整套服务发现低一个量级）。全平台分发是让它真正能替代 AirDrop 的前提，不是加分项而是及格线。

平台与安装

官方明确建议走应用商店或包管理器，原因很实在：应用本身没有自动更新，靠渠道跟版本才不会长期停在旧版。本机就是 brew install --cask localsend。

装完通常开箱即用；连不上时按官方 Setup 表排查：入站 TCP/UDP 53317 放行、出站不限制、路由器关掉 AP 隔离（访客网络常默认开着 AP 隔离，这是最常见的「明明在同一 Wi-Fi 却发现不了对方」的原因）。

一个如实记录的观察：打开时没有常驻后台服务，跟 UU远程、ToDesk、magpie 那几款「开机就挂几个进程」的工具不一样。代价是每次要传文件都得先把两端的应用打开——这正是「没有中间层」的另一面。

边界与注意

  • 同一个局域网是硬前提。跨 VLAN、跨网段、访客 Wi-Fi 开了 AP 隔离、公司网络禁广播、两端各自挂在不同 VPN 里，都会直接发现不了。这不是 bug，是设计。
  • 端口要能通。53317 的 TCP 和 UDP 入站都要放行；企业终端管控、防火墙默认策略常拦这一关。
  • 设备身份靠你自己核对。每台设备即时生成自签证书，HTTPS 保证了链路上是加密的，但没有账号体系或可信设备列表来做身份验证——在公共 Wi-Fi、会议室这种环境里，收到文件前先看清楚对方设备别名，别闭眼点接受。这是「无账号」必然换来的责任，不是实现缺陷。
  • 没有自动更新。安全相关的版本滞后要自己盯；这也是官方反复建议走包管理器/应用商店的原因。
  • 官方挂了 CAUTION 的第三方构建：README 提醒存在一个非官方 MSIX 预览站，稳定性不保证；装包只认官方渠道与签名（Windows 二进制有签名，macOS 版本机实测已公证）。
  • 速度取决于你的 Wi-Fi，不取决于软件。局域网直连没有云端限速，但路由器、2.4G 频段、AP 隔离下的中继都会把它打回原形；大文件别拿它跟有线拷贝比。
  • 构建门槛不小：Flutter + Rust + fvm 锁版本，README 明说系统级 Flutter 版本不匹配会编译失败。想自己出包要按它的 .fvmrc 来。
  • 1,031 个 open issue：项目成熟、star 近十万，但问题也不少；遇到平台特有的坑（尤其 Linux 桌面 portal、iOS 后台限制）先查 issue，别假设是自己的网络坏了。

适合谁

方案 中间层 要账号 跨生态 互联网 数据落在哪
AirDrop 苹果设备直连 Apple ID ✗ 仅苹果 不需要 两端
微信 / QQ 文件助手 厂商服务器 要 ✓ 要 厂商（有留存风险）
网盘同步 云端 要 ✓ 要 云
远控软件的文件传输（13–15 期） 厂商中继或 P2P 要 ✓ 通常要 两端 + 厂商链路
LocalSend 无 不要 ✓ 六端 不需要 只两端
  • 苹果 + Windows + Android 混用的人：这是它最不可替代的场景，一条局域网把所有设备拉平；
  • 对「为什么要上云」敏感的人：日志、客户资料、内部包在两台机器之间走完，不产生云端副本；
  • 弱网 / 无网环境：机房、会议室、临时路由器下照样能传；
  • 不想再多一个账号的人：没有注册、没有设备绑定、没有同步关系，装完就能用，卸了就干净。

不适合谁：需要异地、跨公网互传又不想自己组网的（那该看 VPN / Tailscale 或回远控工具）；企业网络里 UDP 广播和 53317 都被拦、又没有权限改防火墙的；以及需要传输审计、权限控制、留存记录的团队——LocalSend 刻意不提供这些，别把它当内网文件系统的替代品。

一句话收尾：前面五期的选题其实都在问「中间那一层归谁管」——Pinky 归网关、ego lite 归浏览器、RustDesk 归你自己的服务器、UU远程归厂商条款、ToDesk 归价目表。LocalSend 给的是第六个答案：谁都不归，因为压根没有中间层。简单到近乎固执，也因此在隐私这件事上，比前面任何一个都干净。
