P019 · bash 脚本里 `$VAR` 紧跟全角括号：LANG=C 下吞字节，报 unbound variable

blog-publish 三路发布跑到「同步产物回提交」这一步突然中止，退出码 1：

现象

blog-publish 三路发布跑到「同步产物回提交」这一步突然中止，退出码 1：

[redact] 无 P0/P1 命中，继续构建
/Users/kehua/.agents/skills/blog-publish/scripts/publish.sh: line 117: MSG<乱码>: unbound variable

两处误导：

  1. 报错里变量名是乱码（MSG 后面粘了一个不可见字节），看起来像变量真的没赋值 —— 但 MSG 明明由 -m 传入且前面几步已正常用过。
  2. 失败点在整条流水线的 2/3 处：GitLab 已 commit + push、日报已 sync、脱敏门禁已过；但构建、GitHub Pages、服务器 rsync 全没跑。只看到 exit 1 会以为“发布失败什么都没发生”，实际是“发了一半”。

出问题的代码：

git commit -m "sync: 栏目同步产物 $TODAY${MSG:+（$MSG）}"

根因

bash 解析 $MSG） 时，把紧跟其后的全角右括号 ） 的首字节（0xEF）当成了变量名的一部分，于是变量名变成 MSG\xEF → 未定义 → 在 set -u 下报 unbound variable。

关键前提是 locale：

环境 LANG=C（本次） LANG=en_US.UTF-8（此前各次）
bash 对 0xEF 的判断 单字节表里 0xEF 是“字母”（Latin-1 的 ï） 多字节感知，正确整体切出全角字符
结果 吞进变量名 → 崩 正常 
# 复现（本机 bash 3.2.57，macOS 自带）
$ LANG=C bash -c 'set -euo pipefail; MSG=x; echo "${MSG:+（$MSG）}"'
bash: MSG<乱码>: unbound variable

# 加花括号界定变量名即安全，与 locale 无关
$ LANG=C bash -c 'set -euo pipefail; MSG=x; echo "${MSG:+（${MSG}）}"'
（x）

为什么以前没炸：该行 2026-09-16 加入，此后 09-16/17/18/20/21/23 各期都正常 —— 那几次的 LANG 不是 C（IDE/登录 shell 注入 UTF-8 locale）。本机 bash 3.2（11 年前的版本，多字节支持有先天缺陷）不会跟着脚本走，只跟着调用时的 locale 走，所以这是一个“平时看不见、换环境必炸”的定时炸弹。

铁律

  1. 脚本里 $VAR 后面紧跟非 ASCII 字符（中文、全角标点）时，一律写成 ${VAR}。 不要依赖 locale 正确 —— 花括号是零成本的显式边界。

  2. 反向自查命令（$VAR 后直接跟非 ASCII 字节的行）：

    grep -nE '\$[A-Za-z_][A-Za-z0-9_]*[^A-Za-z0-9_"'"'"'$/{}().,:;= \t-]' script.sh

  3. set -u 是放大器：同样的解析错误在没开 -u 时只会静默展开成空串（提交信息里少一段），开 -u 就直接中止整条流水线。开 -u 是好事，但要接受它把“此前静默的问题”升级为“硬失败”。

半成品状态的处置

脚本中途死掉时，先看它死在哪一步再决定重跑方式，不要无脑重跑全流程：

已完成的动作 残留状态 正确做法
GitLab commit + push 已在远端 幂等，重跑会打印 Everything up-to-date，不用回滚
sync 已改写产物 产物已被 git add -A 暂存（未提交） 人工补一次 commit 保住规范的两个提交（源码 commit + sync: commit），再重跑
脱敏门禁已扫 无副作用 —
构建 / GitHub / 服务器 完全没跑 重跑脚本补齐

本次处置：修脚本 → 人工补 f02b3e8 sync: 栏目同步产物 ... 并 push → 重跑脚本（EXIT=0，GitLab=done GitHub=done Server=done）。历史分两笔提交的结构得以保持，与 09-23 期形态一致。

同类隐患一并修掉

同一个脚本里还有两处相同写法，都藏在很少走到的分支里，这次一起改成 ${VAR}：
