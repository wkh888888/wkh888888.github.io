P020 · `git push` 卡住十几分钟：ssh config 映射 `ssh.github.com` + 本机 DNS 不可达

现象

blog-publish 三路发布卡在 GitHub 段约 15 分钟，日志停在：

[main 73a49b2] Site updated: 2026-10-07 (AI 日报 2026-10-05)
 6 files changed, 451 insertions(+), 4 deletions(-)
 create mode 100644 ai-daily/2026-10-05.html
                              ← 之后长时间无输出

没有报错、没有超时退出，就是不动。

根因

本机 ~/.ssh/config 刻意把 GitHub 的 SSH 走 443（规避 22 端口封锁）：

Host github.com
    Hostname ssh.github.com
    Port 443
    User git

本次本机 DNS 服务器不可达（dig +short ssh.github.com 直接 connection timed out），ssh.github.com 无本地缓存 → 解析不出来。ssh 默认没有连接超时，于是进程挂在解析/连接阶段，表现为无限挂起。

与 P004（git/curl 直连 GitHub hang 死）同族，但根因不同：P004 是「没注入代理」，本次是「DNS 解析失败 + 命令无超时」。

定位（三条只读命令）

ps -ef | grep 'git-receive-pack'                   # 卡住的 ssh git-receive-pack 进程
dig +short +time=3 ssh.github.com                  # 超时/无结果 → DNS 侧故障
nc -z -G 5 github.com 22 && echo 22通               # 备用通道是否可用
git -C <pages-repo> log --oneline -1               # 确认 commit 已生成、只是没推出去

实测参考：dig github.com 也超时（DNS 服务器整个不可达），但 nc -z github.com 22 通 —— 说明系统解析器有缓存、纯 DNS 查询路径坏了。

处置

1. 中断卡死进程（kill <publish.sh pid> <git push pid> <ssh pid>），脚本随之退出。

2. 人工补推 Pages 仓 —— 绕过坏掉的 config 直连可用通道：

cd ~/projects/server-apps/wkh888888.github.io
git -c core.sshCommand='ssh -F /dev/null -o BatchMode=yes -o StrictHostKeyChecking=accept-new' push origin main

（-F /dev/null 忽略 ssh config，回落到默认 github.com:22；本机 known_hosts 已有 github.com 条目，不会交互提示。）

3. 人工补跑服务器段（参数与脚本一致）：

cd ~/projects/server-apps/astro-blog
STAGE=/home/walker/.deploy/blog.walkerhua.com; ROOT=/www/wwwroot/blog.walkerhua.com
O=(-p 22222 -o LogLevel=ERROR -o BatchMode=yes -o ConnectTimeout=10)
ssh "${O[@]}" walker@192.0.2.10 "mkdir -p $STAGE"
rsync -az --delete -e "ssh -p 22222 -o LogLevel=ERROR -o BatchMode=yes" dist/ "walker@192.0.2.10:$STAGE/"
ssh "${O[@]}" walker@192.0.2.10 "set -e; sudo -n mkdir -p $ROOT; sudo -n rsync -a --delete --exclude='.user.ini' --exclude='.well-known' $STAGE/ $ROOT/"

4. 补记发布留痕（脚本第 5 段随中断被跳过）。

⚠️ 铁律：GitHub 段失败后，重跑脚本推不上去

脚本判断「要不要 push」用的是工作区是否干净（git status --porcelain），不是「本地是否领先远端」。

PAGES 仓已 commit 未 push 时，工作区恰恰是干净的 → 重跑打印 [github] 无变更，跳过 commit/push，推送永远不会发生。

所以这种情况必须人工 git push，别指望重跑自愈。

已修复进脚本（2026-10-07）

publish.sh GitHub 段的 push 注入连接与存活超时：

GIT_SSH_COMMAND="${GIT_SSH_COMMAND:-ssh} -o ConnectTimeout=15 -o ServerAliveInterval=10 -o ServerAliveCountMax=3" git push origin main

DNS/网络异常时 15 秒快速失败（脚本 set -e 随即退出），不再挂 15 分钟。注意这只缩短失败时间，不解决连通性；ssh config 的 443 映射保持不变。

教训

  1. 无超时的网络命令是定时炸弹。ssh / git push / rsync 默认都可能无限等，关键链路一律显式给 ConnectTimeout。
  2. “卡住”和“报错”要分开处置：报错能看堆栈，卡住得先 ps -ef 找进程、再逐层探活（DNS → TCP → 认证）。
  3. 幂等重跑不是万能的：重跑能不能补漏，取决于脚本的判据是「状态干净」还是「目标一致」。判据是前者时，半完成状态会被判成“无需动作”。
