P009 · 升级/重启/卸载全都"报成功"却全都没生效——三个假成功，同一个病根：落点不一致

现象

同一条链路上三次操作，CLI 都报成功，实际全都没生效：

# 操作 CLI 输出 实际结果
1 openship update installed openship@0.7.2 / Restarted the service onto the new version 装进了 bun 全局目录，服务端仍跑 nvm 的 0.6.8；Dashboard 横幅持续提示“可更新到 0.7.2”
2 openship stop && openship up ✔ Openship is running as a service / launchd agent io.openship.up / Starts on boot and auto-restarts launchd job 根本没加载（launchctl print → Could not find service），无进程、10303/10304 无监听，浏览器“拒绝连接”
3 npm uninstall -g openship up to date in 379ms（无任何报错） 包目录和 bin 链接纹丝未动

关联症状：Dashboard 一直提示“有新版本”——它是对的，因为真正在跑的服务确实还是旧版。

根因

一句话：CLI 的成功输出描述的是「命令自身执行完毕」，不是「你预期的那份产物在预期位置生效」。 只要机器上存在多套 node / 多个包管理器 / 多种安装形态，这个断层就必然出现。

三个子现象的直接原因：

  1. update 装错落点——detectPackageManager2() 只判断 bun --version 能否执行成功，完全不看 CLI 自己装在哪：

    const hasBun = spawnSync("bun", ["--version"]).status === 0;
return hasBun ? "bun" : "npm";     // 机器上有 bun → 永远用 bun

    而 launchd plist 硬编码了 nvm 的 node + nvm 的 openship。更新落点 ≠ 运行落点，从此版本永不一致。

  2. up 没真正 bootstrap——stop 只做 bootout（不移除 plist），紧接着 up 会跳过真正的加载；输出文案照旧是“已装好”。plist 文件本身完全正常（手动 launchctl bootstrap 一次即成功，exit 0），坏的只是安装路径。

  3. npm -g 作用于错误 prefix——npm 的全局 prefix 由 process.execPath 推导。~/.nvm/.../bin/npm 是 #!/usr/bin/env node 脚本，当 PATH 把另一个 node（WorkBuddy 托管版）排在前面时，prefix 被算成那个 node 的目录：

    ~/.nvm/versions/node/v22.22.3/bin/npm config get prefix
→ /Users/kehua/.workbuddy/binaries/node/versions/22.22.2-3     # 不是 nvm 目录

    于是 uninstall -g 跑去错误目录找包 → 找不到 → “up to date”，而真身还在原地。

解法

1. 消除落点不一致（治本）：统一到单一安装形态

以 OpenShip 为例，改用官方 installer 的 tarball 形态——它是自包含 + sha256 校验的，且 selfInvocation() 会走 cli.launcher 分支，plist 只需引用一个恒定路径的 launcher：

curl -fsSL https://get.openship.io | sh
~/.openship/bin/openship up --port 10303 --dashboard-port 10304

之后升级只切换一个符号链接，launcher 与 plist 都不用动：

launchd plist → ~/.openship/bin/openship（恒定） → cli/current（软链） → cli/v0.7.2/

2. 验证必须看「运行时」，不看被操作方的输出

launchctl list | grep <label>                                    # job 真的加载了吗
ps -o command= -p $(pgrep -f "dist/server/index.js" | head -1)   # 实际跑的是哪份代码
command -v <cmd>                                                 # PATH 生效的是哪一份
readlink -f <bin>                                                # 符号链接真实落点

3. 多 node 环境下 npm -g 一律显式 --prefix

~/.nvm/versions/node/v22.22.3/bin/npm uninstall -g <pkg> --prefix ~/.nvm/versions/node/v22.22.3

4. 排查起手式：先查落点，别先查逻辑

which -a <cmd>            # 机器上有几份同名命令
npm config get prefix     # 全局装的落点在哪
ls -la <install-dir>      # 文件时间戳能不能对上"我刚更新过"

文件时间戳是最硬的证据：服务端文件停在 8/26、而 update 发生在 9/11 → 一眼看穿“根本没更新”。

预防规则（建议上浮 L1）

  • 铁律：CLI 报成功 ≠ 生效。 凡涉及“改运行时 / 装包 / 装服务”，必须用独立命令验证目标状态（job 列表、进程命令行、文件时间戳、符号链接指向），不得引用被操作方自己的输出。
  • 多运行时机器上，npm -g 必须显式 --prefix；which -a + npm config get prefix 是前置检查。
  • 同一工具只允许一种安装形态；发现两种并存，先收敛再操作。

相关文件

  • ~/.openship/cli-install.json（分布标记，决定 update 走哪条分支）
  • ~/.openship/bin/openship（launcher）、~/.openship/cli/current（软链）
  • ~/Library/LaunchAgents/io.openship.up.plist
