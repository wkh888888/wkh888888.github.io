P029 · 新写的坑文会在下一轮发布突然中止整条流水线：门禁在「已推 GitLab」之后

发 AI 日报时顺手同步了一批源笔记，门禁直接中止整轮发布：

踩坑于 2026-11-08约 3 分钟网络运维
目录
现象根因处置套路通用教训关联

内容管线是「全量同步 + 门禁卡在提交之后」，所以新写的源笔记不会立刻出事，而是下一轮发布时才炸，且炸的时候 GitLab 已经推上去了。

元信息
日期 2026-11-08
领域 网络 / 运维
严重度 中（发布中断，且留半推送状态）
关键词 全量同步、发布门禁、半推送状态、源笔记隔离、mtime 判据、预构建、同步产物单向覆盖、P026、P028
状态 有效

现象

发 AI 日报时顺手同步了一批源笔记，门禁直接中止整轮发布：

[redact] 检出敏感内容（P0/P1），已中止发布：先 apply 脱敏再跑，或加 --skip-redact 绕过

关键在于源笔记是新写的：写它的那一轮发布已经跑完了，它当时还没被同步，所以一切正常； 下一轮发布才把它带进 src/content/ → 门禁命中 → 中止。

  • 中止点在脚本第 2.5 步（构建前），而第 1 步已经 git push origin main → 留半推送状态（GitLab 已收新内容，Pages 与服务器还是旧的）。
  • 脚本注释写「门禁中止时不落提交，保持工作区原样」——那只对同步产物成立，第 1 步的 commit 早于同步，工作区里手写的改动照旧被推走了。

根因

三个设计叠在一起，缺一不可：

  1. 同步是全量的：源目录里新增的笔记会被下一轮自动带进公网产物，不需要任何人批准。
  2. 门禁只看产物：它扫 src/content / src/pages / public/ai-daily，扫不到源目录 —— 所以源笔记里的敏感内容在写入那一刻没有任何拦截。
  3. 门禁排在提交之后：敏感内容是在「已经推上 GitLab」之后才被发现的。

结果就是问题被推迟到下一轮暴露，而暴露时流程已经跑了一半。

处置套路

① 先判「这轮会不会带出新东西」，再决定是否隔离。

发版前把源目录与目标目录做差集，看有没有源有目标无的新文件。判它是不是「待发稿」要两条硬判据，缺一不可：

  • 源文件 mtime 是否晚于上一轮发布时刻（晚于 = 真正新稿；早于 = 上一轮本该带上却被漏掉的「补收录」，后者可放行）；
  • 是否被源目录索引或任何发布记录提及（= 有明确待发意图）。

两条都不满足 → 判为未发布新稿，隔离。

② 隔离要挪「源 + 目标 + dist 产物」三处。

只挪目标无效 —— 全量同步会从源重建它。只挪源、目标与产物都没有 → 只挪源一件即可（三处一起挪的前提不成立时，多挪反而多余）。源和目标绝不能挪进同一个目录：mv 第二次会覆盖第一次，原始源文件直接丢失。

③ 敏感内容改源文件，不改产物。

同步脚本每次发布单向覆盖目标产物，改产物下次就被原样同步回来。改源文件。

改完必须复扫：0 命中才算过。

④ 预构建。

脚本第 1 步先推 GitLab 再构建，构建失败会留半推送状态。所以先手工 npm run build 跑一遍， 确认构建能过再让脚本接管。

通用教训

  1. 「写入时没报错」不等于「会安全发布」：全量同步管线里，源目录的每一次新增都是一份对下一轮发布的承诺。
  2. 门禁的位置决定了失败形态：排在提交之后 → 失败时状态是「一半已推」。判断一个发布流程安不安全，先看门禁在第几步。
  3. 自动化留痕不等于内容被审过：脚本会替你发布，但不会替你决定该不该发布。
  4. 发布脚本的注释与实际行为要对照着读：注释说的保护范围可能只覆盖部分产物，不覆盖你在工作区里的手写改动。
