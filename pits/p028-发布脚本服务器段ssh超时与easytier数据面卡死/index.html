现象

[github] 已推送 GitHub Pages（线上生效约 1-2 分钟）
ssh: connect to host 192.0.2.1 port 22222: Operation timed out

服务器是 walker@192.0.2.1:22222，走 EasyTier 虚拟内网（utun4，本机 192.0.2.2，peer 段 192.0.2.0/24）。

先排除的「看起来合理」的解释

猜想 实际排查结果 判据
服务器宕机 ❌ 机器活着 https://blog.walkerhua.com/ 仍 200，nginx last-modified 还是上一期产物
SSH 密钥失效 / 被拒 ❌ 不是认证问题 超时发生在 TCP connect 阶段，根本没走到认证（认证失败会立刻回 Permission denied）
SSH 端口改了 ❌ 端口没变 ~/.ssh/known_hosts 里 [192.0.2.1]:22222 仍是当前 key；22222 与 22 全超时说明是「连不上」而非「端口拒绝」
本机隧道整体故障 ❌ 只是定向到该节点 对 192.0.2.11 / .12 的 22 端口 nc 秒连成功
宝塔面板侧可绕 ❌ 白名单挡住 面板 28888 公网可达，API 签名正确，但返回「IP校验失败,您的访问IP为[203.0.113.10]」——本机出口 IP 不在白名单

真正的根因

EasyTier 隧道到该服务器的「数据面」定向卡死，控制面仍正常。

  • easytier-cli peer 显示 192.0.2.1 在线、p2p 直连、0% 丢包 → 控制面（peer RPC / 路由同步）活着
  • 但 ping / nc 对该节点的所有端口（22 / 22222 / 80 / 443 / 3306 / 8888）全部超时 → 数据面（真实业务流量）不通
  • 同一时刻其他 peer 一切正常 → 本机 easytier-core 进程（launchctl 里的 com.easytier.walker）健康，不是本机整体问题

处置套路（核心）

不要重跑整个 publish.sh —— 重跑会重复 commit、重复构建、重复推送，而且脚本判据是「工作区干净就跳过 commit」，已推送的内容不会再推一遍，容易造成状态混乱。

正确做法是只补跑服务器段：

# 1) 先 raw socket 复测端口（比 nc/ssh 少一层封装，更能反映真实连通性）
python3 -c "
import socket,time
s=socket.socket(); s.settimeout(60); t=time.time()
try:
    s.connect(('192.0.2.1',22222)); print('CONNECTED in',round(time.time()-t,1),'s')
except Exception as e: print('FAIL after',round(time.time()-t,1),'s:',e)
"

# 2) ssh 复测（确认认证也通）
ssh -p 22222 -o LogLevel=ERROR -o BatchMode=yes -o ConnectTimeout=15 walker@192.0.2.1 "echo SSH_OK; uptime"

# 3) 只补服务器段
bash ~/.agents/skills/blog-publish/scripts/publish.sh -m "<消息>" --skip-gitlab --skip-github

第 1 步实测立即 CONNECTED（0.0s）—— 说明隧道卡死是瞬时的，自己会恢复，多等一会儿就好。

⚠️ 两段式跑完的副作用：发布记录被污染

第二段用 --skip-gitlab --skip-github 跑，脚本的自动留痕会把这一行写成：

| 16:53 | AI 日报 2026-11-05 | `116f746` | `—` | ——✓ | 首页 200 |

Pages 仓哈希丢成 —，三路标记变成「——✓」，与实际（GitLab ✓ / Pages ✓ / Server ✓）不符。

→ 必须手工改回 116f746 / bfa5c27 / ✓✓✓。查实际哈希：git -C <Pages仓> log --oneline -1。

通用教训

  1. 「连接超时」与「认证失败」是两回事：前者说明链路/服务没通，后者说明密钥/账号问题。排查顺序必须先分清，否则会在密钥上白费功夫。
  2. 多路径部署脚本要能分段重跑：全流程重跑比单段补跑风险大得多（重复副作用、状态混乱）。有 --skip-* 就该优先用。
  3. 备用通道要先验证可用性再依赖它：宝塔面板 crontab 拉包法看着能用，实际卡在 IP 白名单 —— 备用方案也要先探活。
  4. 自动化留痕会因分段执行失真：脚本只知道自己这次跑了什么，不知道上次跑了什么 → 分段跑完要人工校对留痕。
