P016 · 末尾健康检查失败，被判成整次发布失败（并静默吞掉收尾动作）

发布脚本三路跑完，末尾报失败：

状态 有效

现象

发布脚本三路跑完，末尾报失败：

[github] 已推送 GitHub Pages（线上生效约 1-2 分钟）
curl: (28) Resolving timed out after 10000 milliseconds

复核线上，三路其实全部成功：首页与目标页均 200，服务器文件时间戳也对得上。

真正被这次「失败」连累的是它后面的动作全没执行：

受影响 后果
发布记录自动留痕 整段被跳过，当日记录缺失
源码仓产物提交 未提交（同步发生在 commit 之后）

于是「发布没做」的假象成立 —— 实际只是最后一步观测失败。

根因

一句话：把「观测动作」放在了能终止「执行流程」的位置，而它下游还有收尾动作。

  • 直接原因：瞬时 DNS 解析失败（Resolving timed out），curl 退出码非 0。
  • 根本原因：脚本用 set -euo pipefail，落位后的验证 curl 是普通语句，失败即 exit 1。此时犯了两层错：
    1. 判定错位 —— 部署动作（ssh + rsync）已完成，「落位是否成功」与「此刻能否立刻 curl 通」是两件事。一个网络观测动作拿到了否决整个发布的权力。
    2. 收尾被吞 —— 留痕、补提交等收尾动作排在验证之后，验证一挂就全部不执行，失败被放大成「什么都没干」。

注意触发因素是噪音（DNS 抖动），但缺陷不是 —— 换个网络抖动、证书续期、CDN 缓存任何一种都会复现。同类失误在任何「执行 → 验证 → 收尾」结构的脚本里都成立。

解法

验证步与执行步分离，验证失败降级为告警：

if curl -fsS --connect-timeout 10 --retry 3 --retry-delay 2 --retry-all-errors \
     https://<站点>/ > /dev/null; then
  echo "[server] 已部署并验证 https://<站点>/"
else
  echo "[server] 部署已完成，但首页验证未通过（疑似瞬时 DNS/网络抖动），请人工复核" >&2
fi

--retry-all-errors 需 curl ≥ 7.71（本机 8.7.1 已确认支持）。

在旧版本上撞到时，别急着重跑全流程（可能造成重复发布），先复核事实：

curl -o /dev/null -w '%{http_code}\n' https://<站点>/<目标页>   # 200 即已上线

确认已上线后，只补做被跳过的那两步（补提交 + 补记留痕）即可。

预防规则（判断是否上浮 L1）

本条暂留 L2：~/.workbuddy/MEMORY.md 于 2026-09-15 实测 5219 字符，超 4000 硬上限。 当日已做第一轮瘦身（5219 → 4407，主压 CODEGRAPH 块与自有冗余节），仍差 407； 按「达到软阈值后先迁移再新增」的规则，暂不上浮本节前两条，待 L1 达标后再补。

  • 执行与观测分离：健康检查/验证类动作失败只告警，不作为流程终止条件。成败判定依据是「是否真正落盘」，不是「此刻能否探测到」。
  • 收尾动作不能排在致命步骤之后：留痕、日志、提交这类收尾，要么前置，要么用 trap ... EXIT 兜底。
  • set -e 下显式区分致命与非致命：非致命步骤写 || true 或包进 if，别让它继承全局的「失败即死」。
  • 通用问法：这个报错的动作，是不是流程成败的依据？ 不是，就别让它说话算数。
