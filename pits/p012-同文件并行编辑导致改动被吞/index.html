P012 · 同一文件并行发多条编辑请求：只有末条生效，工具条条报「成功」

现象

给 src/pages/ai-daily/index.astro 同时改两处（副标题文案 + 元信息行的条件渲染），两条改文件请求在同一条消息里并行发出。

  • 两条都返回 Successfully edited file: …
  • 构建后产物里：副标题的新文案在，元信息行的新逻辑不在（还是旧的 <span>{issue.miniCount} 条速览</span>）
  • 源文件 grep "miniCount > 0" 无结果 → 改动确实没落盘，不是构建缓存问题

根因

两条编辑各自读取同一份文件快照、各自基于快照写回；后写入的把先写入的结果覆盖掉（写回的是“自己的快照 + 自己那处改动”，不含对方的改动）。工具层面无冲突检测，两处都报成功。

解法 / 预防规则

  • 同一文件的多处改动，串行发送（一次消息一个改动），或干脆一次调用写完整个区块。
  • 跨文件的改动才可以并行。
  • 改动后必须回读校验：grep -c "<新标记>" 源文件，而不是只看工具返回的 “Successfully”。
  • 最终以构建产物校验为准：改完构建一次，去 dist/ 里 grep 新逻辑/新文案是否存在（本次就是靠产物 grep 抓出来的）。
  • 面向用户的交付前自检同理：渲染后的页面截图 / 产物 grep 才算证据。

与 P008/P009 的关系

同一家族（「报成功 ≠ 生效」）的第三种形态：P008 是 CLI 升级的超时/缓存默认值骗人，P009 是多安装源的假成功，本条是并发的读写覆盖。共同检查项：任何写操作之后都要用独立手段回读确认，不要以工具返回码/措辞作为结论。

复现记录 2026-09-17（不限「两条」，且末条必赢）

在写小说连载版某章时又踩一次，并做了控制实验：

  • 10 条 Edit 同消息发出 → 回读只落地 2 条，其余 8 条静默丢失，10 条全部返回 success。
  • 控制实验（临时文件，3 行内容、3 条互不重叠的 Edit 同消息发出）→ 回读只有最后一条生效， 前两条未落地，3 条全部返回 success。

结论补齐两点：

  1. 不是「两条」的问题，是「同文件任意并行条数」——条数越多丢得越多。
  2. 末条必赢（写回时后写覆盖先写），此现象由「各自基于旧快照写回」直接推出。
  3. 失控后的补救：改用一次 Write 覆盖整篇，或逐条 Edit（每条单独消息）；改完必须回读校验。
