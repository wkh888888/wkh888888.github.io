现象

OpenShip 用非默认端口跑（api 10303 / dashboard 10304，默认是 4000 / 3001）。MCP 客户端接入时连续撞两堵墙：

# 症状 表面指向 真实原因
1 点授权 → 浏览器跳到 http://localhost:3001 → ERR_CONNECTION_REFUSED 以为 MCP 客户端配置写错 DEFAULT_PORT.dashboard 硬编码 3001，--dashboard-port 10304 没被派生进去
2 授权页点“同意” → 页面报「无法完成授权」 以为账号/权限问题 POST /api/tokens/mcp-authorize → 403，Origin http://localhost:10304 不在信任列表

关键证据：同一接口用不同 Origin 打，返回码不同 —— 说明是来源校验，不是凭证问题：

Origin: http://localhost:3001  → 401   # 默认端口，来源通过，只是没带凭证
Origin: http://localhost:10304 → 403   # 自定义端口，来源直接被拒
无 Origin                       → 401

根因

一句话：运行时参数（启动 flag）与代码内硬编码默认值之间存在断层，而来源校验/回跳地址这类安全逻辑往往读的是后者。

// server/index.js
const DEFAULT_PORT = { dashboard: 3001, api: 4000, web: 3000 };   // ← 硬编码

// 回跳地址：用 LOCAL_DASHBOARD_URL，但它不理会 runtime 的 --dashboard-port
// 信任列表：基础只有默认的 dashboard / api
extraTrustedOrigins = (env.OPENSHIP_EXTRA_TRUSTED_ORIGINS ?? "")
  .split(",").map(o => o.trim()).filter(Boolean);
trustedOrigins = [...new Set([runtimeTarget.dashboard, runtimeTarget.api, ...extraTrustedOrigins])];

于是：换了端口 → 回跳仍指向 3001；来源校验只放行默认端口 → 403。

第二个坑（更隐蔽）： 修复靠在 launchd plist 里加 EnvironmentVariables，但 serviceEnv() 只透传 OPENSHIP_DASHBOARD_DIR / OPENSHIP_HOME。手动执行 openship up 时，plist 级环境变量全部丢失，403 立即复发。 且 plist 里 KeepAlive=true，手动起的进程还会和 launchd 抢端口。

解法

1. 用显式环境变量补齐「运行时参数 → 安全校验」的断层

<!-- ~/Library/LaunchAgents/io.openship.up.plist -->
<key>EnvironmentVariables</key>
<dict>
  <key>OPENSHIP_LOCAL_DASHBOARD_URL</key><string>http://localhost:10304</string>
  <key>OPENSHIP_EXTRA_TRUSTED_ORIGINS</key>
  <string>http://localhost:10304,http://127.0.0.1:10304,http://localhost:10303,http://127.0.0.1:10303</string>
</dict>

改完必须重载才生效（plutil -p 确认解析结果，别只看文件内容）：

plutil -lint ~/Library/LaunchAgents/io.openship.up.plist
launchctl bootout   gui/$(id -u)/io.openship.up
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/io.openship.up.plist
launchctl print gui/$(id -u)/io.openship.up | grep -A8 "environment = "   # 确认变量真进去了

2. 用「对照 curl」定位 403 是来源问题还是凭证问题

curl -s -o /dev/null -w "%{http_code}\n" -X POST \
  -H "Origin: http://localhost:10304" -H 'Content-Type: application/json' \
  -d '{}' http://127.0.0.1:10303/api/tokens/mcp-authorize

403 = 来源被拒；401 = 来源通过、缺凭证。 两个 Origin 打同一接口对比，一次定性。

3. 走 MCP OAuth 三件套做端到端验收

修完别只看一个接口，把客户端要走的链路全打一遍：

curl -s http://localhost:10304/.well-known/oauth-protected-resource/api/proxy/api/mcp  # issuer 是不是新端口
curl -s http://localhost:10304/.well-known/oauth-authorization-server                  # issuer / 各 endpoint
curl -s -X POST -H 'Content-Type: application/json' -d '{...}' \
     http://localhost:10304/api/auth/mcp/register                                      # DCR 能否签发 client_id

issuer 必须是新端口；若仍是默认端口，说明第 1 步没生效。

4. 封装重启入口，杜绝「手动 up 丢环境变量」

已落地 ~/bin/openship-restart：plutil 校验 → kickstart -k → 回读环境变量 → 探端口 → 打一发 Origin 对照检查。重启一律走它，不要手敲 openship up。

预防规则（建议上浮 L1）

  • 服务跑非默认端口时，必须同时检查「回跳地址」与「来源信任列表」 —— 这两处最容易残留默认端口硬编码。改端口的验收清单：issuer / redirect_uri / trustedOrigins 三处一致。
  • launchd 服务的配置一律放 plist，并且只通过 launchctl kickstart/bootstrap 重启；手动跑 CLI 的 up/start 会绕过 plist 环境变量。
  • 改 plist 后必须回读运行时环境（launchctl print ... | grep environment），文件写对 ≠ 进程读到。
  • 区分 403 与 401：403 查来源/权限，401 查凭证。用两个 Origin 对照一次定性，不要靠猜。
