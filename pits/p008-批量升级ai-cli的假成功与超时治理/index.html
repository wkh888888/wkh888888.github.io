P008 · 批量升级 AI CLI：exit 0 不等于升级成功，超时/缓存/代理三个默认值都在骗人

自研的 agentctl（~/projects/agentctl）一次全量升级，12 个 Agent 里 5 个有问题：

现象

自研的 agentctl（~/projects/agentctl）一次全量升级，12 个 Agent 里 5 个有问题：

Agent 日志结果 真实情况
Gemini CLI failed (exit 124) 超时 180s 卡在非交互/信任提示上，不是纯粹网络慢
OpenCode failed (exit 124) 超时 180s 同上
Cursor CLI failed (exit 1) ETIMEDOUT 裸连外网，本机代理没注入
Kimi Code ok（假成功） 只打印了 “To update manually, run: curl …” 就 exit 0
Hermes ok（假成功） 输出 “⚠ Update partially complete”，SQLite WAL bug 未修复仍 exit 0
openclaw failed 自身拒绝：“package manager owner is unknown”

agentctl check 另有 7 项 unknown，看不到有没有更新。

根因

一句话：把「命令退出码」当成「升级结果」，把「固定长超时」当成「没事」，把「查不到 latest」当成「没有更新」。

三条具体缺陷：

  1. 假成功：多数 CLI 的自更新只负责“提示”，不保证“完成”，且统一 exit 0。 校验缺失 → Kimi / Hermes 这类被记成成功。
  2. 超时与并发：单个命令 180s 且串行，两个卡住就 6 分钟；同时环境里没有代理变量 （P004：代理是按需注入，不是全局 export），外网类操作必然 ETIMEDOUT。
  3. latest 缓存反噬：注册表查不到时回落到旧缓存，而旧值比已安装版本还旧， 版本比较给出 lat < cur → up to date，于是“缓存过期”被包装成“已是最新”。 实测 claude 已装 2.1.267，缓存里是 2.1.236 → 显示 up to date，纯属谎言。

解法

改 agentctl（已落地，备份 src.bak-20260910/）：

  1. 升级后回读版本再判定，而不是看退出码：
    • 版本变了 → OK
    • exit 0 但输出含 partially complete / manually / Update refused / not replaced → WARN
    • 自更新后版本没变且输出没有 up to date → WARN（Kimi 立刻现形）
    • 非 0 退出 / 超时 / 网络错误 → FAILED
    • 注意边界：包管理器命令（brew/npm/pipx）exit 0 即算成功，不能用“版本没变”判 WARN
  2. 超时 90s 可配 + 并发 4：同类包管理器（brew / npm / pnpm / yarn / pip / cargo）用锁串行，其余并行。
  3. 代理四级回退：--proxy > AGENTCTL_PROXY/HTTPS_PROXY > 配置文件 > 自动探测本机 7890/7897/1087/8888/1080。
  4. 缓存只许报新不许报旧：缓存版本 < 已装版本 → 标 stale cache (x.y.z) + unknown，绝不谎报 up to date。
  5. --only-outdated：先 check 再只升有更新的，12 个里只跑 3 个。
  6. 抑制 Homebrew 的 30 天 cleanup 与 hint 横幅（省几十秒 + 一屏噪音）。

效果：gemini 从 180s 卡死 → 6.3s 快速失败并暴露真实错误（~/.gemini/settings.json 里 mcpServers.bt-panel 多了 disabled 键 + Gemini Code Assist 个人版已停止支持）； unknown 从 7 项降到 4 项且每项带原因；Kimi 从假 ok 变成 WARN + 可直接复制的修复命令，退出码 3。

预防规则（上浮 L1 的候选）

判断任何“批量升级 / 批量执行外部命令”的工具是否可信，按这个检查项过一遍：

# 检查项 不通过的表现
1 完成后是否回读状态校验，而不是只看退出码 exit 0 但什么都没变，记为成功
2 是否有可配超时，且默认不至于拖垮整批 单条 180s × 串行
3 是否需要代理，有没有回退链 裸连 → ETIMEDOUT
4 缓存值是否可能比现状更旧，旧了怎么处理 缓存 2.1.236 < 已装 2.1.267 → 谎报 up to date
5 输出能否区分 ok / warn / failed，退出码是否区分 全 ok，看不出部分完成
6 结尾有没有汇总（before → after / 耗时） 一屏流式日志，得自己翻

一句话铁律：凡是“我帮你批量升级/批量执行”的工具，都要先问它拿什么证明真的做成了。
