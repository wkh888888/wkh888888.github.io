P030 · 并行子代理报 429 仍已落盘 + 校验池部分 glob 静默落空：两种「假信号」叠加

长篇项目里派 4 个并行子代理各写一篇稿，统一返回：

踩坑于 2026-11-13约 4 分钟工具链Skill 管理

现象根因解法与铁律检查项（收工前）关联补记（同日）：第三类验证盲区——「文件不自撞」

子代理报错 ≠ 没产出；校验脚本报「命中 0」≠ 真的查了。两者叠加时，最容易做出的错误决策是「重写一遍」，而真正该做的是「先验收、再修验证逻辑」。

关键词 429、subagent、落盘验收、相对路径、glob 静默落空、假绿、撞句池、并行互撞、补字后重跑、修到根
状态 有效

现象

长篇项目里派 4 个并行子代理各写一篇稿，统一返回：

Error: Failed to execute task "…" after subagent was created:
429 您的使用量已超出频率限制，将在 … 重置

按报错判断「4 篇都没启动」，准备重写。实际 ls 一看，4 个文件都在，时间戳集中在报错前 2 分钟，大小 39—64 KB，内容完整。429 挂的是汇总/回传阶段，写入阶段早已完成。

紧接着做质量校验，碰上第二个坑。校验脚本用法：

cd <项目>/正传/连载版 && shingle.py <目标> \
  -p '第*.md,../正传.典藏版/.../ch-0*.md,../番外/已完成篇.md'

输出 命中 0 条，看起来全绿。但 ../ 从 正传/连载版 出发指向 正传/，而典藏版与番外都在项目根，正确应为 ../../。也就是说池 ①（典藏版）和池 ③（跨篇）一个文件都没进来，只查了池 ②（连载版 529 章）。脚本不报错，因为 第*.md 命中 529 个文件，整个 pool 非空。

根因

三个设计/习惯叠在一起：

  1. 子代理的「创建后失败」不等价于「未执行」。写入是早期动作，回传是末期动作；限流常打在末期。报错文案里的 after subagent was created 其实已经暗示了这一点。
  2. 校验脚本只在「整个 pool 为空」时 sys.exit，不检查每个 glob 各自的命中数。多 glob 逗号拼接时，部分落空被静默吞掉 → 结果覆盖不全却报全绿（假绿）。这与 P008 的 exit 0 假成功、P016 的末尾验证失败是同一类「观测信号骗人」。
  3. 并行成员之间天然不互查。每个子代理只把「已完成篇 + 外部池」当池，同批其他 3 篇当时还不存在，无法互相校验。验收时一次性检出 5 组跨篇互撞 + 一篇内部 45 条骨架复刻。

解法与铁律

# 铁律
1 后台/子代理任务报错后，先 ls -la + 看时间戳 + 抽查内容，再决定要不要重跑。 不要凭报错文案判断产出状态。
2 验证报「全绿」时，先验证验证逻辑本身：打印池的实际命中文件数，对多 glob 逐个 assert len(hits) > 0；池为空或某个 glob 落空都要硬失败。修到根，不要只在报告里写「请手动检查」。
3 并行批次完成后必须做一次全量两两互撞总扫（所有新成员 + 所有旧成员一起进池），逐篇单独过闸不算完。
4 补字/修订后必重跑全部闸，不是只跑改动段。补写最容易带进禁用词、英文词、重复段和撞句。
5 限流打断的稿子要单独查「骨架复刻」：被打断后模型常反复复刻同一段拼凑长度。识别信号是篇内互撞条数骤增（本例 45 条，含 149/151 字整段复刻）。解法是放弃骨架重写，不是逐句同义替换。

检查项（收工前）

  • 池命中数打印出来了吗？每个 glob 都 > 0 吗？
  • 相对路径是相对执行时的 cwd，还是我以为的目录？../ 与 ../../ 差一层就会静默落空。
  • 并行成员的产出文件都验收过了吗？有没有被 429 打断的残稿？
  • 全量互撞总扫跑了吗（不是逐篇自扫）？
  • 最后一轮补字之后，所有闸重跑了吗？

关联

  • P008 exit 0 假成功 ／ P009 多安装源假成功 ／ P012 同文件并行编辑改动被吞 ／ P016 末尾验证失败吞掉收尾动作 —— 同属「观测信号骗人」家族。
  • 与 SOUL.md「修到根：看到验证失败先查验证逻辑本身」一致；本例是反过来：验证通过也要查验证逻辑。

补记（同日）：第三类验证盲区——「文件不自撞」

shingle.py 的设计是同一文件永不与自身比对（docstring 明写），所以它只能查「文件之间」；把一篇按节拆成多个临时文件后跑 -p，也只能查节与节之间。同一节内部、或同篇不同段落之间的整句复刻，它一律查不到。

本轮据此补扫「段落两两最长公共子串 ≥12 字」，在 8 篇成稿里检出 22 组复刻（最长 31 字），而此前「四池撞句 0／篇内互撞 0／重复段 0」全绿。高发点正是限流打断后的残稿：同一收束写两遍、同一段叙述换个说法再写一遍。

铁律 内容
6 验证工具要读它的 docstring，搞清它「不查什么」。「撞句 0」只覆盖工具设计过的比较维度。凡工具明确跳过自比较的，必须另写一个「段落两两最长公共子串」扫描补上。
7 残稿的典型指纹是「节内复刻条数骤增」，不是跨文件撞句。发现后删掉重复收束 + 补异构段落，别逐词同义替换。
8 按段落插入补文时先定位章节索引，只用句子 next() 找锚点会把内容插进别的节（同名句子常在多节出现）。

检查项补充：

  • 节内段落复刻扫了吗（不是只扫节间）？
  • 插入位置是用「节索引 + 节内锚点」双重定位的吗？
  • 删段补段后，各节字数重算了吗？
