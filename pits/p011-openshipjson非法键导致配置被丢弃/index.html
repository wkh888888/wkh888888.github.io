现象

openship deploy（本地目录部署）连续 4 次失败，每次报错都指向不同且都误导的方向：

# 报错 误导方向
1 Deploy failed: Cannot read Openship edge routes 以为缺 Edge 组件
2 Endpoint target (30202): Static deployments cannot expose port-targeted routes 以为端口配错
3 同上（改了库里的项目设置后） 以为改错了地方
4 同上（改完 openship.json 后仍报） 以为配置没生效 
openship deploy --name ai-probe --watch
# ✖ Folder deploy failed
# Pre-deploy checks failed: Endpoint target (30202): Static deployments cannot
# expose port-targeted routes. Use a static target path instead.

根因（两个叠加，第一个是关键）

① 配置里有一个 schema 不认识的键 → 整份文件被丢弃

openship.json 里写了 "workload": "web"。但官方 schema 是：

{
  "additionalProperties": false,
  "properties": {
    …
    "productionMode": { "enum": ["host", "static", "standalone"] },
    // ← 根本没有 "workload" 这个属性
  }
}

additionalProperties: false + 一个未知键 ⇒ AJV 整体拒绝整个对象，不是“忽略这一个字段”。

CLI 侧对应逻辑：

// server/index.js:298725  extractOpenshipConfig()
const { config, errors, warnings } = parseOpenshipConfig(raw);
if (!config) return { diagnostics: { errors, warnings: [], wholeFile: true } };  // ← 整份丢弃

CLI 会打印 openship.json was ignored entirely — deployed with detected settings，但这句在失败时不一定滚到屏幕上（错误是从后续接口抛回的 ApiError，捕获分支只 err(e.message)，不输出 configDiagnostics）。

→ 配置全丢 → 退回自动探测 → 项目按目录结构被重新分类。

② 项目被探测成 monorepo，而 CLI 的 folder 部署读不到子应用的 startCommand

目录是两个 package.json：根（express 后端）+ client/（vite 前端）。扫描结果：

{ "projectType": "monorepo", "stack": "vite",
  "startCommand": "",                       // ← 顶层是空的！
  "monorepoApps": [
    { "rootDirectory": ".",      "stack": "express", "startCommand": "node server.js" },
    { "rootDirectory": "client", "stack": "vite",    "startCommand": "" } ] }

而 deployFolder（dist/index.js:1603）只读顶层：

const hasServer = Boolean(scan.startCommand);      // → false
await apiRequest("/projects/ensure", {
  projectType: scan.projectType,                   // monorepo 被原样存下
  framework: scan.stack,                           // → "vite"
  productionMode: hasServer ? "standalone" : "static",   // → "static" ← 死因
});
// 注意：body 里根本没有 monorepoApps —— 子应用配置被丢掉

hasServer=false ⇒ productionMode=static ⇒ 预检：

// server/index.js:300415  checkPublicEndpoints()
const workload = snapshotToClass(snapshot).workload;
if (workload === "static" && hasPortTarget) {
  fail(…"Static deployments cannot expose port-targeted routes…");
}

端口 30202 是 openship.json 写的（这份值恰好被扫描读到了），于是「静态部署 + 端口端点」互斥 → 判死。

解法

1. 修配置：删掉 schema 里没有的键

用 schema 校验，别靠猜。校验方式：直接 fetch https://openship.io/openship.schema.json，比对每个键是否在 properties 里；有 additionalProperties: false 时，一个多余键就是全盘失效。

改后：

{
  "$schema": "https://openship.io/openship.schema.json",
  "framework": "express",
  "packageManager": "npm",
  "rootDirectory": ".",
  "installCommand": "npm i && npm i --prefix client",
  "buildCommand": "npm run build",
  "startCommand": "node server.js",
  "runtime": "bare",
  "productionMode": "host",
  "port": 30202,
  "domains": []
}

（删掉 workload 与对 bare 无意义的 buildImage；显式补 rootDirectory: "."。）

2. 关键诊断动作：把扫描结果原样打出来，不要猜

官方 folder 部署五步流程，可以手工逐段调，中间结果全部可见：

SID=$(openship api /projects/folder/session -X POST \
  -d '{"name":"scan-probe","packageManager":"npm","stack":"node"}' | python3 -c 'import json,sys;print(json.load(sys.stdin)["sessionId"])')

tar -czf /tmp/x.tar.gz --exclude=./node_modules --exclude=./.git -C . .
TOKEN=$(python3 -c 'import json;print(json.load(open("'"$HOME"'/.openship/config.json"))["contexts"]["default"]["token"])')
curl -X POST "http://localhost:10303/api/projects/folder/upload/$SID" \
  -H "x-upload-ticket: <ticket>" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/gzip" --data-binary @/tmp/x.tar.gz

openship api /projects/folder/scan/$SID -X POST -d '{}'     # ★ 这一步是破案关键

scan 的返回会直接把 stack / projectType / startCommand / monorepoApps / productionMode 全摊开 —— 一眼看出「被判成 monorepo 且顶层 startCommand 为空」。

3. 绕过 CLI 缺陷：ensure 时自己纠正 projectType

openship api /projects/ensure -X POST -d '{
  "projectId":"proj_…","name":"ai-probe","gitProvider":"upload",
  "framework":"express","projectType":"app",          # ← 把 monorepo 改回单应用
  "packageManager":"npm",
  "installCommand":"npm i && npm i --prefix client",
  "buildCommand":"npm run build","startCommand":"node server.js",
  "outputDirectory":"","rootDirectory":".",
  "hasBuild":true,"hasServer":true,"productionMode":"host","port":30202 }'

openship api /deployments/build/access -X POST -d '{
  "projectId":"proj_…","uploadSessionId":"<SID>","environment":"production" }'

→ 预检直接通过，install + build 全绿。

4. 或者用 MCP 改库里的项目记录

mcp__openship__patch_projects_by_id 可以直接写 workloadType / productionMode / hasServer / framework。注意：/projects/ensure 会用扫描结果覆盖这些字段，所以要改必须在 ensure 之后。

预防规则（建议上浮 L1）

  • 给工具写配置文件时，先 fetch 官方 schema 逐键核对。 有 additionalProperties: false 的 schema，一个不认识的键 = 整份配置作废，而且报错往往出现在很久之后、指向完全无关的地方。
  • 配置类问题先验证「配置到底被读到了吗」，再查业务逻辑。判据：把中间产物（扫描结果 / effective config / 项目记录）原样打印出来，和磁盘上的文件逐字段对比。不一致 → 配置根本没进去。
  • CLI 报错 ≠ 根因。 连挂多次且每次报错都不同时，停下来找共同的上游（本例是“配置整份被丢弃”），不要逐个错误去追。
  • 工具自带的多步流程（本例的 session→upload→scan→ensure→deploy）可以手工逐段调用来定位，比黑盒跑整条链高效得多。
