一句话

macOS 上 OpenShip 的路由/证书提供者是写死的空实现（NoopInfraProvider），宿主 OpenResty 这条代码路径被平台判断直接挡掉 —— 所以「让 OpenShip 托管域名」只有 Docker 容器一条路。宿主安装 OpenResty 只能让部署不再因读不到路由清单而致命失败，不会、也不可能真正接管路由。

故事线：装完 OpenResty，错误“变轻”了但没消失

同一条部署链，装 OpenResty 前后：

装之前 装之后
日志 Missing: edge Missing: docker, edge
接着 Failed to install edge: needs root Failed to install docker: needs root
结果 致命 Cannot read Openship edge routes → 部署失败 warn Edge/routing setup failed — deploy continues → 部署成功
路由 无 Registering route ai-probe.localhost → http://127.0.0.1:30202（只写进 DB，无人消费）

原因：OpenShip 里那段路由装配是 try/catch 包着的 ——

try {
  if (plannedRoutes.length > 0 || needsStrictLoopbackInventory) { /* ensureEdge ... */ }
} catch (err2) {
  logger4.log("Edge/routing setup failed — deploy continues; services run and routing is retried later", "warn");
}

而 bare 运行时下 needsStrictLoopbackInventory 恒为真：

function usesHostLoopbackUpstream(strategy, runtime) {
  return runtime.name !== "cloud"
      && (strategy === "loopback-port" || runtime.name === "bare" || …);   // ← bare 恒真
}

ensureEdge 内部会先 scanOpenshipEdgeStrict() 读宿主 openresty -T 的路由清单。机器上没 OpenResty 时这个读取抛错 → 被 catch 的是外层，但错误向上冒泡成了致命失败；装了 OpenResty，读取通过，于是流程能继续走到后面的 docker 检查，失败在那里被降级成 warn。

→ OpenResty 的作用是“让代码走完”，不是“让域名能访问”。

为什么宿主 OpenResty 接不了路由（决定性代码）

createInfraProvider()（server/index.js:63754）是按固定顺序短路返回的：

async function createInfraProvider(_mode, config2, executor, edgeContainer) {
  if (edgeContainer) { …localContainerEdgeProvider… }        // ① 显式容器（OPENSHIP_EDGE_MODE=docker）
  const remoteEdge = await resolveOurEdgeContainer(executor)
  if (remoteEdge) { …containerEdgeProvider… }                // ② 主机上已有的 edge 容器
  if (executor instanceof LocalExecutor && process.platform !== "linux") {
    return new NoopInfraProvider();                          // ③ ★ macOS + 本地 → 空实现
  }
  …detectOpenRestyPaths / ensureOpenRestyConfig / NginxProvider…   // ④ 宿主 OpenResty（仅 Linux）
}

macOS + 本地 executor 永远落在分支 ③，拿到一个什么都不做的路由/证书提供者：

class NoopInfraProvider {                 // server/index.js:62216
  async registerRoute(_route) {}          // ← 空函数体
  async removeRoute(_domain, _opts) {}    // ← 空函数体
  async provisionCert(domain) { return { domain, expiresAt: "", issuer: "none", verified: false }; }
}

→ 部署日志里那句 Registering route ai-probe.localhost → http://127.0.0.1:30202 只写进 DB，registerRoute() 把它吞掉。所以「路由已登记」和「域名能访问」是两件事。

实测三重印证分支 ③ 生效：

判据 结果
/opt/homebrew/etc/openresty/nginx.conf vs nginx.conf.default 逐字节相同 → OpenShip 从未改过宿主 nginx 配置
OpenResty 前缀内搜 openship 产物 零
~/.openship/logs/instance.log 里的 [openresty] 行 一条都没有（分支 ④ 从未进入）

（对比：detectMail() 明确有 flavor: "host" 分支，说明“宿主模式”是一处一议的特例，不是通用能力。）

Edge 侧同样只有容器：detectEdge2() 只调 detectEdgeContainer()；installContainerEdge 在检查 Docker 之前就先过提权门 prepareExecutor → privilegedExecutor，macOS 上 isRoot=false/canSudo=false → 直接 refuse，给 sudo 也没用；SYSTEM_COMPONENT_DEPENDENCIES = { edge: ["docker"] }。

openship doctor 也直说：

{ "name": "Edge", "state": "warn", "detail": "docker unavailable — can't check" }

那么「域名 + HTTPS」到底有几条路（更正：不止一条）

严格区分两件事 —— 交给 OpenShip 托管 vs 只要域名能访问：

方案 需要什么 OpenShip 管 端口
A. OpenShip edge 容器（启 Docker/OrbStack） Docker 在跑 ✅ 原生托管 80/443
B. 自建反代 + 绑 :80 root（本机无免密 sudo，需输密码） ❌ 手工 80/443
C. 自建反代 + 绑 ≥1024 端口 什么都不需要 ❌ 手工 如 8080，URL 带端口
D. 把 deploy target 换成 Linux 主机 Linux 机器 ✅ 80/443
  • 「让 OpenShip 自己托管」→ 只有 A，因为 macOS 的分支 ③ 写死返回 Noop，宿主 OpenResty 那条路被平台判断直接挡掉（这是设计如此，不是配置问题）。
  • 「只想让 ai-probe.localhost 能打开」→ 还有 C：非 root 无法 bind :80（实测 socket.bind(("127.0.0.1",80)) → PermissionError），但 ≥1024 端口不需要任何权限。用已有的 /opt/homebrew/bin/nginx（或新装的 OpenResty）监听 8080、proxy_pass 到 127.0.0.1:30202，就能用 http://ai-probe.localhost:8080 访问。代价：带端口、无自动 HTTPS、脱离平台管理。

所以早先那句「要域名 + HTTPS 只能启 OrbStack」说过头了 —— 准确说法是：要域名在标准 80/443 上、且由 OpenShip 托管，只有 A 一条路。

附：Apple Silicon 装 OpenResty 的坑（可复用）

brew tap openresty/brew
brew trust openresty/brew           # 官方仓库 github.com/openresty/homebrew-brew
brew install openresty/brew/openresty
# ✗ ./configure: error: the GeoIP module requires the GeoIP library
#   （M 系列已知问题，homebrew-brew issue #53）

brew install openresty/brew/openresty --without-geoip    # ✓ 54 秒装成

Formula 自带 option "without-geoip", "Compile without ngx_http_geoip module"。

验收判据（OpenShip 会这样判）：

command -v openresty            # 需在 plist PATH 内，如 /opt/homebrew/bin
openresty -T >/dev/null 2>&1; echo $?    # 必须 0
openresty -T 2>/dev/null | grep -c "server {"   # 需 > 0

注意 OpenResty 不是常驻服务，OpenShip 只需要能读到它的配置；别去 openresty 起进程（默认 conf listen 80，非 root 起不来）。

后续发现：域名记录不能删（“无用”≠“可删”）

想“清理”那条域名警告时踩了一步：把域名记录删掉，项目就再也部署不了。

现象 根因
删域名后部署 → 403 CLOUD_REQUIRED_MANAGED_PROJECT_DOMAIN requestBuildAccess()：routeState.publicEndpoints 为空时自动补 defaultFreeEndpoint() —— 一个免费 *.opsh.io 端点。免费端点需要 Openship Cloud 路由，自托管下必 403
只把域名加回来仍 403 新建域名没有 targetPort，被 routeDomainRowToPublicEndpoint 丢弃（它要求 port/targetPath 恰好有其一）→ buildRouteState() 的 publicEndpoints[0] 为 undefined → 仍判「没有自定义域名」
重部署时 Port 30202 is already in use 旧部署进程已孤儿化（PPID=1）但继续监听端口，需先 kill

正确的部署方式：把域名写进 openship.json，并在部署请求里显式传 publicEndpoints：

"domains": [ { "domain": "ai-probe.localhost", "port": 30202, "type": "custom" } ]

→ publicEndpoints: [{ "domainType": "custom", "customDomain": "ai-probe.localhost", "port": "30202" }] （port 必须是字符串 —— 传数字报 400 Expected string）

教训：判断一个对象能不能删，不能只看「它有没有在产生价值」，还要问「删掉它会不会触发别的行为」。 这条域名行同时承担「路由端点声明」和「占位、防止回落到免费域名」两个职责 —— 与“有没有人真的访问这个 URL”完全无关。删掉它触发了自动补全逻辑，把项目推到了一个必然失败的状态。

routingUnsynced 也清不掉：它读自部署记录的 meta.deployWarning，自托管项目必须有自定义域名、域名没证书就每次部署都写 → 每次都是 true。POST /api/projects/<id>/routing/retry 同样无效，只会返回「需要 Docker 才能恢复 edge」。只有让 edge 真正跑起来才会消失。

预防规则

  • 看到“组件缺失”先分清是“读取失败致命”还是“安装失败降级”。 本例装宿主 OpenResty 只解决了前者；误以为它能解决后者会白等一轮。
  • 判断某个组件有没有“宿主模式”，别猜 —— 看 detect 函数有没有 host 分支。 有（mail）说明支持；没有（edge）说明只能容器。
  • macOS 上任何要占 80/443 的方案，先确认特权来源：root / 免密 sudo / Docker 端口转发，三选一，缺一即为死路。

2026-09-11 后续：edge 容器手动装成功了（推翻「macOS 上 NoopInfraProvider 恒定」的结论）

关键更正：createInfraProvider() 的分支①（已有 edge 容器）优先于平台短路。之前说「macOS + 本地 executor 永远 Noop」不准确 —— 准确说法是「无 edge 容器时才落到 Noop」。只要 docker ps 能看到 openship-edge，macOS 上路由就走容器通道，完全可用。

三条安装通道都堵死后手动复刻成功的完整 runbook：

通道 结果
openship edge up CLI 有 requireLinux() 守卫，macOS 直接退出
面板/POST /api/system/install prepareExecutor 提权门：无免密 sudo → Installing edge needs root
手动 docker run（buildEdgeRunCommand 原样） ✅ 成功

要点：

  1. 前置一次性 sudo：sudo mkdir -p /var/lib/openship/edge/{sites-enabled,acme} /etc/letsencrypt /opt/openship/static && sudo chown -R $(whoami) …（/var/lib、/opt 在 macOS 都是 root 的）。
  2. docker run -d --name openship-edge --network host --restart unless-stopped -v <四个挂载> ghcr.io/oblien/openship-edge:<cli版本>。OrbStack 的 --network host + 80/443 绑定不需要 root。
  3. 起来后 POST /api/projects/<id>/routing/retry 从「requires Docker」变成 {"ok":true}，vhost 自动写进 /var/lib/openship/edge/sites-enabled/，Host: ai-probe.localhost 打 :80 → 200，http://ai-probe.localhost 直接可访问。
  4. .localhost 拿不到 Let’s Encrypt 证书（Certbot 报 no certificate produced）→ 面板 “Verify DNS” 警告对 .localhost 永远清不掉，HTTPS 死路，属预期。
  5. 面板三条警告的实际收敛：Docker ECONNREFUSED ✅ 消（Docker 在跑）；routingUnsynced ✅ 消（新部署 meta 不再写 deployWarning）；Verify DNS ❌ 永在（.localhost 无证书）。
  6. OrbStack 默认不开机自启，重启后 edge 掉线；应用本身不受影响（仍 127.0.0.1:<port>）。

教训： ①「恒定短路」类结论要标注前提条件——分支顺序里只要有更高优先级的出口，前提一变结论就翻。②平台的安装 API 被提权门锁死时，读它的 ensure* 实现，里面的降级路径（rootOrDegrade）往往才是真实的最小需求。③.localhost 域名注定无 HTTPS，别再为它点 Verify。
