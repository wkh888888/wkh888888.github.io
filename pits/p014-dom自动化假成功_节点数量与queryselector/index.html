一句话现象

脚本每一条都打印成功/失败，但结果全错：要么所有记录都被误判失败，要么字段其实根本没写进去、 脚本却显示 set。两类问题的共同点是——用 DOM 的“存在/数量”代替了“值”来判断状态。

案例 A：用节点数量判断“有没有校验错误” → 每条都被误杀

表单里常驻 5 个 .cube-check-error 容器，class 是 cube-card-editformitem2 fieldValue cube-check-error（OA字段值容器的通用类名，不是“有错误”的标志）。

实测这 5 个节点的属性：

属性 值 结论
textContent 全为空 只有这一项能区分
offsetParent 不为 null 可见性过滤不掉
display block 可见
尺寸 299x30 等，有实际大小 尺寸过滤也无效

判定逻辑实测对比：

判据 结果
querySelectorAll('.cube-check-error').length > 0 恒为 5 → 每条都判失败（10 条全废）
文本非空 && offsetParent !== null 0，但 offsetParent 条件是无效装饰
只看文本非空 0 ✅

⚠️ offsetParent 不能用来判可见性：position: fixed 元素的 offsetParent 恒为 null， 会把真实错误提示一起滤掉 —— 那是比误判更危险的静默漏判。

结论：唯一可靠判据是「文本非空」。系统只在真的有错误时才往容器里写文本。

案例 B：querySelector('textarea') 命中占位元素 → 必填项其实一直为空

表单里有 2 个 textarea：

idx id 尺寸 说明
0 无 id 707x10 占位元素 ← querySelector 命中的是这个
1 field12341 707x88 真实的「描述」字段

写进 idx0 后，值确实被保留（React 不会重置）→ 脚本打印 Description: set → 看似成功。 但真实描述字段始终为空 → 提交时必填校验不过 → 表单不关闭 → 整批 10 条全部失败。

反直觉的地方：写入操作本身是成功的，只是写错了对象。所以任何“写完就打印 set”的代码都发现不了。

通用规则（可跨项目）

  1. 写 DOM 字段后必须回读校验，只打印 set / ok 等于没校验。 回读要读目标元素的真实值（#field12341.value），不是“我写入的那个值”。
  2. 不要用节点“数量”判断状态。常驻空容器会让 length > 0 恒为真； 状态的载体是内容（文本/属性/值），不是元素个数。
  3. 不要用 offsetParent 判可见性，它对 position: fixed 恒为 null。 要判可见用 getComputedStyle（display/visibility/opacity）+ getBoundingClientRect()。
  4. querySelector 取“第一个”元素前，先确认页面上有几个同类元素。 一层 querySelectorAll(...).length 的探测就能避免，成本极低。
  5. “提交后表单不关闭”通常 = 某个必填项没写进去，不是网络问题。 错误数组可能为空，不要只依赖错误提示，要逐个字段回读实际值。

排查手法（本次有效）

写一个一次性 CDP 脚本，打开目标表单，把候选节点全量 dump（id / class / 尺寸 / offsetParent / textContent / 父子文本），再拿着真实结构去改脚本 —— 比反复猜选择器快得多。

const { chromium } = await import('/opt/homebrew/lib/node_modules/playwright/node_modules/playwright-core/index.mjs');
const info = await (await fetch('http://[::1]:9223/json/version')).json();
const b = await chromium.connectOverCDP(info.webSocketDebuggerUrl);
const page = b.contexts()[0].pages().find(p => p.url().includes('internal.example.com'));

注意：Chrome 调试端口可能只在 IPv6 上监听，http://127.0.0.1:9223 会 404， 要用 http://[::1]:9223/json/version 动态取 webSocketDebuggerUrl。
