P001 · 邮件入口三撞车：Skill 与 MCP 混用导致 4 次授权失败

现象

用户要求「给 walkerhua@vip.qq.com 发个 test」。助手加载了 agently-mail skill，走 agently-cli auth login 的 OAuth device-code 流程，连续 4 次失败：

次数 结果 直接原因
1 13 秒后 login failed 后台启动未分配 pty，进程立刻读到 stdin EOF
2 10 分钟 authorization expired 浏览器端未授权（进程本身正常）
3 8 秒后 login failed 同第 1 次
4 10 分钟 authorization expired 已改用 pty，进程正常挂满有效期，浏览器端仍未授权

根因

不是授权没点、也不是网络问题，是选错了工具层。

用户截图显示管理端提示：「Workbuddy 已存在智能体邮箱，无需再绑定」 —— 说明该账号的 agently-cli 独立绑定入口已被官方关闭。而同一个能力其实由 WorkBuddy 内置的 MCP connector mcp__agent-mail 提供，零授权、直接可调用。

根本失误在于：收到任务后先去搜 Skill 加载，而没有先看当前会话已经挂了哪些 MCP 工具。

环境里实际存在 4 个名字撞车的邮件入口

名称 类型 服务商 结局
agently-mail Skill（提示词 + agently-cli） 腾讯 agent.qq.com ⛔ 已移除
agent-mail（name: agentmail） Skill，第三方 agentmail.to（与腾讯无关） ⛔ 已移除
智能体邮箱（name: agentmail） 上者的中文马甲 agentmail.to ⛔ 已移除
mcp__agent-mail MCP connector 腾讯 agent.qq.com ✅ 唯一可用

第三个是查台账时从「复用标记 ✅」条目里挖出来的：目录名中文化，但 frontmatter 的 name 仍是 agentmail。按目录名查重会漏。

解法

  1. 放弃 agently-cli，直接调 mcp__agent-mail__SendMessage，一次成功（queued: true）。
  2. 三个邮件 Skill 全部禁用移除，备份在 /tmp/skill-backup-20260903/（真实目录 + tar.gz 各一份，零物理删除）。

mcp__agent-mail__SendMessage 正确用法

{
  "to": [{"email": "walkerhua@vip.qq.com"}],
  "subject": "test",
  "body": "test"
}
  • to / cc / bcc 是 {email, name?} 对象数组，传 ["user@example.com"] 会报 schema_type: array field_type: string。
  • 首次调用必返 42801 + confirmation_token（5 分钟有效）→ 必须展示 operation_summary → 停下等用户明确许可 → 再带 token 重发。禁止自己确认自己；token 过期就重新调用拿新的。
  • 发件别名 walkerhua@agent.qq.com，日配额 50 封（响应头 x_dailyquota_remaining 可见）。

预防规则（已上浮至 ~/.workbuddy/MEMORY.md）

  1. 先扫 MCP，再考虑 Skill。有 mcp__<服务>__<动作> 就直接调，不去加载同名/近名 Skill。MCP = 宿主托管凭据；Skill = 提示词文档，常附本地 CLI 且多半要自行 OAuth。
  2. 加载 Skill 前按 frontmatter 的 name 字段查重，不看目录名。
  3. 遇「已存在账号，无需再绑定」类提示即判结构性死路，不重试第二次。
  4. 该规则适用于所有能力域（日历 / 网盘 / IM / 代码托管），不限于邮件。

通用排查手法（副产品）

后台跑交互式长命令（OAuth、安装向导等）时，不分配 pty 会导致进程秒退。用以下方式包裹可挂满有效期：

script -q /dev/null agently-cli auth login

判据：秒退 = pty 问题；挂满有效期仍失败 = 用户端/权限问题。两者不要混为一谈。
